## 1. Что это

**RTM** (retailtaskmanager) — подсистема задач для розничной сети: поставить задачу на
магазин или оборудование, выполнить её в поле с телефона, проверить результат, собрать
отчёт. Продуктовое имя — **«Пульс»**; позиционируется как полевой модуль IIoT-платформы
MITE (телеметрия оборудования живёт там, сюда приходит то, что требует человека на месте).

Одни и те же вещи называются по-разному, и это не разные сущности:

| Имя | Где встречается |
|---|---|
| RTM, retailtaskmanager | репозиторий, разговорное название |
| «Пульс», `pulse_tasks` | интерфейс, мобильный клиент, имена регламентов |
| `storetask-logics` | Maven-артефакт (`lsfusion.solutions:storetask-logics:7.0-SNAPSHOT`) |
| `StoreTask` | единственный `NAMESPACE` всего lsFusion-кода и префикс ручек API |
| Retail help-desk | проект в трекере Redmine; номера `#NNNNN` в коммитах и шапках модулей — оттуда |

Сервер написан на **lsFusion** (платформа 7.0-SNAPSHOT, PostgreSQL). Это декларативный
язык: данные — свойства (`DATA`) и вычисляемые выражения над ними, поведение — действия,
события (`WHEN`) и ограничения (`CONSTRAINT`), интерфейс — формы (`FORM`, `DESIGN`,
`NAVIGATOR`). Синтаксис по памяти здесь не принимается — источником служит справка
платформы, см. AGENTS.md.

Подсистема — **артефакт без собственного хоста**. Она подключается jar-зависимостью и
не знает, кто у хоста сотрудник и что у него магазин. Хостов два: ERP на базе mycompany
(`REQUIRE StoreTask`, мосты в `erp/`) и сам артефакт в одиночку (`StoreTaskStandalone`) —
на втором идёт вся разработка и проверка. Подробно — README.

## 3. Предметная модель

| Понятие | Класс | Модуль | Суть |
|---|---|---|---|
| Задача | `Task` | `task/StoreTaskCore` | единица работы: объект, тип, статус, автор, назначение, срок |
| Исполнитель | `TaskPerformer` (абстрактный) | `meta/TaskPerformer` | человек или группа; кем он является, решает хост |
| Подразделение | `TaskUnit` | `task/TaskUnit` | исполнитель-группа с иерархией для хоста без оргструктуры |
| Объект проверки | `CheckObject` (абстрактный) | `task/CheckObject` | на что ставится задача; дерево «магазин / касса / сканер» |
| Объект | `CheckAsset` | `fillable/CheckAsset` | готовая реализация `CheckObject` |
| Роль на объекте | `ObjectRole` | `task/ObjectRole` | «директор магазина», «региональный»: кто отвечает за объект |
| Тип, статус, приоритет, метка | `TaskType`, `TaskStatus`, `TaskPriority`, `TaskTag` | `task/StoreTask*` | справочники; тип определяет, чем задача выполняется |
| Выполнение | `Execution` | `task/Execution` | одна попытка выполнить задачу; у задачи их может быть несколько |
| Заполнение | `Filling : Execution` | `fillable/Filling` | выполнение по бланку: ответы на поля шаблона |
| Фотоотчёт | `SimpleExecution : Execution` | `corrective/SimpleExecution` | выполнение без бланка: снимки и комментарий |
| Шаблон, раздел, поле, колонка | `Template`, `Section`, `Field`, `Column` | `fillable/` | бланк: что спрашивать и как оценивать |
| Строка | `FillRow` | `fillable/FillRow` | строка табличного поля внутри заполнения |
| Правило авто-создания | `SchedulePlan` | `schedule/SchedulePlan` | «этот шаблон на каждый объект категории раз в N дней» |
| Уведомление, доставка | `Notification`, `Delivery` | `notification/` | запись журнала для человека и попытка отправить её наружу |
| Заявка извне | `TaskRequest` | `intake/TaskRequest` | событие внешней системы, из которого рождается задача |
| Гипотеза | `Hypothesis` | `hypothesis/` | проверка данных ERP кодом, который написала модель и утвердил человек |

Справочные значения адресуются **идентификатором, а не названием**: название переводится
и правится пользователем, идентификатор — контракт с кодом и с телефоном.

- Статусы: `new`, `in progress`, `acceptance`, `done`, `canceled` (последние два закрытые).
- Типы задач: `form` (процедура), `checklist`, `recount` (пересчёт), `pricing` (ценники),
  `corrective` (корректирующее действие), `issue` (поручение).
- Роли: `executor`, `supervisor`, системная `admin`.

Справочники заводит `seedRequiredData` — идемпотентно и на каждом старте сервера.

## 4. Жизнь задачи

1. **Создание** — руками в бэк-офисе, с телефона (`apiCreateTask`, в том числе офлайн),
   по графику (`SchedulePlan`), из внешней заявки, из черновика AI, корректирующей по
   замечанию проверки. Телефон адресует задачу своим UUID (`clientId`), сервер — номером
   `ST000123`; обе формы принимает `taskByAnyId`.
2. **Назначение и взятие.** `assignedTo` — на человека или подразделение; видимость
   считается с учётом иерархии. `takenBy` — отдельный факт «кто взял на себя»: это
   координация, а не замок, и переназначение его сбрасывает (`task/StoreTaskTakeover`).
3. **Старт выполнения.** `startExecution` — точка расширения: тип задачи сам решает, что
   создать. `executionKind` типа говорит клиенту, чем открывать задачу: `fill` — бланк
   (`form`, `checklist`, `recount`, `pricing`), `simple` — фотоотчёт (`corrective`, `issue`).
4. **Завершение.** Задача закрывается, когда успешны все её выполнения (`allDone`).
   Если тип или сама задача требует приёмки, вместо закрытия она уходит в `acceptance`.
5. **Приёмка** (`task/StoreTaskAcceptance`). Принимающий — человек по роли на объекте
   либо автор. Он принимает или возвращает с причиной; возврат — снова `in progress`.
6. **Проведение.** Переход в закрытый статус запускает `onProceed` — ровно один раз на
   задачу. Отсюда уходят уведомления и рождаются корректирующие. Правила того, что можно
   делать внутри реакции, — README, раздел «Reacting to a closed task».

Статус, который поставила система, помечается `autoStatus`; матрица переходов по ролям
(`task/StoreTaskWorkflow`) судит только выбор человека.

## 5. Движок заполнения

Все «бланочные» типы работают на одном движке: `Template → Section → Field`, у табличного
поля ещё `Column`, ответы — `Filling`, строки таблицы — `FillRow`. Чек-лист — это шаблон
с оцениваемыми полями, процедура — шаблон без оценки и с явным исходом (`Resolution`).

- **Типы полей** (`fillable/FieldType`): `scale`, `number`, `score`, `boolean`, `choice`,
  `text`, `longtext`, `date`, `photo`, `scan`, `objectref`, `table`. Короткий код типа —
  контракт с клиентом.
- **Значения** лежат свойствами над парой `(Filling, Field)`; у ячеек — над `(FillRow, Column)`.
  Поле адресуется стабильным `code` внутри шаблона, а не позицией.
- **Баллы.** Оценка — по желанию (`scoreable`). Каждая механика — отдельный модуль
  (`ScoreByNorm`, `ScoreByOption`, `ScoreByValue`, `ScoreByFlag`), подключённый в
  `maxScore(Field)` и `score(Filling, Field)`. Новая механика — новый модуль, а не правка
  ядра. Итог — процент; при весах разделов — взвешенное среднее по разделам.
- **Вердикт.** Проходной порог шаблона либо шкала оценок (`VerdictScale`); проваленное
  критичное поле делает проверку непройденной при любом проценте.
- **Несоответствие** — вариант с отметкой либо число вне нормы. По нему требуются фото и
  комментарий, если так настроено поле, и заводится корректирующая задача.
- **Итог фиксируется.** При завершении результат записывается снимком (`resultRecorded`),
  и дальнейшие правки шаблона, весов и справочников прошлое не меняют. У каждого узла
  расчёта две ветки: `live*` считает по текущим настройкам, публичное имя отдаёт записанное.
- **Редакции.** Менять состав шаблона с ответами нельзя (`TemplateGuard`): делается новая
  редакция — клон в том же семействе (`TemplateVersion`). Код шаблона — имя семейства;
  лукап по коду отдаёт опубликованную редакцию.
- **Предметы строк и ссылок** (`RefValue`) приходят по каналам: объект проверки, позиция
  справочника, сотрудник. Откуда берётся предмет, решает хост.

Проектные решения — `docs/mvp/fillable-tasks-design.md`, `fillable-rows-design.md`,
`filling-result-freeze-design.md`, `template-version-design.md`.

## 6. Кто что видит и может

Слоёв несколько, и они независимы — правка одного не заменяет другого:

| Слой | Где | Что решает |
|---|---|---|
| Участие | `participant(Task, User)` в `StoreTaskCore` | назначенный с учётом иерархии, автор, наблюдатель, принимающий |
| Видимость в бэк-офисе | `taskVisible` в `StoreTaskAccess` | администратор, право «видеть все», участник |
| Права роли | `StoreTaskAccess`, `GeoPolicy` | видеть все задачи, назначать, закрывать чужую, править шаблоны и настройки, видеть координаты, работать без геолокации |
| Переходы статуса | `StoreTaskWorkflow` | матрица «роль × тип × из статуса × в статус» |
| Гварды ручек API | `api/ApiCommon` | `canTouch` — назначенный, `canView` — ещё и принимающий, участник — для переписки и файлов |
| Геолокация | `GeoPolicy`, `Execution` | обязан ли исполнитель работать по координатам; признаки «не на объекте» |

Роль `admin` обходит все слои: `taskVisible` и матрица переходов для неё не действуют.
Проверять права под ней бессмысленно — регрессию не видно. Проверка ведётся под самой
узкой ролью, которой функция адресована.

## 7. Мобильный JSON API

Ручки — действия lsFusion с именем `api*`, вызываются как `/exec/StoreTask.<имя>`.
Конвенции собраны в одном месте — шапка `api/ApiCommon.lsf`; коротко:

- вход: клиент один раз меняет логин и пароль на токен (`Authentication.getAuthToken`),
  дальше ходит с `Authorization: Bearer`;
- чтение — параметры запроса и `EXPORT JSON`; запись — JSON в теле (один параметр `FILE`);
  читающая и пишущая ручки всегда разные действия;
- гвард доступа — первой строкой каждой ручки: сама аннотация ручки не ограничивает, кто зовёт;
- отказ чтения — код и тело `{"error", "message"}`: 401 `locked`, 403 `notPerformer` /
  `forbidden`, 404 `notFound`; мутация отказывает исключением;
- повтор запроса безопасен: у задачи, файла, комментария, снимка и строки есть ключ
  клиента, уникальность которого и есть идемпотентность.

| Группа | Модуль | Ручки |
|---|---|---|
| Задачи | `StoreTaskApi` | `apiCurrentUser`, `apiTasks`, `apiStatuses`, `apiSetStatus`, `apiCreateTask`, `apiTakeTask`, `apiReleaseTask`, `apiNearbyObjects` |
| Бланк, чтение | `FillReadApi`, `RowSubjectsApi` | `apiExecutionInfo`, `…Fields`, `…Options`, `…Columns`, `…Rows`, `apiRowSubjects` |
| Бланк, запись | `FillWriteApi` | `apiStartExecution`, `apiSetField`, `apiSetCell`, `apiAddRow`, `apiDeleteRow`, `apiSetFieldPhoto`, `apiDeleteFieldPhoto`, `apiSetResolution`, `apiFinishExecution` |
| Фотоотчёт | `SimpleApi` | `apiStartSimple`, `apiSimpleInfo`, `apiSetSimplePhoto`, `apiSetSimpleComment`, `apiFinishSimple` |
| Приёмка | `AcceptanceApi` | `apiAcceptTask`, `apiReturnTask` |
| Переписка и файлы | `TaskCommentApi`, `TaskFileApi`, `TaskWatcherApi` | лента комментариев, файлы задачи, подписка |
| Главная и создание | `HomeApi`, `QuickActionApi`, `BrandingApi` | блоки главной, объекты, пресеты, шаблоны, исполнители, оформление |
| Уведомления | `NotificationApi`, `DeviceApi` | лента, отметка прочтения, регистрация устройства |
| AI | `AiTaskApi`, `AiSearchApi` | черновик задачи по тексту и поиск для него |
| Внешние системы | `intake/TaskIntakeApi` | `apiTaskRequest` |

Ручка — общий код для телефона и для всех, кто его повторяет: изменение её ответа
проверяется на клиенте, а не только запросом.

## 8. Пакеты поверх ядра

Ядро — `StoreTaskCoreLib`. Остальные пакеты требуют его и не требуют друг друга; ядро не
требует ни одного. Хост берёт столько, сколько ему нужно.

| Пакет | Каталог | Что даёт |
|---|---|---|
| `StoreTaskMobileLib` | `home/`, `mobile/` | главная телефона по ролям, показатели, пресеты быстрого создания, оформление, раздача APK |
| `StoreTaskNotifyLib` | `notification/` | события, журнал, каналы доставки: пуш через FCM и почта |
| `StoreTaskAiLib` | `ai/` | постановка задачи текстом через `ai-service` |
| `StoreTaskIntakeLib` | `intake/` | приём заявок из внешних систем: правила, сопоставление площадок, карантин |
| `StoreTaskHypothesisLib` | `hypothesis/` | гипотезы о данных ERP и код их проверки |

**Уведомления** — три слоя, которые нельзя путать: событие (что произошло), уведомление
(запись, адресованная человеку, она же журнал) и доставка (попытка отправить наружу).
Наружу отправляет регламент в своей сессии, а не код рядом с событием.

**AI** не создаёт задачу. Сервер собирает контекст короткими списками, сервис возвращает
черновик, решение о сущностях принимает сервер (`AiDraftDecision`), задачу создаёт человек
обычной ручкой. Модель не видит базу и не получает SQL.

**Гипотезы.** Модель по исходникам пишет код проверки, человек его читает и утверждает,
дальше проверка идёт по расписанию и порождает задачи через приём заявок. Данные в модель
не уезжают.

**Фоновые задания** подсистема заводит себе сама при старте (`meta/StoreTaskRegulation`):

| Задание | Действие | Когда |
|---|---|---|
| «Пульс: задачи по графику» | `generateAll` | раз в сутки, 00:30 |
| «Пульс: очистка журналов» | `cleanLogs` | раз в сутки, 02:30 |
| «Пульс: уведомления по срокам» | `processNotifications` | раз в сутки, 07:00 |
| «Пульс: отправка уведомлений» | `processDeliveries` | каждые 15 секунд |
| «Пульс: гипотезы по расписанию» | `runDue` | каждые 15 минут |

Задание опознаётся по имени; существующее не пересоздаётся и не правится.

## 9. Сателлиты

**`ai-service/`** — FastAPI-сервис между сервером и языковой моделью. Говорит с моделью по
OpenAI-совместимому протоколу, поэтому движок заменяем; по умолчанию — небольшая локальная
модель. Ручки: `GET /health`, `POST /v1/task-draft`, `POST /v1/hypothesis-code`. Настройки —
переменные окружения, единственный их список — `.env.example`. Установка — `INSTALL.md`.

**`mobile/pulse_tasks/`** — Flutter-клиент, работающий без связи. Локальная база SQLite,
очереди отправки, синхронизация при появлении сети; форму бланка клиент рисует по схеме
из API, поэтому новый шаблон не требует пересборки. Слои: `lib/data` (клиент API,
локальная база, очереди, контроллеры), `lib/models`, `lib/ui`. Модульные тесты — `test/`,
сквозные — `integration_test/`.

Оба сателлита меняются только по своей задаче.

## 10. Точки расширения

Подсистема расширяется реализацией абстракций, а не правкой ядра. Основные:

| Точка | Объявлена в | Кто реализует |
|---|---|---|
| `TaskPerformer`: `id`, `name`, `archived`, `in`, `parent`, `performer(User)` | `meta/TaskPerformer` | хост |
| `CheckObject`: `name`, `parent`, адрес, координаты | `task/CheckObject` | хост или `CheckAsset` |
| `startExecution(Task)`, `executionKind(TaskType)` | `StoreTaskCore`, `Execution` | модуль типа задачи |
| `succeeded(Execution)`, `resultSummary(Execution)` | `Execution` | модуль вида выполнения |
| `onProceed(Task)` | `StoreTaskCore` | любой модуль и хост — реакция на закрытие |
| `participant(Task, User)`, `visibleTask(Task)` | `StoreTaskCore`, `StoreTaskAccess` | модули, добавляющие участников |
| `maxScore(Field)`, `score(Filling, Field)` | `fillable/Field`, `Filling` | механики `ScoreBy*` |
| `seedRequiredData()` | `StoreTaskSettings` | любой модуль со своими справочными данными |
| `copyTemplate`, `rebindTemplate` | `TemplateClone`, `TemplateVersion` | модули, хранящие настройки на шаблоне или ссылку на него |
| `send`, `suppressDelivery` | `notification/` | канал доставки |

## 11. Что легко сломать

- **Одиночный запуск.** Всё, что требует модулей ERP (`Activity`, `Assignee`, `Location`),
  живёт только в `erp/`. Попав в `StoreTaskLib`, такой модуль роняет старт standalone-хоста.
  Имена модулей уникальны на весь classpath — ERP-хост грузит и форки из `meta/`, и оригиналы.
- **Расслоение пакетов.** Ядро не требует ни одного пакета поверх себя. После правки
  графа `REQUIRE` — `scripts/tests/run-core-only-host.ps1`.
- **`REQUIRE` перечисляется явно**, с пояснением «зачем»; транзитивной зависимости не доверяют.
- **Сервер грузит `target/classes`, а не `src`.** Правка, не доехавшая туда, проверяется
  по старому коду и выглядит рабочей. Готовность правки `.lsf` — успешный старт сервера.
- **Схема данных.** Переименование или удаление класса, свойства `DATA`, таблицы требует
  записи миграции, иначе данные колонки теряются. Заводить её по умолчанию не нужно —
  сначала выяснить, есть ли рабочие данные.
- **Ложно только `NULL`.** Ноль истинен; `BOOLEAN` — это `TRUE` или `NULL`; сумма с нулевым
  результатом отдаёт `NULL`, и строка выпадает из фильтра. Там, где нужны три состояния,
  используется `TBOOLEAN` или маленький статический класс.
- **`ABSTRACT` без `CASE`** выбирает реализацию по классам параметров, а не по значению:
  две реализации на одной сигнатуре молча перекрывают друг друга. Складывать их по «или»
  умеет только `ABSTRACT CASE`.
- **`APPLY` в ручке** всегда идёт в паре с разбором отказа; `EXPORT` после `APPLY` в одном
  действии отдаёт пустое тело.
- **Строковые литералы** могут подменяться переводом из бандла. Технические коды и
  идентификаторы пишутся как `r'...'`, подписи — ключами `{storeTask.*}`.
- **Комментарии в коде — мотивировки.** В шапке модуля и у неочевидного свойства записано,
  почему сделано именно так и какая попытка сделать иначе уже провалилась. Их читают до правки.

## 12. Как проверяется

- **Старт сервера** — критерий компиляции; порядок запуска и маркеры в логе — AGENTS.md.
- **Серверные автотесты** — `scripts/tests/*_check.lsf`: текст отправляется на работающий
  стенд в `POST /eval/action`, ответ — JSON `ok` / `checks` / `failures`. Обёртки
  `run-*.ps1` возвращают код 0 или 1. Синтетические данные тестов носят префикс `ZZZ`.
- **Ручные сценарии приёмки** — `docs/mvp/test-scenarios.md`.
- **Клиент** — `flutter test` и `integration_test/` в `mobile/pulse_tasks`.
- **Сервис** — `pytest` в `ai-service/tests`; согласованность настроек — `scripts/tests/ai_env_check.py`.
- **Бандлы** — `scripts/check-bundle-keys.sh`: ключи кода против файлов подписей.
