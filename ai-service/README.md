# AI-сервис постановки задач

Тонкая прослойка между lsFusion и локальной языковой моделью. Принимает запрос сервера,
собирает prompt, зовёт модель, проверяет её ответ и возвращает плоский JSON.

```
Flutter ──► lsFusion ──► ai-service ──► LLM (локально)
```

Телефон к модели не ходит и её адреса не знает. Модель к базе не ходит и SQL не видит —
всё, что она знает о магазинах, людях и бланках, приезжает готовыми списками от lsFusion
(`storeTasks/ai/AiTools.lsf`).

## Запуск

**На сервере** — [INSTALL.md](INSTALL.md): `sudo ./install.sh` ставит ollama и сервис
службами systemd, без Docker. Там же — требования к машине, подключение к lsFusion,
проверка руками и разбор типичных отказов.

**Docker** — для разработки и там, где Docker уже используется:

```bash
cp .env.example .env          # при необходимости поправить модель и порты
docker compose up -d
docker compose logs -f llm    # первый запуск качает модель — это минуты
curl localhost:8010/health    # {"status":"ok","llm":"up","model":"..."}
```

В обоих случаях остаётся сказать lsFusion, где сервис, — INSTALL.md, раздел
«Подключение к lsFusion».

## Настройки и модель

Все настройки — переменные окружения, и единственный их список с пояснениями —
[`.env.example`](.env.example). Его читает `docker compose` (как `.env`), из него же
`install.sh` собирает `/etc/rtm-ai.env`, и те же имена с теми же значениями по умолчанию
знает `app/config.py`. Новая переменная появляется в этих двух файлах и больше нигде;
что они не разъехались, проверяет `scripts/tests/ai_env_check.py`.

Модель по умолчанию — qwen2.5 3B instruct в 4-битной квантизации: около 2 ГБ памяти,
CPU без GPU, сносно понимает русский и держит формат JSON. Варианты полегче и поточнее и
то, как модель сменить, — там же, в `.env.example` и в INSTALL.md. Ни lsFusion, ни телефон
о смене не узнают: адрес и контракт сервиса не меняются. Ради этого сервис и стоит между
ними, а не вызывается из lsFusion напрямую. Движок тоже не прибит гвоздями: сервис
говорит по OpenAI-совместимому `/v1/chat/completions`, на котором отвечают Ollama,
llama.cpp server, vLLM и LM Studio.

## API

### `GET /health`

```json
{"status": "ok", "llm": "up", "model": "qwen2.5:3b-instruct-q4_K_M", "detail": null}
```

`status` — про сервис, `llm` — про модель. Это разные вопросы: пока модель качается,
сервис уже отвечает, и администратору важно видеть, ждать ему или чинить.

### `POST /v1/task-draft`

Запрос — текст человека плюс контекст, собранный lsFusion:

```json
{
  "dialogId": "uuid", "step": 1,
  "text": "Поставь Иванову завтра до 18:00 проверить выкладку Pepsi в магазине на Ленина",
  "today": "2026-08-22", "author": "Сидоров",
  "atObjectId": "b31", "atObjectName": "Санта Уручье",
  "objects":    [{"id": "b24", "name": "Санта на Ленина", "address": "ул. Ленина, 15"}],
  "taskTypes":  [{"id": "issue", "name": "Поручение"}],
  "templates":  [{"code": "pepsi", "name": "Проверка выкладки Pepsi"}],
  "performers": [{"id": "ivanov", "name": "Сергей Иванов", "roles": "Заведующий"}],
  "priorities": [{"id": "high", "name": "Высокий"}],
  "history":    [{"step": 1, "text": "...", "question": "В каком магазине?"}]
}
```

Ответ — плоский, все поля необязательны:

```json
{
  "outcome": "ok",
  "taskName": "Проверить выкладку Pepsi",
  "objectId": "b24", "objectHint": "магазин на Ленина",
  "performerId": null, "performerHint": "Иванову",
  "typeId": "issue", "templateCode": null, "templateHint": null,
  "deadline": "2026-08-23", "photoRequired": true,
  "description": "Сфотографировать нарушения",
  "confidence": 0.9, "clarificationQuestion": null,
  "model": "qwen2.5:3b-instruct-q4_K_M", "llmMillis": 2400, "raw": "{...}"
}
```

Ключевое в контракте — **пары «id + подсказка»**. Модель называет `*Id`, если узнала
объект в присланном списке, и `*Hint` — если не узнала, но человек его назвал. Код,
которого не было в контексте, кодом не считается и уезжает подсказкой: маленькая модель
охотно выдумывает правдоподобный «b17», и пропусти мы его дальше — lsFusion нашёл бы по
нему чужой магазин.

Подсказку разрешает **lsFusion**, по всему справочнику и своими правилами: он же решает,
спросить ли человека, когда подходящих несколько. Сервис только проверяет.

Ошибки — это тоже HTTP 200:

```json
{"outcome": "error", "errorCode": "llmTimeout", "error": "модель не ответила за 60 с"}
```

Коды: `llmTimeout`, `llmUnavailable`, `llmBadResponse`, `badRequest`, `serviceError`.
5xx здесь означал бы поломку самого сервиса, а не молчание модели, — и телефону нужна
фраза для человека, а не код состояния.

## Чего сервис не делает

Не ходит в базу, не знает правил подсистемы задач (какой бланк к какому типу применим,
кому можно поручать, что делать с несколькими подходящими объектами) и ничего не
создаёт. Всё это — в lsFusion, там же, где остальные правила системы.

### Похожесть: где чья половина (решение 2026-09-03)

Похожесть строк считают обе стороны, и это не дублирование — вопросы разные:

| | вопрос | вход | ответ |
|---|---|---|---|
| сервис (`app/matching.py`) | кого из присланного показать модели | текст запроса + список от сервера | подмножество списка |
| сервер (`AiTools.matchHint`) | какой записи справочника отвечает подсказка модели | подсказка + весь каталог с правами | конкретный объект/человек/бланк или уточняющий вопрос |

Сервис ничего не решает: он видит текст рядом со списком и потому дёшево отбирает по
буквам, но выбор остаётся за сервером, которому видны права и полный каталог. Сервер, в
свою очередь, не ранжирует кандидатов — ему не с чем сравнивать, текста запроса рядом со
справочником у него нет.

Общее правило ровно одно — **«ё» и «е» считаются одной буквой** (`normalize` здесь,
`deyo` на сервере; выровнено 2026-09-03 по замеру опорных случаев).

Известное расхождение тоже одно: **склонение коротких слов**. Здесь префиксное правило
срабатывает с пяти символов, и «Артёма» находит «Артем»; на сервере «огрызок» не трогает
слова короче семи, и та же пара не совпадает. Пороги не выровнены сознательно — это
меняет щедрость подбора по всему каталогу и требует своего замера. Обе стороны это
проверяют и называют одинаково: `tests/test_matching.py` и
`scripts/tests/ai_draft_check.lsf` (секция O).

## Разработка

```bash
pip install -r requirements-dev.txt
pytest -q                    # модель не нужна: она подменяется в тестах
uvicorn app.main:app --reload --port 8010
```

Тесты проверяют контракт и разбор, а не качество модели: ответ настоящей LLM
недетерминирован, и тест на нём проверял бы погоду, а не код.

Без Docker и без установщика — так проверялась эта ветка на машине разработки, где
Docker не поднимался: `ollama serve`, `ollama pull` модели из `.env.example`, затем
экспортировать `LLM_BASE_URL` и `LLM_MODEL` с тамошними значениями и запустить uvicorn
как выше.
