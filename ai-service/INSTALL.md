# Установка AI-контура на сервер

Постановка задачи текстом опирается на две службы, которые ставятся рядом с сервером
приложений lsFusion:

> **Постановка задач текстом наружу ничего не отправляет**, пока `LLM_BASE_URL` указывает
> на локальный движок, — так его ставит установщик. `.env.example` допускает любой
> OpenAI-совместимый адрес; с внешним адресом фразы уходят туда. Модель, движок и сервис
> работают на машине заказчика. Черновик задачи (`/v1/task-draft`) собирает локальная
> модель: фразы сотрудников, фамилии, адреса магазинов и ответы модели не покидают сервер.
> Интернет нужен один раз — на установку, чтобы скачать ollama и веса модели; после этого
> постановка задач работает и без него.
>
> **Исключение — генерация кода проверки гипотез** (`/v1/hypothesis-code`, модуль
> «Гипотезы»). Её ведёт не локальная модель, а облачный агент `claude` (Anthropic), которого
> сервис запускает отдельной программой. Ни установщик, ни образ Docker этот CLI не ставят,
> и без него генерация кода не работает: пока MCP стенда не отвечает, запрос отказывает
> раньше — кодом `mcpUnavailable`, а при живом MCP — ошибкой «claude cli не найден». Если CLI
> на сервер поставить, текст гипотезы и прочитанные агентом исходники уходят в облачный
> сервис. Для полностью закрытого контура CLI на сервер не ставят.

```
веб-клиент ─┐
телефон ────┴► lsFusion ──► ai-service (8010) ──► ollama (11434) ──► модель
             владеет      собирает prompt,      движок             qwen2.5 3B,
             данными      разбирает ответ                          ~2 ГБ на диске
```

Ни телефон, ни браузер в модель не ходят и ходить не должны: единственный вход в AI — lsFusion.
Поэтому обе службы слушают только localhost, и открывать их наружу не нужно.

## Требования к машине

То же самое проверяет `./install.sh --check`, ничего не меняя на машине.

| | |
|---|---|
| ОС | Linux с systemd: Ubuntu 22.04+, Debian 12+, RHEL/Rocky 9+ |
| Память | от 4 ГБ свободных для модели по умолчанию (3B); для 7B — от 8 ГБ. На 2 ГБ — модель поменьше, см. `.env.example` |
| Процессор | от 4 ядер; GPU не нужен и не используется |
| Диск | ~3 ГБ для 3B (1,9 ГБ веса модели, остальное — движок и окружение python); для 7B — ещё 4,7 ГБ |
| Python | 3.9 или новее с модулем `venv` (в Ubuntu 20.04 системный — 3.8, не подойдёт) |
| Сеть | на время установки нужен интернет: качаются ollama и веса модели |

Ответ модели на такой машине занимает **20–30 секунд** — это нормально и заложено в
клиенте. Быстрее делают либо модель поменьше, либо GPU. Для ориентира, замер на
Intel i7-14700 без GPU: 3B — 11–14 с на фразу, 7B — 19–26 с; первый запрос после старта
дольше (20–50 с) — модель читается в память.

Первый запуск: скачивание весов 3B (1,9 ГБ) заняло 2,5 минуты, 7B (4,7 ГБ) — 6 минут;
время зависит только от канала.

## Установка

Сначала — проверить машину, ничего в ней не меняя:

```bash
cd ai-service
./install.sh --check
```

Проверка занимает секунду и говорит прямым текстом, чего не хватает: версии python,
модуля `venv`, памяти. Узнать это до того, как скачано два гигабайта весов, дешевле.

Дальше скопировать на сервер папку `ai-service` целиком и запустить:

```bash
cd ai-service
sudo ./install.sh
```

Установщик ставит ollama, качает модель, кладёт сервис в `/opt/rtm-ai`, собирает
`/etc/rtm-ai.env` из `.env.example` — с ключом доступа, который генерирует сам, — заводит
службу `rtm-ai` и проверяет себя: последним шагом он спрашивает `/health` и говорит, видит
ли сервис модель. Ключ он печатает в конце: его нужно ввести в lsFusion. Повторный запуск
безопасен — это же и способ обновить сервис после изменения кода; ключ при этом не меняется.

На входе установщик читает те же переменные, что описаны в `.env.example`, плюс одну свою:

```bash
# машина слабая — модель поменьше
sudo LLM_MODEL=qwen2.5:1.5b-instruct-q4_K_M ./install.sh

# lsFusion стоит на ДРУГОЙ машине — сервис должен слушать сеть, а не localhost
sudo AI_BIND=0.0.0.0 ./install.sh

# системный python старый, но рядом стоит новый — назвать его прямо
sudo PYTHON_BIN=/usr/bin/python3.11 ./install.sh
```

Во втором случае сервис требует ключ доступа (с сетевым адресом и без ключа служба не
стартует; установщик ключ генерирует сам), и порт всё равно стоит закрыть файрволом до
адреса сервера lsFusion:

```bash
sudo ufw allow from <ip-сервера-lsfusion> to any port 8010 proto tcp
```

## Подключение к lsFusion

В веб-клиенте: **Настройка → Настройки → AI**

| Поле | Значение |
|---|---|
| AI включён | да |
| Адрес AI-сервиса | `http://127.0.0.1:8010` (или адрес машины, если сервис на другой) |
| Ключ AI-сервиса | ключ из вывода установщика (он же в `/etc/rtm-ai.env`); пусто, если на сервисе ключ не задан |
| Таймаут, с | 90 |
| Задач в одной пачке, не больше | 50 (пусто или 0 — тоже 50) |

и нажать **«Проверить связь»** — она дёргает `/health` с ключом, записывает результат в
`aiLastError` и говорит прямо, если ключ не подходит или сервис его требует, а в настройке
пусто. То же самое скриптом:

```bash
curl -u 'admin:' -X POST --data-urlencode \
  "script=NEWSESSION { aiUrl() <- 'http://127.0.0.1:8010'; aiApiKey() <- '<ключ>'; aiEnabled() <- TRUE; APPLY; }" \
  http://localhost:7651/eval/action
```

Пункт «AI» в мобильном клиенте появляется только после того, как сервер ответил
«включён» (ручка `apiAiInfo`) — то есть после этого шага и очередной синхронизации.

### Веб-клиент и пачка задач

В веб-клиенте после включения AI появляются пункт навигатора **Операции → «Поставить
задачу текстом»** и одноимённая кнопка на списке задач. При выключенном AI их нет.

Фраза вида «Проверить ценники на кофе по всем магазинам Бреста» даёт не одну задачу, а
пачку: по одной задаче на каждый магазин, у которого в разрезе «Город» стоит «Брест».
Перед созданием форма показывает список попавших магазинов с ответственными; лишние
отмечаются «Выброшен из пачки»; задачи создаются одним нажатием «Создать» и одной
транзакцией. Пачка больше потолка («Задач в одной пачке, не больше») не создаётся вовсе —
форма называет число и просит сузить критерий.

Исполнитель задачи в пачке — ответственный по объекту: человек в активной роли на
объекте (Справочники → «Роли на объекте» и карточка объекта) с наименьшим порядком. Ответственного нет —
задача создаётся без исполнителя, в предпросмотре такой магазин помечен «Нет
ответственного». Каждому назначенному приходит обычное уведомление «назначена задача»:
пачка на 40 магазинов — это до 40 уведомлений.

**Право на массовое создание.** Собрать пачку может любой, у кого включён AI, а создать —
только роль с правом **«Массовое создание задач»** (Система → Доступ → Политика
безопасности, флажок у роли). На новой базе право ставится ролям «Супервайзер» и «Администратор»
само. **На уже работающей базе его нужно поставить руками** — иначе создание пачки
отказывает всем, кроме администраторов системы, со словами «Нет права на массовое создание
задач».

## Проверка руками

```bash
# 1. жив ли сервис и видит ли он модель
curl -s http://127.0.0.1:8010/health
# {"status":"ok","llm":"up","model":"qwen2.5:3b-instruct-q4_K_M"}

# 2. отвечает ли модель по существу (без контекста — просто что жива);
#    ключ — тот же, что введён в lsFusion, без него сервис отвечает 401
curl -s -X POST http://127.0.0.1:8010/v1/task-draft \
  -H "Authorization: Bearer $(sudo sed -n 's/^AI_API_KEY=//p' /etc/rtm-ai.env)" \
  -H 'Content-Type: application/json' \
  --data-binary '{"dialogId":"test","text":"Проверить ценники завтра"}'
```

Второй запрос вернёт черновик или уточняющий вопрос — оба ответа означают, что контур
собран. `"outcome":"error"` с кодом `llmUnavailable` означает, что жив только сервис;
`401` — ключ не передан или не тот.

## Эксплуатация

```bash
systemctl status rtm-ai            # состояние сервиса
systemctl restart rtm-ai           # после правки настроек
journalctl -u rtm-ai -f            # журнал сервиса
journalctl -u ollama -f            # журнал движка
```

**Настройки** — `/etc/rtm-ai.env`, собран установщиком из `.env.example`; смысл каждой
переменной — там. Установщик файл не перезаписывает, так что правки переживают
обновление. После правки нужен `systemctl restart rtm-ai`.

**Смена модели** — две строки. Порядок на работающем стенде: сначала скачать новую
модель (сервис всё это время отвечает на старой), потом переключить и перезапустить.
Перезапуск занимает секунды; запросы в эти секунды получают «Сервис AI не отвечает» и
проходят со второй попытки. Первый запрос после смены — на 10–30 секунд дольше: модель
читается в память.

```bash
sudo -u ollama OLLAMA_HOST=127.0.0.1:11434 ollama pull qwen2.5:7b-instruct-q4_K_M
sudo sed -i 's/^LLM_MODEL=.*/LLM_MODEL=qwen2.5:7b-instruct-q4_K_M/' /etc/rtm-ai.env
sudo systemctl restart rtm-ai
```

Ни lsFusion, ни телефон об этом не узнают: адрес и контракт сервиса не меняются. Ради
этого сервис и стоит между ними, а не lsFusion ходит в модель напрямую.

**Смена ключа** — тоже две строки, плюс тот же ключ в lsFusion («Ключ AI-сервиса»):

```bash
sudo sed -i 's/^AI_API_KEY=.*/AI_API_KEY=<новый ключ>/' /etc/rtm-ai.env
sudo systemctl restart rtm-ai
```

**Персональные данные.** В prompt уезжают фамилии исполнителей и адреса объектов; в
журнал сервиса они по умолчанию не пишутся (`LOG_PROMPT`, см. `.env.example`), включать —
только на время разбора инцидента. Ход генерации кода проверки гипотез сервис пишет файлами
и хранит ограниченный срок (`CODEGEN_LOG_DIR`, `CODEGEN_LOG_KEEP_DAYS`, там же); журнал
AI-запросов хранит lsFusion — срок задаётся в «Настройка → Настройки → AI».

## Если что-то не работает

| Что видно | Где смотреть | Обычная причина |
|---|---|---|
| в вебе нет пункта «Поставить задачу текстом» | Настройка → Настройки → AI | не включён «AI включён»; пункт появляется после повторного входа |
| в вебе «AI-постановка задач выключена в настройках системы» | Настройка → Настройки → AI | форму открыли по старой ссылке при выключенном AI |
| в вебе «Нет права на массовое создание задач» | Система → Доступ → Политика безопасности | у роли пользователя нет «Массовое создание задач» (на работающей базе ставится руками) |
| в вебе «По критерию … попало N объектов, потолок пачки — 50» | Настройка → Настройки → AI | критерий шире потолка: сузить фразу или поднять «Задач в одной пачке» |
| в вебе «В разрезе «Город» нет объектов со значением …» | справочник объектов, разрезы | значения нет в разрезах объектов или оно названо иначе |
| в вебе «Создавать задачи может только исполнитель системы задач» | карточка пользователя | пользователь не заведён исполнителем |
| в клиенте нет пункта «AI» | `curl -u 'admin:' 'http://localhost:7651/exec?action=StoreTask.apiAiInfo'` | не включён `aiEnabled` или телефон не синхронизировался |
| «Сервис AI не отвечает» | `systemctl status rtm-ai` | служба не поднялась; в журнале будет причина |
| «AI-сервис отклонил ключ доступа (HTTP 401)» | `sudo grep AI_API_KEY /etc/rtm-ai.env` | ключ в lsFusion не совпадает с ключом службы |
| служба не поднимается после обновления | `journalctl -u rtm-ai -n 20` | адрес не localhost, а ключа нет: задать `AI_API_KEY` в `/etc/rtm-ai.env` (повторный `install.sh` дописывает его сам) |
| `/health` отвечает `"llm":"down"` | `journalctl -u ollama -n 50` | модель ещё качается или движок не запущен |
| «Модель не успела ответить» | `nproc`, `free -m` | машина слабее ожидаемого: поднять `LLM_TIMEOUT` или взять модель поменьше |
| ответы приходят, но мимо | журнал AI-запросов в lsFusion | там виден ответ модели как есть — сразу понятно, ошиблась модель или разбор |
| `pip` не ставит зависимости | — | нет `venv`: `apt-get install -y python3-venv` |
| «нужен python 3.9 или новее» | `ls /usr/bin/python3*` | Ubuntu 20.04: `add-apt-repository -y ppa:deadsnakes/ppa && apt-get install -y python3.11 python3.11-venv`, дальше `PYTHON_BIN=/usr/bin/python3.11 sudo ./install.sh` |
| `install.sh: $'\r': command not found` | `file install.sh` | скрипт скопирован с Windows с CRLF: `sed -i 's/\r$//' install.sh` (в git он хранится с LF, см. `.gitattributes`) |

## Стенд на Windows (разработка и проверка)

Для проверки на машине разработчика без Linux и Docker — нативная Ollama и сервис из
исходников:

```powershell
winget install --id Ollama.Ollama -e
ollama pull qwen2.5:3b-instruct-q4_K_M
cd ai-service
py -3.12 -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
$env:LLM_BASE_URL = "http://127.0.0.1:11434/v1"
$env:LLM_MODEL = "qwen2.5:3b-instruct-q4_K_M"
.venv\Scripts\python -m uvicorn app.main:app --host 127.0.0.1 --port 8010
```

Python нужен 3.12: под 3.14 закреплённые версии пакетов не собираются. Дальше —
«Подключение к lsFusion» выше, адрес `http://127.0.0.1:8010`, ключ пустой.

## Снятие

```bash
sudo ./uninstall.sh          # снять сервис, ollama и веса оставить
sudo ./uninstall.sh --all    # снять всё
```

## Почему без Docker

Docker-вариант в проекте есть — [docker-compose.yml](docker-compose.yml), одна команда
`docker compose up -d`, — и он уместен там, где Docker уже используется под другое или
где важно переносить контур между машинами байт в байт.

Но на сервере, где lsFusion стоит нативно службами systemd, установка через Docker
означает: новый runtime, который надо обновлять и охранять; свой способ смотреть логи;
свой способ перезапускать; тома, о которых надо помнить при резервном копировании. Всё
это ради двух процессов, один из которых — готовый бинарник с официальным установщиком,
а второй — четыре питоновских пакета. Нативная установка даёт админу ровно те же
команды, которыми он уже управляет сервером приложений, и на одну технологию в контуре
меньше.
