# Установка AI-контура на сервер

Постановка задачи текстом опирается на две службы, которые ставятся рядом с сервером
приложений lsFusion:

```
телефон ──► lsFusion ──► ai-service (8010) ──► ollama (11434) ──► модель
             владеет      собирает prompt,      движок             qwen2.5 3B,
             данными      разбирает ответ                          ~2 ГБ на диске
```

Телефон в модель не ходит и ходить не должен: единственный вход в AI — ручка lsFusion.
Поэтому обе службы слушают только localhost, и открывать их наружу не нужно.

## Требования к машине

То же самое проверяет `./install.sh --check`, ничего не меняя на машине.

| | |
|---|---|
| ОС | Linux с systemd: Ubuntu 22.04+, Debian 12+, RHEL/Rocky 9+ |
| Память | от 4 ГБ свободных для модели по умолчанию (3B). На 2 ГБ — модель поменьше, см. `.env.example` |
| Процессор | от 4 ядер; GPU не нужен и не используется |
| Диск | ~3 ГБ: 2 ГБ веса модели, остальное — движок и окружение python |
| Python | 3.9 или новее с модулем `venv` (в Ubuntu 20.04 системный — 3.8, не подойдёт) |
| Сеть | на время установки нужен интернет: качаются ollama и веса модели |

Ответ модели на такой машине занимает **20–30 секунд** — это нормально и заложено в
клиенте. Быстрее делают либо модель поменьше, либо GPU.

## Установка

Сначала — проверить машину, ничего в ней не меняя:

```bash
cd ai-service
./install.sh --check
```

Проверка занимает секунду и говорит прямым текстом, чего не хватает: версии python,
модуля `venv`, памяти. Узнать это до того, как скачано два гигабайта весов, дешевле.

Дальше скопировать на сервер папку `ai-service` целиком и запустить:

```bash
cd ai-service
sudo ./install.sh
```

Установщик ставит ollama, качает модель, кладёт сервис в `/opt/rtm-ai`, собирает
`/etc/rtm-ai.env` из `.env.example`, заводит службу `rtm-ai` и проверяет себя: последним
шагом он спрашивает `/health` и говорит, видит ли сервис модель. Повторный запуск
безопасен — это же и способ обновить сервис после изменения кода.

На входе установщик читает те же переменные, что описаны в `.env.example`, плюс одну свою:

```bash
# машина слабая — модель поменьше
sudo LLM_MODEL=qwen2.5:1.5b-instruct-q4_K_M ./install.sh

# lsFusion стоит на ДРУГОЙ машине — сервис должен слушать сеть, а не localhost
sudo AI_BIND=0.0.0.0 ./install.sh

# системный python старый, но рядом стоит новый — назвать его прямо
sudo PYTHON_BIN=/usr/bin/python3.11 ./install.sh
```

Во втором случае порт обязательно закрыть файрволом до адреса сервера lsFusion —
сервис не спрашивает пароля, он рассчитан на закрытый контур:

```bash
sudo ufw allow from <ip-сервера-lsfusion> to any port 8010 proto tcp
```

## Подключение к lsFusion

В веб-клиенте: **Настройка → Настройки → AI**

| Поле | Значение |
|---|---|
| AI включён | да |
| Адрес AI-сервиса | `http://127.0.0.1:8010` (или адрес машины, если сервис на другой) |
| Таймаут, с | 90 |

и нажать **«Проверить связь»** — она дёргает `/health` и записывает результат в
`aiLastError`. То же самое скриптом:

```bash
curl -u 'admin:' -X POST --data-urlencode \
  "script=NEWSESSION { aiUrl() <- 'http://127.0.0.1:8010'; aiEnabled() <- TRUE; APPLY; }" \
  http://localhost:7651/eval/action
```

Пункт «AI» в мобильном клиенте появляется только после того, как сервер ответил
«включён» (ручка `apiAiInfo`) — то есть после этого шага и очередной синхронизации.

## Проверка руками

```bash
# 1. жив ли сервис и видит ли он модель
curl -s http://127.0.0.1:8010/health
# {"status":"ok","llm":"up","model":"qwen2.5:3b-instruct-q4_K_M"}

# 2. отвечает ли модель по существу (без контекста — просто что жива)
curl -s -X POST http://127.0.0.1:8010/v1/task-draft \
  -H 'Content-Type: application/json' \
  --data-binary '{"dialogId":"test","text":"Проверить ценники завтра"}'
```

Второй запрос вернёт черновик или уточняющий вопрос — оба ответа означают, что контур
собран. `"outcome":"error"` с кодом `llmUnavailable` означает, что жив только сервис.

## Эксплуатация

```bash
systemctl status rtm-ai            # состояние сервиса
systemctl restart rtm-ai           # после правки настроек
journalctl -u rtm-ai -f            # журнал сервиса
journalctl -u ollama -f            # журнал движка
```

**Настройки** — `/etc/rtm-ai.env`, собран установщиком из `.env.example`; смысл каждой
переменной — там. Установщик файл не перезаписывает, так что правки переживают
обновление. После правки нужен `systemctl restart rtm-ai`.

**Смена модели** — две строки:

```bash
sudo -u ollama OLLAMA_HOST=127.0.0.1:11434 ollama pull qwen2.5:7b-instruct-q4_K_M
sudo sed -i 's/^LLM_MODEL=.*/LLM_MODEL=qwen2.5:7b-instruct-q4_K_M/' /etc/rtm-ai.env
sudo systemctl restart rtm-ai
```

Ни lsFusion, ни телефон об этом не узнают: адрес и контракт сервиса не меняются. Ради
этого сервис и стоит между ними, а не lsFusion ходит в модель напрямую.

**Персональные данные.** В prompt уезжают фамилии исполнителей и адреса объектов; в
журнал сервиса они по умолчанию не пишутся (`LOG_PROMPT`, см. `.env.example`), включать —
только на время разбора инцидента.

## Если что-то не работает

| Что видно | Где смотреть | Обычная причина |
|---|---|---|
| в клиенте нет пункта «AI» | `curl -u 'admin:' 'http://localhost:7651/exec?action=StoreTask.apiAiInfo'` | не включён `aiEnabled` или телефон не синхронизировался |
| «Сервис AI не отвечает» | `systemctl status rtm-ai` | служба не поднялась; в журнале будет причина |
| `/health` отвечает `"llm":"down"` | `journalctl -u ollama -n 50` | модель ещё качается или движок не запущен |
| «Модель не успела ответить» | `nproc`, `free -m` | машина слабее ожидаемого: поднять `LLM_TIMEOUT` или взять модель поменьше |
| ответы приходят, но мимо | журнал AI-запросов в lsFusion | там виден ответ модели как есть — сразу понятно, ошиблась модель или разбор |
| `pip` не ставит зависимости | — | нет `venv`: `apt-get install -y python3-venv` |
| «нужен python 3.9 или новее» | `ls /usr/bin/python3*` | Ubuntu 20.04: `add-apt-repository -y ppa:deadsnakes/ppa && apt-get install -y python3.11 python3.11-venv`, дальше `PYTHON_BIN=/usr/bin/python3.11 sudo ./install.sh` |
| `install.sh: $'\r': command not found` | `file install.sh` | скрипт скопирован с Windows с CRLF: `sed -i 's/\r$//' install.sh` (в git он хранится с LF, см. `.gitattributes`) |

## Снятие

```bash
sudo ./uninstall.sh          # снять сервис, ollama и веса оставить
sudo ./uninstall.sh --all    # снять всё
```

## Почему без Docker

Docker-вариант в проекте есть — [docker-compose.yml](docker-compose.yml), одна команда
`docker compose up -d`, — и он уместен там, где Docker уже используется под другое или
где важно переносить контур между машинами байт в байт.

Но на сервере, где lsFusion стоит нативно службами systemd, установка через Docker
означает: новый runtime, который надо обновлять и охранять; свой способ смотреть логи;
свой способ перезапускать; тома, о которых надо помнить при резервном копировании. Всё
это ради двух процессов, один из которых — готовый бинарник с официальным установщиком,
а второй — четыре питоновских пакета. Нативная установка даёт админу ровно те же
команды, которыми он уже управляет сервером приложений, и на одну технологию в контуре
меньше.
