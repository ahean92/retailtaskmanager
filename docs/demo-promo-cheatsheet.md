Стенд: erp + подсистема задач «Пульс», база Санты (`santa_demo`), веб-клиент
**http://localhost:8080/7**, телефон — тот же сервер.
Дата подготовки: 13.10.2026. Данные — идемпотентные скрипты `scripts/demo/demo_promo_01…15`
(полный пересев: `bash scripts/demo/demo_promo_reseed.sh`; прогон одного:
`bash scripts/demo/mcp-eval.sh <скрипт>`). Каталог/остатки перенесены из бэкапа santa2:
2360 товаров, 2793 штрихкода, остатки документами «Изменение остатков» на торговые
отделы С-216/С-272 (магазины разведены ассортиментом и количествами).

План и механика — `docs/demo-scenarios-plan.md`.

## 2. Сценарий 1 — сроки годности → авто-задача на изъятие

**Дано**: шаблон `expiry-check` «Проверка сроков годности» (скан штрихкода / дата
«годен до» / количество). Демо-заполнения: `EXP-216` — у молока «РогачевЪ 1,7%» и
«Вкусное 1,5%» срок = сегодня (2 поз.), у «Молоко пастер 1,5%» +5 дней (мимо);
`EXP-272` — у двух позиций +2 дня (задачи НЕТ — встанет послезавтра сама), одна +5.
Гипотеза **`expired`** (версия 4, в расписании): последняя завершённая проверка
магазина → строки с «годен до» ≤ сегодня → находка с кодами позиций. Правило приёма
`hypothesis/expired` → задача «Изъятие просрочки» (шаблон с host-полем: остаток по
системе подставляется мостом, вводится только «Изъято» + фото).

**Ход**:
1. Веб (admin): *Гипотезы → «Просрочка на полке…»* — формулировка, код проверки
   (READ-файл `scripts/demo/data/promo_expired_check.lsf`), воронка последнего
   прогона (2 магазина с проверкой → 1 с просрочкой), находка 2216 → заявка → задача.
2. Телефон (zav216): задача **ST000385** «Изъятие просрочки — … С - 216 (2 поз.)» —
   начать → бланк со строками (остатки 12/6), изъять по факту, фото, завершить.
3. Живая проверка (пресет `demo_promo_15`): на главной телефона плитка
   **«Проверка сроков годности»** — zav216 сам заводит проверку (назначение
   «Себе», срок — сегодня, без приёмки) и сам сканирует полку; то, что найдёт,
   подхватит следующий прогон гипотезы.
4. Повторный прогон (eval `demo_promo_08_run.lsf` или регламент ≤15 мин) — второй
   задачи НЕТ (дедуп по «магазин#дата проверки»).
5. «Через 2 дня»: EXP-272 — показать, что задачи по +2 дня нет; формулировка объясняет,
   почему она появится послезавтра.

## 3. Сценарий 2 — весовые ±1 кг → пересчёт

**Дано**: остатки: С-216 — 10 весовых 0,35–0,95 кг; С-272 — 13 весовых 0,28–0,98
(другие коды); в обоих по 3 штучных с дробным остатком (2,5 / 0,5 / 1,5). Гипотеза
**`weigh-recount`** (в расписании): весовые (по «ВЕС» в имени группы) с остатком
0 < x ≤ 1 + штучные с дробным → находка на магазин.

**Ход**:
1. Веб (admin): гипотеза → воронка прогона: 2 магазина → 23 весовых → 6 дробных →
   2 находки (названия с числами: «Весовые ≤1 кг: 10, дробные штучные: 3 — С - 216»).
2. Задачи **ST000387** (С-216, 13 поз., zav216) и **ST000386** (С-272, 16 поз., zav272):
   составы НЕ пересекаются — показать списком.
3. Телефон (zav216): начать → строки с остатком по системе → взвесить, ввести факт →
   завершить.
4. Ручной вход: веб, форма «Товары» (ERP) → отметить позиции → «Создать задание на
   пересчёт» (штатные кнопки моста).
5. Повторный прогон в те же сутки (`demo_promo_11_weigh_run.lsf`) — дублей нет.

## 4. Сценарий 3 — чек-лист подготовки акции с приёмкой

**Дано**: шаблон `promo-prep` «Подготовка акции»: Да/Нет-оценки (товар в наличии ×2
веса, сроки в норме, **ценники заменены — критичный**, POS по макету), фото выкладки
обязательно, host-поле «Позиции акции» (остаток системы + «Выложено»). Задачи
**PROMO-216 / PROMO-272** «Чистота со скидкой» (мыло + паста, единый состав из
6 позиций): автор sup.demo, исполняют заведующие, приёмка включена на задаче.

**Ход**:
1. Веб (sup.demo): карточка PROMO-216 — состав задания на вкладке «Позиции»
   (с остатками), приёмка «Требуется».
2. Телефон (zav216): чек-лист — оценка пунктов, фото выкладки, количество по позициям,
   сдача → статус **«На приёмке»**.
3. Веб (sup.demo): приёмка — принять; показать возврат с причиной (статус «В работе»,
   признак «возвращена», повторная сдача) — на PROMO-272.
4. Лента/уведомления обеим сторонам.

## 6. Сценарий 5 — отзыв товара во всех активных магазинах

**Дано**: шаблон `product-recall` «Снятие товара с продажи»: host-поле позиций
(остаток по системе + «Снято, шт» — обязательное), фото обязательно. Задачи
**RECALL-2216 / RECALL-2272** «Отзыв товара: снять с продажи…»: автор sup.demo,
исполнители — заведующие (резолв по роли на объекте, как в пачке), приоритет
«Срочный», срок сутки, приёмки нет. Позиции — 2 SKU Safeguard из группы «Мыло
туалетное кусковое» с остатком в обоих магазинах («одна партия ездила по всей сети»).

**Ход**:
1. Живой путь (нужен рестарт стенда с мостом 2026-10-12): веб — **сначала** на форме
   «Магазины» отметить «Отм.» Уручье (С - 216, С - 272): в базе активна ВСЯ сеть
   santa2 (~280 магазинов), без отметок задачи уйдут всем, у большинства — без
   заведующего. Затем форма «Товары»: отметить 2 позиции мыла → кнопка
   **«Снять с продажи»** (группа «Задачи магазина») → подтвердить «в 2 магазинах» →
   откроется список задач.
2. Веб (sup.demo): в списке задач — задача отзыва у КАЖДОГО магазина; одна
   постановка = N задач, у каждой свой состав и свой остаток.
3. Телефон (zav216): начать → строки с остатком → ввести «Снято» → фото →
   завершить (без фото — отказ).
4. Данные для показа — сид `demo_promo_14_recall.lsf` (задачи RECALL-2216/2272);
   повторный прогон сида дублей не даёт. Кнопочные задачи получают обычные ST-номера.

## 7. Справка ведущему

- Отзыв товара: задачи `RECALL-*` раскладывает сид `demo_promo_14_recall.lsf`;
  «активный магазин» = магазин с назначенным заведующим (роль на объекте), исполнитель
  резолвится по той же роли — то же правило, по которому работает пачка по критериям.
- Регламент «ESB:Задачи — гипотезы по расписанию» гоняет назревшие гипотезы каждые 15 минут;
  для немедленного повтора — eval-скрипты `demo_promo_08_run.lsf` (expired) и
  `demo_promo_11_weigh_run.lsf` (weigh-recount): сбрасывают nextRun и зовут `runDue`.
- Гипотезы: обновление кода проверки — ТОЛЬКО новой версией (утверждённую править
  нельзя, констрейнт); на стенде рабочая версия expired — 4 (история 1–3: починки
  компиляции, хорошая история «генерация → ошибка → починка»).
- Приёмка: включена на ЗАДАЧЕ (`acceptancePolicy`), типы не тронуты. Если сдающий =
  принимающий, задача закрывается сразу без «На приёмке» — для демонстрации приёмки
  сдаёт не тот, кто принимает.
- Цены (`sysprice`) пустые — прайсы на стенде не заведены; остатки (`sysqty`) реальные
  из документов «Изменение остатков».
- Веб-клиент после рестарта сервера перезапустить (Tomcat держит старые RMI-заглушки).
