# Сценарии SaaS-версии: рабочий набор

Черновик (2026-10-11, из обсуждения SaaS-ветки). Рамка: lsFusion остаётся
headless-бэком (существующий JSON API), веб-морда надстраивается поверх API,
исполнительский контур — мобилка pulse_tasks. Модель изоляции: клиент —
доменная сущность, скоуп всех выборок — серверный (из сессии), физическая
компоновка (общая база или инстанс на клиента) — режим деплоя. Схемы
устройства — в [saas-architecture.md](saas-architecture.md).

Легенда статусов (относительно текущей кодовой базы):
- **[есть]** — работает сегодня в артефакте/мобилке;
- **[частично]** — механика есть, но с известными дырами или только для одного канала;
- **[новое]** — в SaaS-ветке надо строить с нуля;
- **[идея]** — концепт без реализации (черновики в docs/mvp, памяти).

## 0. Роли и каналы

| роль | кто это | основной канал |
|---|---|---|
| Директор/руководитель сети | ставит задачи, смотрит аналитику | веб (новый), частично мобилка |
| Админ тенанта | настраивает объекты, людей, шаблоны, план | веб (новый) |
| Исполнитель | сотрудник магазина, заполняет бланки | мобилка |
| Контролёр | принимает результаты, возвращает на доработку | мобилка + веб |
| Наблюдатель | смотрит задачу, комментирует без действий | мобилка/веб |
| Оператор SaaS (мы) | провижининг, обновления, поддержка | свои инструменты |

## А. Жизненный цикл тенанта — почти всё новое

**A1. Регистрация и триал** [новое]. Руководитель заходит на лендинг → создаёт
организацию (поддомен `company.pulse...`) → триал N дней → приглашает команду.
Провижининг тенанта в v1 ручной (оператор создаёт по заявке), self-service —
позже. Вход в мобилке: одно приложение, «введите код компании/поддомен».

**A2. Онбординг с примером данных** [новое, дёшево]. При создании тенанта
опционально сеется демо-контур: пара магазинов, 3–4 шаблона, задачи на неделю —
новичок видит живую картину до своей настройки. Генераторы `demo/` уже умеют
такое сеять, их надо превратить в «сид тенанта» (без удаляющих все задачи
скриптов, естественно).

**A3. План и лимиты** [новое]. Планы отличаются лимитами: пользователи, объекты,
задачи/мес, AI-вызовы, хранение фото. Метрики считаются на бэке. Оплата в v1 —
счёт вручную, платёжка после подтверждения спроса. Упор в лимит — мягкий:
предупреждение админу, а не блокировка исполнения задач.

**A4. Рост тенанта** [новое]. Сеть растёт 5 → 25 магазинов: админ добавляет
объекты и людей, план апгрейдится. Проверить на бенч-стенде rtmperf (20 тыс.
объектов), чтобы экономика инстанса не сюрпризила.

**A5. Экспорт данных** [новое, обязательное для B2B]. Админ выгружает шаблоны,
задачи, заполнения (CSV/XLSX), фото архивом, отчёты PDF. Без этого выезд
клиента = скандал.

**A6. Выезд/удаление** [новое]. Экспорт (A5) → удаление тенанта = контейнер +
база + поддомен. В модели «инстанс на тенанта» это дёшево и чисто — плюс
модели.

## Б. Настройка тенанта (админ, веб)

**B1. Каталог объектов** [новое поверх готового шва]. Справочник магазинов:
название, адрес, ответственный, регион/формат (для пачки и отчётов). Ядро уже
имеет host-шов `CheckObject` и generic `CheckAsset` — в SaaS-хосте это свой
справочник «Магазин» без какой-либо доработки ядра. Импорт списком (XLSX/CSV) —
желательно в v1, сети приходят с готовым перечнем.

**B2. Люди и права** [частично]. Приглашение по e-mail/ссылке, роли: админ,
руководитель, исполнитель, контролёр; область видимости — свои объекты/регион.
Пользователи сегодня — встроенные lsFusion-аккаунты (mycompany-форки в
standalone); приглашения, самостоятельная смена пароля, восстановление доступа —
новое. Права по объектам в erp-хосте решаются `responsibleData` — в SaaS-хосте
нужен свой аналог, механика ограничений в ядре уже есть.

**B3. Конструктор шаблонов** [есть, GWT]. Разделы/поля/колонки/механики баллов
`ScoreBy*`/печать — всё работает, но в платформенном веб-клиенте. Для SaaS:
v1 — оставить админам GWT-клиент (внутренний инструмент), v2 — веб-конструктор
в новом фронте. Это самый дорогой экран для переноса, не блокирует запуск.

**B4. Библиотека шаблонов** [новое]. Готовые чек-листы по вертикалям (стандарт
полки, утренний обход, санминимум, приёмка поставки…) — «поставить себе и
адаптировать». Наполняется нами из удачных клиентских шаблонов; технически —
сиды, продажи — контент-маркетинг.

## В. Постановка задач (руководитель)

**В1. Разовая задача вручную** [есть]. Выбрать шаблон, объект(ы), исполнителя,
срок, приоритет → создать. В вебе уже есть форма постановки.

**В2. Пачка по критериям** [есть, #36992]. Один шаблон × выборка объектов
(регион/формат/все) → N задач с разрезами. Готово, обкатано.

**В3. Задача из текста (AI)** [есть]. Вставить описание словами → ai-service
генерит черновик шаблона/задачи → правка → постановка. Дифференциатор продукта,
в SaaS — лимитируемый AI-вызов.

**В4. По графику** [есть]. Расписание → автогенерация (ежедневный обход,
еженедельный аудит). `schedule/`, включая разнос по исполнителям.

**В5. Из внешней системы** [частично]. Контур intake есть; для SaaS —
токенизированный публичный API + вебхуки позже (1С, Bitrix, ESB). Не v1.

## Г. Исполнение (сотрудник, мобилка) — ядро готово

**Г1. Новые задачи** [есть]. Push (FCM) о новой задаче/дедлайне, домашний экран
с дашбордами, фильтр «мои».

**Г2. Заполнение бланка** [есть]. Разделы-чипы, поля всех типов, таблицы,
скан штрихкода, фото, примечания; баллы считаются на лету; ответ не теряется
при навигации (недавний фикс).

**Г3. Офлайн** [частично]. Подвальное помещение без сети: заполнение офлайн,
финиш при появлении сети — работает для simple-форм, для fill-форм есть
известная дыра (очередь финиша с пустым телом) — чинится локально в мобилке.

**Г4. Гео- и фотофиксация** [есть]. Отметка позиции при выполнении, фото как
доказательство; освобождение от гео per-object (exemptFromGeo).

**Г5. Прошлая проверка** [есть]. «Глаз» в карточке — сравнение с прошлым
заполнением этого объекта.

**Г6. Комментарии и наблюдатели** [есть]. Обсуждение задачи, добавление
наблюдателя (просмотр + комментарии). Известная дыра: @упоминания не нотифицируют
— либо починить, либо не показывать собачку в SaaS-версии.

**Г7. Сдать на приёмку** [есть]. Отправка результата контролёру; статусная
машина, автозакрытие по гардам.

## Д. Приёмка и корректирующие — готово

**Д1. Приёмка** [есть]. Контролёр просматривает заполнение, принимает или
возвращает с замечанием; лента уведомлений с отметками прочтения.

**Д2. Корректирующие действия** [есть]. Из замечания — задача на исправление,
перепроверка, эскалация при повторе.

**Д3. Ознакомление с результатом** [есть, #37497]. Уведомить сотрудника/
руководителя о результате, флаг «ознакомлен» (доработка в локальной ветке,
ждёт коммита).

## Е. Контроль и аналитика (директор/руководитель, веб) — ядро веб-v1

**Е1. Дашборд директора** [частично]. % выполнения по сети, просрочки, горячие
точки. Экраны телефона есть (`home/`), веб-дашборда нет — первый экран нового
фронта.

**Е2. Список задач с разрезами** [есть в API]. Фильтры статус/объект/
исполнитель/тип, канбан-представление — данные все в JSON API.

**Е3. Просмотр заполнения** [есть]. Карточка с ответами, фото, баллами;
PDF-печать (jrxml). Основной экран контролёра в вебе.

**Е4. Отчёты** [есть]. Срезы по заполнениям, динамика score по шаблонам/
объектам/исполнителям (`report/`, `ScoreBy*`), экспорт.

**Е5. Лента уведомлений** [есть]. С «отметить все прочитанными» и чисткой
«вечных непрочитанных» (недавние фиксы).

## Ж. Автоматизмы и AI — дифференциаторы

**Ж1. Гипотезы** [есть]. Скан-цикл (сроки годности) → находка → заявка → задача
на изъятие; гипотезы по расписанию; дедуп находок. Обкатано на демо-стенде.
«Библиотека гипотез» = сиды формулировок без утверждения — черновик.

**Ж2. Сценарии из готовых операций** [идея]. Реестр операций (createTask,
notify, runReport, setStatus…) + сценарий шагами; текст пользователя → выбор
операций и параметров → превью → запуск. Средний этаж между пресетами и
гипотезами, черновик постановки не написан.

**Ж3. Сводка по расписанию** [идея]. AI-операция из MVP-ядра Ж2: еженедельная
выжимка по выполнению в мессенджер/почту.

**Ж4. Интеграции** [частично]. Мосты есть в erp-варианте (объект=Store,
исполнитель=Employee); для SaaS — токен-API, потом коннекторы.

## З. Наша сторона (оператор SaaS)

**З1. Провижининг тенанта** [новое]. Новый клиент → контейнер + база + поддомен
+ сид (A2). v1 — скрипт руками по заявке, v2 — кнопка.

**З2. Платформа и обновления** [новое]. Зафиксировать версию платформы
(SNAPSHOT недопустим), регламент обновлений с коротким окном, единый
протестированный артефакт на все тенанты.

**З3. Мониторинг** [новое]. Здоровье инстансов, лимиты/диски, алерты, логи,
Sentry мобилки. Бенч-стенд rtmperf — база для порогов.

**З4. Поддержка** [новое]. Вход оператора в тенант по приглашению клиента,
аудит действий оператора, канал фидбека из приложения.

## Сводка: где проходит граница «готово / строить»

- **Готово почти целиком**: исполнение (Г), приёмка и корректирующие (Д),
  постановка задач всеми способами (В), отчёты (Е3–Е5), гипотезы (Ж1).
  Это и есть продукт — SaaS его упаковывает, а не создаёт.
- **Строить в SaaS-ветке**: весь раздел А (тенант, планы, экспорт), З1–З3
  (эксплуатация), B1/B2 в вебе (каталог, люди — частично поверх готовых швов),
  веб-v1 из раздела Е (дашборд + списки) — на существующем API.
- **Отложить**: веб-конструктор шаблонов (B3 в GWT на переходный), платёжка,
  self-service signup, интеграции (В5/Ж4), Ж2/Ж3.
