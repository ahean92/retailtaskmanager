## 1. [Отчёты] Свод нарушений: пункт × объект × период — ЗАВЕДЕНО #36730

**Цель.** Балл говорит «плохо», свод нарушений — «что чинить». Сегодня несоответствие
видно только внутри одного заполнения: чтобы понять, что по сети третий месяц подряд
проваливается один и тот же пункт, надо открыть проверки по одной. Ради этого ответа
проверки и проводятся.

**Состав.**

- Отчёт «пункт шаблона × объект × период»: сколько проверок с несоответствием и **доля**
  от числа проверок, где пункт вообще заполнялся. Доля обязательна: пункт, проваленный
  трижды из трёх, важнее пункта, проваленного пять раз из ста, а по абсолютному числу
  второй всегда наверху.
- Разрезы и фильтры: шаблон, раздел, объект, период (месяц / квартал), проверяющий.
  Критичные несоответствия — отдельной величиной, они не равны обычным.
- Топ повторяющихся: упорядочивание по доле и по количеству, ограничение периодом.
- Переход из любой ячейки в конкретное заполнение. Отчёт без первичного документа
  заканчивается вопросом «а что там было на самом деле».
- Экспорт в XLSX.
- Считать **только по завершённым** заполнениям. Иначе брошенная на середине проверка,
  где до плохих пунктов не дошли, выглядит идеальной и разбавляет статистику.

**Готово когда.** По демо-набору видно, какие пункты чаще всего проваливаются по сети и
по конкретному объекту, с переходом в первичное заполнение; свод за месяц собирается без
ручной обработки.

**Универсально.** Несоответствие — свойство ядра `nonconformity` над (`Filling`, `Field`),
одинаковое для всех типов полей и всех механик начисления балла. Поэтому отчёт не знает
ни про один конкретный бланк и работает на любом шаблоне, включая процедурные без оценки.

**Зависит от.** Ничего. Фильтр по категории объекта добавится после #36708 одной строкой —
это не блокер, до тех пор фильтруем по объекту.

**Не путать с черновиком 6** бэк-офиса («свод результатов по объектам и периодам»): тот
про баллы, этот про пункты, общего кода нет. Разбор сводных файлов заказчика (черновик 0)
для этого тикета **не обязателен**: структура «пункт × объект × период» следует из модели,
а сверка с ручным файлом заказчика — отдельный проход.

**Подсказки.** `fillable/Filling.lsf:46` (`nonconformity(Filling, Field)`), `:74`
(`countCriticalFail`), `:69-72` (`totalScore`, `percent`); объект — `checkObject(task(e))`,
период — от `dateTime(e)` (`task/Execution.lsf:25`), раздел — `section(f)`; `critical(Field)`
в `fillable/Field.lsf`.

**Риск.** Состав колонок может не сойтись со сводом заказчика — тот файл ещё не разобран.
Принимаем продуктовую структуру; подгонка под конкретный файл — вёрстка, а не механика.

**Оценка.** M.

## 2. [UI] Рабочее место супервайзера — ЗАВЕДЕНО #36731

**Цель.** Веб-клиент сегодня — набор списков. Руководителю нужна сводка: просрочки,
сегодняшние проверки, средний балл по сети, худшие объекты, последние результаты. При
этом весь механизм настраиваемых показателей уже есть — он сделан для главной страницы
мобильного клиента, и заводить в вебе второй такой же значило бы вести два набора
показателей вручную.

**Состав.**

- Форма-дашборд на тех же `HomeBlock` / `HomeMetric`, что и мобильная главная: показатель
  настраивается один раз и виден в обоих клиентах. Веб добавляет своё отображение и
  переходы, а не свою модель.
- Клик по плитке открывает `FORM tasks` с соответствующим фильтром — переходы уже описаны
  данными (`HomeTaskFilter`: открытые / на сегодня / просроченные).
- Разрез по объекту: у блока есть флаг `byObject`, значения хранятся парой
  (`HomeMetric`, `CheckObject`). В вебе это таблица «объект × показатель» целиком, а не
  переключатель одного магазина, как на телефоне.
- Показатели супервайзера, которых нет у исполнителя (средний балл по сети за период,
  худшие объекты, открытые несоответствия, просрочки по исполнителям), добавляются
  **отдельным модулем-плагином** через `calcValue +=`. Ядро не трогается — это и есть
  проверка, что точка расширения настоящая.
- ⚠ Встроенные `myOpen` / `myOverdue` / `myToday` считаются по `currentUser()`. Для
  супервайзера нужен разрез «все» и «по исполнителю» — заводить **новые коды**
  показателей, а не переопределять существующие: одна и та же плитка не может значить
  «мои» на телефоне и «все» в вебе.
- Видимость по ролям берётся из `visible(HomeBlock)` — та же матрица `roleOn`, что и на
  телефоне, отдельного механизма прав здесь не заводится.

**Готово когда.** Показатель, настроенный один раз, виден и на телефоне, и в вебе; клик по
плитке открывает список задач с нужным фильтром; супервайзер видит просрочки, сегодняшние
проверки, средний балл и худшие объекты, не открывая ни одного списка вручную.

**Универсально.** Ни один показатель не зашит: набор блоков и плиток — данные, арифметика —
модуль-плагин, видимость — роли. Второму клиенту дашборд настраивается из интерфейса.

**Зависит от.** Ничего — главная страница уже в ветке `mvp_tasks`.

**Подсказки.** `mobile/HomeScreen.lsf`: `HomeBlock` (:88), `HomeMetric` (:124),
`calcValue` / `value` (:180-190), `taskFilter` (:135), `visible` (:118), форма настройки
`homeConfig` там же; `task/StoreTaskCore.lsf:183` (`FORM tasks` — цель переходов).

**Риск.** Плитки, шкалы и графики в вебе упираются в собственные компоненты. MVP делать
штатными средствами (гриды, `PROGRESS`, цвет из `color(HomeMetric)`); `CUSTOM` — отдельным
этапом, если понадобится.

**Оценка.** M.

## 3. [Печать] Механизм печатных форм по типам задач — ЗАВЕДЕНО #36732

**Цель.** Печати в проекте **нет вообще** — ни одного `PRINT`, ни одного `.jrxml`. При
этом акт проверки и есть то, что уходит ответственным и обсуждается. Делать печать
«формой на каждый случай» неправильно: у разных типов задач и разных клиентов разные
бланки, и каждый новый бланк означал бы правку `.lsf` и релиз. В MyCompany эта задача
решена механизмом шаблонов документов: шаблон загружается файлом из интерфейса и
привязывается к типу документа. Нужен тот же механизм у нас — с привязкой к типу задачи.

**Почему копия, а не зависимость.** Подключить `Utils.DocTemplate` из ERP нельзя: он
тянет `MasterData` и `Utils`, а модуль задач обязан собираться и в MITE, и standalone
(roadmap 30). Копировать чужой модуль **под тем же именем** тоже нельзя — при подключении
к ERP сервер падает с `module 'X' has already been added`. Значит: свой модуль, своё имя,
свой метакод, с оглядкой на эталон.

**Состав.**

- `CLASS PrintTemplate 'Печатная форма'` + метакод: название; файл шаблона, загружаемый
  из интерфейса (`DATA FILE`), либо путь к ресурсу в classpath для поставляемых с
  продуктом; формат вывода (PDF / DOCX / XLSX / RTF / HTML / сразу на принтер); имя файла
  выгрузки; действия «открыть», «загрузить», «сбросить».
- Матрица «печатная форма × тип задачи» — `in(PrintTemplate, TaskType)`, вкладкой и на
  форме печатной формы, и на форме типа задачи (`FORM taskType` с `tabbedPane` уже есть).
- Действие «Печать» в карточке задачи и в списке: один шаблон на тип — печатает без
  вопросов, несколько — диалог выбора, ни одного — кнопки нет.
- `FORM printTask` — источник данных отчёта: шапка (номер `ST000078`, название, объект,
  адрес, тип, приоритет, исполнитель, автор, сроки, статус), выполнения с результатом, а
  для заполнений — разделы, поля, ответы, примечания, фото, итог и вердикт. Именно она
  подставляется в шаблон.
- Подстановка шаблона — `REPORT OVERRIDE` на форме печати (файл из базы либо ресурс),
  вывод в выбранном формате.
- Раздел «Печатные формы» в настройках (`FORM options` уже есть).
- ⚠ **Именование.** Слово «шаблон» в проекте занято: `Template` — это БЛАНК заполнения
  (`fillable/Template.lsf`), и `template(Task)` означает бланк. Печатная форма обязана
  называться иначе (`PrintTemplate`, подпись «Печатная форма»), иначе через месяц никто не
  разберёт, что к чему привязано.

**Готово когда.** Пользователь загружает docx-шаблон из интерфейса, отмечает его для типа
задачи и печатает задачу из карточки; для типа с двумя шаблонами появляется выбор; новый
бланк не требует ни правки `.lsf`, ни пересборки.

**Универсально.** Метакод параметризуется объектом и его классификатором, а не зашивается
на `Task`: вторая ось — печатная форма по бланку заполнения, у разных чек-листов свой акт —
добавляется одним вызовом, без копирования механизма. Ни один шаблон не поставляется
кодом, все загружаются данными.

**Зависит от.** Ничего.

**Отношение к печатной форме акта** (черновик 5 бэк-офиса): этот тикет даёт **механизм** и
минимальный источник данных, тот — **вёрстку акта** по бланку заказчика, и ждёт #36708
(роли в шапку) и #36709 (подытоги разделов). Одним тикетом делать нельзя: механизм не
должен ждать чужих ролей. Заводить оба можно и нужно — но акт после механизма и с явной
оговоркой, что печатную форму он не изобретает заново.

**Подсказки.** Эталон — `utils/DocTemplate.lsf` в MyCompany: `@defineDocTemplate` (класс
шаблона, файл или ресурс, формат, имя выгрузки), `@defineDocTemplateType` (матрица с типом
документа), `@defineDocTemplateTypeForm` (выбор шаблона, `REPORT OVERRIDE`, сборка
`PRINT`-скрипта строкой и `EVAL ACTION`); применение — `sales/orders/print/SalesOrderPrint.lsf`
(`FORM printOrder` плюс три вызова метакода). У нас: `task/StoreTaskType.lsf` (`TaskType`,
`FORM taskType`), `task/StoreTaskCore.lsf:104` (`FORM task` — куда встаёт кнопка),
`StoreTaskSettings.lsf` (`FORM options`). Имя `.jrxml` обязано совпадать с каноническим
именем формы — иначе платформа молча уходит на автоматический дизайн; для загруженного
файлом шаблона это неважно, для поставляемого в ресурсах — критично.

**Риск.** В эталоне `PRINT`-скрипт собирается строкой и выполняется через `EVAL ACTION` —
так сделано потому, что формат выбирается в рантайме. При переносе проверить это на нашей
версии платформы и не потерять экранирование в имени файла выгрузки (в ERP там
`replace(number(o),'/','')`, у нас номер вида `ST000078` и чистить нечего).

**Оценка.** M.

## 4. [UI] Канбан задач в вебе — ЗАВЕДЕНО #36733

**Цель.** Список с фильтрами есть, картины «что где стоит» нет. Диспетчеру нужен поток
задач по статусам и перевод одним движением, без открытия карточки.

**Решение 2026-08-07: сразу собственный компонент (`CUSTOM`), без промежуточного варианта
на гридах.** Причина простая: число колонок — это данные (сколько статусов в справочнике,
столько колонок), а форма статична, и штатными средствами честной доски не выходит —
получается список с группировкой, то есть тот же список, который уже есть. Промежуточный
вариант пришлось бы выбросить целиком, а не доработать.

**Состав.**

- Доска рисуется собственным компонентом: `OBJECTS t = Task CUSTOM 'kanbanBoard'`, функция
  в `.js`-файле в ресурсах проекта, возвращающая `render` / `update` / `clear`. Отдельной
  формой — `FORM tasks` остаётся как есть, доска её не заменяет.
- **Колонки приезжают данными, а не зашиты в JS**: список статусов (код, название, порядок,
  `closed`) передаётся в компонент через `OPTIONS` — свойство класса `JSON`, собранное по
  справочнику `TaskStatus`. JS не знает ни одного кода статуса; добавленный в справочник
  статус даёт новую колонку без правки скрипта.
- Карточка: объект, исполнитель, срок, тип, тег; свойства берутся с формы обычным
  `PROPERTIES(t)`, значения и цвета — из `list` и `controller` (`getValue`,
  `getBackground` — `BACKGROUND rgbColorPriority` на форме задач уже есть). Просроченные
  подсвечены. Тему брать из `getColorThemeName()`, цвета в скрипте не хардкодить.
- Перетаскивание: карточка тянется мышью в другую колонку. ⚠ **Дроп не меняет статус
  напрямую.** Перевод обязан пройти `allow(TaskType, TaskStatus)` — набор статусов зависит
  от типа задачи, — и не спорить с автопростановкой «Выполнено» по выполнениям (#36473).
  Поэтому компонент сообщает намерение серверу: целевой статус пишется в свойство формы и
  тут же выполняется действие перевода на строке, одним запросом
  (`changeProperties([...], [...], [...])`). Вся валидация остаётся в логике; при отказе —
  сообщение, а карточка возвращается на место сама, потому что следующий `update` приходит
  с фактическим состоянием сервера.
- Перерисовка через `controller.diff(list, ...)`, а не «стереть и нарисовать заново»: на
  доске из сотни карточек полная перерисовка на каждое изменение заметно мигает.
- Фильтры (исполнитель, объект, тип, тег, «мои / все») — обычные фильтр-группы формы,
  компонент их не дублирует. Закрытые статусы (`closed`) по умолчанию скрыты — иначе доска
  зарастает выполненным за неделю.
- Размер выборки задать явно: у не-табличных видов читается 1000 объектов, `PAGESIZE 0`
  читает все. На доске нужен осознанный лимит плюс фильтр по умолчанию, иначе через год
  она открывается минуту.

**Готово когда.** Диспетчер перетаскивает карточку в другую колонку — статус меняется и
сохраняется; недопустимый по типу задачи перевод отклоняется с сообщением, а карточка
возвращается; добавленный в справочник статус появляется отдельной колонкой без правки
`.js`; фильтр по исполнителю и объекту работает; на демо-наборе доска открывается без
задержки.

**Универсально.** Колонки — справочник статусов, приезжающий в компонент параметром: у
второго клиента свой workflow из своих статусов, и ни `.lsf`, ни `.js` не правятся. Логика
разрешённых переводов остаётся на сервере, компонент — только отрисовка и жест.

**Зависит от.** Ничего. Новый модуль плюс свой `.js`; ядро только читается.

**Подсказки.** `task/StoreTaskCore.lsf:183` (`FORM tasks` — источник свойств карточки),
`task/StoreTaskStatus.lsf` (`sortingOrder`, `index`, `closed`),
`task/StoreTaskType.lsf:17` (`allow(TaskType, TaskStatus)`). По платформе: вид `CUSTOM` у
группы объектов, контракт `render(element, controller)` / `update(element, controller,
list, options)` / `clear`, методы контроллера (`isCurrent`, `changeObject`,
`changeProperty`, `changeProperties`, `getValue`, `getBackground`, `diff`,
`getColorThemeName`), `OPTIONS` с JSON — документация «How-to: Custom Components (objects)»;
без сборки достаточно обычного `.js` в веб-ресурсах.

**Риск.** Это фронтенд без типов и сборки: отлаживается в браузере, тестами не
закрывается, а контракт `render`/`update` — платформенный и может измениться при
обновлении. Плюс drag&drop мышью и на тач-экране — два разных набора событий; если доску
собираются открывать с планшета, это надо заложить сразу.

**Оценка.** L.

# Порядок работ

Порядка нет — в этом и был смысл отбора: четыре тикета берутся в любой
последовательности и любым числом исполнителей.
