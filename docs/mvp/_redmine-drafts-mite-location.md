## [MITE] Объектом проверки сделать точку размещения, а не прибор — ЗАВЕДЕНО #36775

**Цель.**

Объект проверки должен быть местом, куда человек приезжает, а не датчиком, который там
висит. Сейчас `StoreTaskMite.lsf:54` объявляет `EXTEND CLASS Device : CheckObject`, и из
этого выбора следуют три симптома одной причины.

В магазине «Соседи» в Уручье три прибора — 470301 (горка), 470302 (ларь), 470303
(витрина) — с одинаковыми координатами. `chosenObject` выбирает **один** объект по
тай-брейку и попадает в 470301; `apiTasks` фильтрует по нему, поэтому задача ST000031 на
470303, назначенная на `sosedi.qc`, из этой точки не видна вообще. Проверено: `opened` и
`assignedTo` у неё TRUE — дело только в гео-гейте. Тем же вызвано и второе: из этой точки
`apiNearbyObjects` возвращает три неразличимые записи «MITE-T2 (термогигрометр) №4703xx»,
и человеку не из чего выбирать. Третье — имя объекта в приложении это модель датчика,
хотя осмысленное имя рядом уже есть: `EquipmentUnit.euName` («Уручье · горка молочная»),
связанное с прибором через `euDevice`.

Ни один из трёх не чинится точечно. Объектов проверки на одной точке столько, сколько на
ней датчиков, а гео-гейт по построению выбирает один объект — с этим ничего нельзя
сделать, пока объектом остаётся прибор.

**Состав.**

- `EXTEND CLASS Location : CheckObject` вместо `Device`; реализовать `name` (название
  точки), `address` (адрес точки), координаты.
- **Бизнес-ключ для `StoreTask.id`.** У `Location` его нет. `MachineBot.machineNumber`
  («Код») не подходит: он уникален только внутри организации и предназначен машинам.
  Завести на `Location` собственный `code` с `GROUP AGGR` на глобальную уникальность —
  для розницы это естественно, у магазинов есть номера.
- **Координаты — «свои, иначе последнего отчитавшегося прибора».** Не просто
  `latitude(Location)`: у машин `MachineBot` собственных координат нет, они ездят по
  карте только потому, что объектом сейчас является прибор
  (`Location.lsf:93` — `latitude(Device d) = OVERRIDE latitude(lastMeasurement(d)),
  latitude(location(d))`). Сузив до собственных координат точки, мы остановим машины.
- `device 'Прибор' = DATA Device (Task)` в `StoreTaskMite` — задача продолжает указывать
  на конкретное оборудование. Правило «инцидент → задача» (`WHEN SET(ManagerLog l)`,
  `StoreTaskMite.lsf:187`) ставит `checkObject(t) <- location(incidentDevice(...))`, а
  сам прибор кладёт в новое свойство.
- Имя автозадачи собирать с названием единицы оборудования: «Авария: отклонение
  температуры — Притыцкого · ларь заморозки» вместо голого имени шаблона.
- Перевести на `Location` фильтры прав и `CONSTRAINT`, написанные сейчас через
  `checkObject(t) AS Device` / `organization(o AS Device)` (`StoreTaskMite.lsf:77-89`).
- **Решить: отсекать ли точки с флагом `machine`** (машины бота) из объектов проверки.
  По умолчанию после переделки они тоже станут объектами.
- `SosediDemo.lsf`: проставить магазинам `code`, задачи заводить на точки, прибор класть
  в новое свойство.

**Готово когда.**

Из точки в Уручье приложение показывает один объект «Соседи, Уручье» и все задачи этого
магазина, включая ST000031 на витрине. `apiNearbyObjects` возвращает магазины, а не
датчики. В названии задачи и в карточке видно, о какой единице оборудования речь. Машины
`MachineBot` по-прежнему двигаются по карте.

**Обязательно учесть.**

1. **Миграция — до, а не после.** Перевести `checkObject` существующих задач с прибора на
   его точку нужно ДО того, как `Device` перестанет быть `CheckObject`: иначе ссылки
   обнулятся. На стенде 16 задач. Перед прогоном — `pg_dump -Fc lsfusion` (предыдущий
   дамп: `/root/lsfusion-pre-update-20260811.dump`).
2. **Контракт с мобильным приложением.** `objectId` в `apiTasks` и `apiNearbyObjects`
   меняет смысл: был серийник прибора, станет код магазина. Клиент
   (`D:\dev\lsf\retailtaskmanager\mobile\pulse_tasks`) обновляется синхронно, иначе
   сохранённый на устройстве выбор объекта перестанет находиться.
3. **`GeoLog.checkObject`** переедет сам, но журнал координат после переделки стоит
   открыть и посмотреть — он и есть инструмент разбора таких инцидентов.
4. **`APPLY` без проверки — молчаливая потеря.** В сиде и в любом коде, пишущем данные
   через Action API, каждый `APPLY` обязан проверять `canceled()` и падать через
   `throwException`. Иначе отказ по ограничению откатывает сессию, а вызывающий получает
   HTTP 200 и считает, что всё записалось. На этом уже теряли время.
5. **Обратный перевод включён** (`logics.lsfStrLiteralsLanguage = ru`): технические
   литералы — коды, id, имена endpoint'ов — писать как `r'...'`, иначе они участвуют в
   переводе и могут подмениться.

**Зависит от.** Ничего в MITE. Смежное — см. ниже, но оно не блокирует.

**Подсказки.**

`mite_public/src/main/lsfusion/StoreTaskMite.lsf:54-72` — сам мост, все пять реализаций;
`:77-89` — фильтры прав и `CONSTRAINT` через `AS Device`; `:187-209` — правило
«инцидент → задача». `Location.lsf:5` — `CLASS Location : POI`, то есть адрес и
координаты у точки уже есть по линии POI; `:93-94` — то самое `OVERRIDE
latitude(lastMeasurement(d)), latitude(location(d))`, которое надо перенести на точку.
`Agro.lsf` — `EquipmentUnit`, `euName`, `euDevice`.

Со стороны артефакта: `retailtaskmanager/src/main/lsfusion/storeTasks/task/CheckObject.lsf`
— `id`, `checkObject(id)`, `nearbyDistance`, `nearestObject`, `chosenObject`;
`api/StoreTaskApi.lsf:82` — `apiTasks` и то, как `chosenObject` попадает в `WHERE`.
Артефакт при этом **не правится**: он специально ничего не знает о том, что у хоста
является объектом проверки.

**Риск.**

Смысл `objectId` меняется у уже работающего API. Если приложение обновится позже сервера,
человек на точке получит пустой список — тот же симптом, что чиним, но по другой причине.
Порядок выкладки должен быть оговорён до начала.

**Оценка.** M.

## Смежное: явный `objectId` не срабатывает — это дефект артефакта, не MITE

На стенде `apiTasks` с явным `objectId=470303` не отдаёт задачу, хотя она открыта,
назначена на вызывающего, а объект в радиусе (расстояние 0 м). То есть выбор объекта
руками не работает и сам по себе, независимо от того, прибор там или точка.

Это **не** в `mite_public`: и разбор параметра, и `chosenObject` живут в артефакте.
Заводить надо отдельным тикетом на retailtaskmanager, иначе он утонет внутри переделки
моста и достанется не тому исполнителю.

Что проверять в первую очередь:

- `checkObject(ISTRING[30] c) = GROUP MAX CheckObject o IF id(o) = c` — совпадает ли
  строка. На MITE `StoreTask.id(Device d) += ISTRING[30](STRING(Device.id(d)))`, то есть
  число через `STRING`; лишний пробел или иной регистр здесь и дают тихий NULL.
- Доезжает ли параметр вообще. `lat` и `lon` доезжают — это видно по журналу координат;
  в том же журнале пишется и `requestedObject`, поэтому ответ на вопрос «сервер получил
  470303 или пусто» уже лежит в базе, смотреть надо там, а не в клиенте.
- Первая ветка `chosenObject`: `checkObject(id) IF nearbyDistance(checkObject(id), lat, lon)`.
  Если `checkObject(id)` пуст, ветка молча уступает место `nearestObject`, и снаружи это
  неотличимо от «объект вне радиуса» — то есть ровно то поведение, которое наблюдается.

После этого станет понятно, часть ли это той же проблемы или отдельная.
