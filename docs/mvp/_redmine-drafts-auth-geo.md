## Что изменилось после разбора авторизации (2026-08-05)

Первая редакция черновика исходила из того, что авторизация у нас — HTTP Basic на
каждом запросе, и своей ручки входа не будет. Проверка документации платформы это
опровергла: **токенная авторизация в lsFusion уже есть**.

- `Authentication.getAuthToken[]` вызывается с Basic-заголовком и возвращает JWT с
  фиксированным сроком жизни (по умолчанию сутки, параметр `authTokenExpiration`).
  Суточный срок оставляем как есть — решено 2026-08-05, параметр серверный и влияет
  на всех.
- Дальше все запросы идут с `Authorization: Bearer <token>`.

То есть настоящую аутентификацию писать не нужно — ею надо воспользоваться. Пароль
перестаёт улетать на сервер при каждом запросе, а украденное устройство теряет доступ
вместе с протухшим токеном.

Оттуда же выяснились две вещи, которые в первой редакции были сформулированы слишком мягко:

- Приём внешних запросов регулируется параметром **`enableAPI`**: `0` — только действия
  с `@@api` и только аутентифицированным (значение по умолчанию), `1` — любые действия
  любому аутентифицированному, `2` — **разрешены анонимные**. В официальном how-to по
  фронтенду `enableAPI=2` прямо предлагается как быстрый способ; если так сделали на
  каком-то из наших стендов, авторизация там выключена целиком. **Отдельным тикетом
  сейчас не заводим** (решено 2026-08-05: это вопрос стендов, а не разработки) —
  проверка перенесена в инфраструктурный тикет, к боевой установке.
- `@@api` пускает **любого** аутентифицированного пользователя без разбора. Ограничение
  по конкретному человеку делается только проверкой `currentUser()` **внутри** действия.
  Поэтому фильтрация `apiTasks` — не улучшение, а обязательный элемент защиты.

Ручка профиля при этом остаётся, но окончательно перестаёт быть про авторизацию и
получает честное имя `apiCurrentUser`. Разделение ролей чистое:
`Authentication.getAuthToken` — платформенная аутентификация, `apiCurrentUser` —
прикладной профиль и настройки.

## Точки стыка сервера и клиента

Зафиксировать в первый же день, дальше стороны почти не мешают друг другу:
1. формат ответа `apiCurrentUser` (исполнитель + `geoRequired`);
2. новые поля в `apiTasks` (`objectId`, координаты объекта, `distance`);
3. формат ответа `apiNearbyObjects` (объекты в радиусе с расстоянием до каждого).

Если одиннадцать тикетов покажется дробно — схлопываются в три эпика (сервер / клиент /
инфраструктура) с теми же подпунктами внутри, как сделано с 30 и 31.

# СЕРВЕР — lsFusion

## [Авторизация] `apiCurrentUser` — профиль исполнителя и флаг `geoRequired` по роли

**Цель.** Сегодня сервер не умеет ответить на вопрос «а кто ко мне пришёл». Мобильному
приложению это нужно как воздух: без этого нельзя ни показать человеку, под кем он
работает, ни понять, чьи данные хранить на устройстве, ни решить, требовать ли
геолокацию.

**Состав.**
- Новое `@@api`-действие `apiCurrentUser` в `api/StoreTaskApi.lsf`: возвращает логин
  пользователя, имя и `id` исполнителя. Аутентификацию оно не выполняет — к моменту
  вызова платформа уже опознала пользователя по Bearer-токену.
- Если у вошедшего нет `TaskPerformer` (учётку завели, с человеком не связали) — не
  отдавать пустоту молча, а бросать понятное исключение. Приложение покажет «учётная
  запись не является исполнителем», и никто не будет полдня гадать, почему список пуст.
- Признак `geoRequired` в том же ответе — обязательна ли геопривязка для этого
  пользователя. Значение берётся из настройки по роли (см. ниже): решение принимает
  сервер, клиент его только исполняет.
- Настройка «разрешить работу без геолокации» на `UserRole`: свойство плюс место на
  форме ролей. Нужна на случай морозильной камеры и подвала, где фикса просто не будет, —
  без неё первый такой случай станет инцидентом в поле.

**Готово когда.** Запрос с Bearer-токеном возвращает данные этого человека и корректный
`geoRequired`; у учётки без исполнителя — внятная ошибка, а не пустой ответ; переключение
настройки у роли меняет ответ.

**Зависит от.** —. Блокирует экран входа в клиенте.

**Подсказки.** `currentPerformer()` — `meta/TaskPerformer.lsf:29`. Работа с ролями уже
есть рядом: `has(currentUser(), UserRole r)` в `mobile/StoreTaskArm.lsf:24` — там
настройки АРМ разложены по ролям, тот же приём. Клиентский `_decodeList` терпим и к
объекту, и к массиву из одного объекта — формат ответа некритичен.

## [Задачи] `apiTasks` — фильтрация по назначенному исполнителю

**Цель.** `apiTasks` сегодня отдаёт вообще все открытые задачи — кто бы ни спросил.
Приложение потом отфильтровывает лишнее у себя, по «ID исполнителя», который
пользователь вбивает руками. То есть чужие задачи не просто остаются в кэше после
перелогина — они с самого начала лежат на устройстве, и любой аутентифицированный
пользователь может их выкачать: `@@api` сам по себе никого не различает.

**Состав.**
- Добавить в `WHERE` условие «задача назначена на вошедшего пользователя». Предикат для
  этого уже написан и материализован — тот самый, что стоит в фильтре «Назначенные мне»
  на десктопной форме.
- Эндпоинт при этом **не параметризовать**: фильтр берётся из сессии. В шапке модуля не
  зря написано, что на 7.0-сервере параметризованный экспорт умеет возвращать пустое
  тело; ручку специально оставили без параметров, ломать это не надо.
- Тем же проходом проверить остальные ручки `api/` — `apiStatuses` отдаёт справочник и
  безобиден, а вот `FillApi` адресуется по `id` задачи и сейчас не проверяет, имеет ли
  вызывающий к этой задаче отношение. Если проверка нужна, вынести отдельным тикетом,
  но зафиксировать вывод здесь.
- Заодно закрепить в комментарии к модулю `api/`, что `@@api` **не** ограничивает, какой
  именно пользователь вызывает действие: ограничение делается только проверкой
  `currentUser()` внутри. Это ловушка, на которую легко наступить при добавлении
  следующей ручки, и стоит она одной строки комментария.

**Готово когда.** Под учёткой A в ответе нет ни одной задачи, назначенной на B.
Проверяется запросом, а не глазами в приложении. По `FillApi` есть письменный вывод —
нужна доработка или нет.

**Зависит от.** —.

**Подсказки.** `assignedTo(Task, User)` — `task/StoreTaskCore.lsf:48`, тот же предикат в
`FILTERGROUP my` там же ниже.

## [Справочники] `CheckObject` — координаты объекта проверки

**Цель.** У `CheckObject` сегодня есть только название и адрес — оба абстрактные, чтобы
хост сам решал, откуда их брать. Координат нет вообще, а без них «ближайший объект»
считать не из чего.

**Состав.**
- Широта и долгота на `CheckObject` тем же швом, что имя и адрес: абстрактные свойства
  в ядре, реализации — в хостах.
- Для `CheckAsset` (приборы, холодильники) — либо собственные `DATA`-свойства, либо
  наследование от места размещения, ровно по образцу того, как там уже сделан адрес.
- Для ERP — реализация в мосте `CheckObjectLocation`.
- Пункт, который легко забыть: объект без координат для мобильного приложения станет
  невидимым. Поэтому на форму `checkObjects` — колонки координат и фильтр «без
  координат», чтобы администратор видел дыры до того, как исполнитель приедет в магазин
  и не найдёт там задач. Жёсткий `CONSTRAINT` не ставить — он положит существующие данные.

**Готово когда.** У объектов можно заполнить координаты; на форме видно, у кого их нет;
сервер стартует на чистой БД.

**Зависит от.** —. Можно делать параллельно с авторизацией.

**Открытый вопрос (закрыть до старта).** Есть ли у `Location` в mycompany готовые
координаты, или их придётся заводить в мосте. Это правка в репозитории ERP — может
оказаться отдельной историей с чужим владельцем данных, и это главный риск по срокам
во всём блоке.

**Подсказки.** Образец шва — `fillable/CheckAsset.lsf:18` (`addressAsset`), образец
моста — `erp/CheckObjectLocation.lsf:11`. Класс — `task/CheckObject.lsf`.

## [Геолокация] `apiNearbyObjects` — расчёт расстояния и `objectId`/`distance` в `apiTasks`

**Цель.** Приложение присылает координаты — сервер отвечает, какие объекты рядом и какой
ближе всех, и отдаёт задачи только по выбранному.

**Состав.**
- **Первым делом — не код, а пятнадцатиминутная проверка:** отдаёт ли параметризованный
  экспорт с числовыми параметрами непустое тело на нашем 7.0-сервере. От ответа зависит
  вся конструкция. Если да — фильтруем на сервере, это правильнее: лишние данные не
  покидают контур. Если нет (прецедент со строковыми параметрами уже был, из-за него
  `apiTasks` и сделали беспараметрической) — сервер отдаёт объекты с координатами,
  ближайший считает клиент, фильтрация идёт по `objectId`. Оба варианта рабочие, второй
  чуть хуже по приватности и лучше по офлайну.
- Расчёт расстояния — гаверсинус через `FORMULA` на стороне PostgreSQL.
- Ручка `apiNearbyObjects` (имя рабочее): не только ближайший, а **список объектов в
  радиусе, отсортированный по расстоянию** — приложению это нужно, чтобы дать выбор,
  когда рядом больше одного объекта (два магазина в одном ТЦ автоматика различает плохо).
  Первый в списке — выбор по умолчанию.
- Новые поля в `apiTasks`: `objectId`, координаты объекта, `distance`. `objectId` нужен
  в любом случае — сейчас в ответе только название объекта, по нему фильтровать нельзя.

**Готово когда.** По паре координат сервер стабильно определяет ближайший объект и
отдаёт задачи только по нему; когда рядом несколько объектов, в ответе видны все,
по возрастанию расстояния.

**Зависит от.** координаты `CheckObject`.

**Подсказки.** Идиома «объект с минимальным значением» уже применена —
`GROUP LAST … ORDER DESC …` в `api/FillApi.lsf:17`. Перед тем как писать свои
гео-свойства, стоит посмотреть, что уже есть в платформенном модуле `Geo`: он же даёт
представление `MAP` для групп объектов, и форма `checkObjects` получит карту почти
бесплатно.

**Оценка.** M.

# МОБИЛЬНОЕ ПРИЛОЖЕНИЕ — Flutter

## [Авторизация] Экран входа: `getAuthToken`, настройки подключения отдельно, вход без сети

**Цель.** Сегодня приложение открывается формой «Подключение» с адресом, логином,
паролем и ID исполнителя. Это экран для наладчика, а не для человека, который пришёл
на смену. Плюс пароль сейчас уходит на сервер при каждом запросе — платформа даёт
токены, надо ими воспользоваться.

**Состав.**
- Разделить на два экрана. Первым идёт **вход**: логин, пароль, «Войти». Адрес сервера
  уезжает в **настройки подключения** — туда ведёт шестерёнка с экрана входа, и заходят
  туда один раз при развёртывании.
- Вход — два шага: `Authentication.getAuthToken` с Basic-заголовком отдаёт JWT, затем
  `apiCurrentUser` с `Authorization: Bearer <token>` отдаёт профиль. Дальше **все**
  запросы идут с Bearer; Basic остаётся только в первом шаге.
- Перевыпуск токена: срок жизни сутки, поэтому на 401 клиент молча перевыпускает токен
  из сохранённых учётных данных и повторяет запрос один раз. Пользователь этого не
  замечает и пароль заново не вводит. Повторный 401 после перевыпуска — это уже
  «пароль сменили на сервере»: сбрасываем сессию и просим войти заново.
- Разбор ошибок входа: 401 → «Неверный логин или пароль», таймаут → «Сервер недоступен»,
  профиль без исполнителя → «Нет доступа к задачам». Три разные причины — три разных
  сообщения, а не одно «Ошибка: …».
- **Вход без сети** (решено 2026-08-05): если сервер недоступен, пускать по совпадению
  введённого пароля с локально сохранённым хэшем, при условии что последнее успешное
  обращение к серверу было **не более суток назад**. Отсчёт именно от последнего
  контакта, а не от последнего входа: иначе человек, вошедший в понедельник и всю неделю
  работавший онлайн, окажется заперт на ровном месте. Иначе первый же магазин без связи
  останавливает работу, а приложение задумано офлайн-первым.
  Сетевые операции в таком режиме ждут восстановления связи и перевыпуска токена.
- Окно офлайн-входа намеренно совпадает с сроком жизни токена — обе величины сутки,
  поэтому отдельного состояния «токен уже протух, а войти ещё можно» не возникает.
  Если человек не выходил на связь больше суток, вход требует сети.
- Поле «ID исполнителя» удалить совсем — вместе с клиентским фильтром по нему: после
  фильтрации `apiTasks` сервер сам отдаёт что нужно.
- Логин и ФИО вошедшего — в шапку списка. Сейчас человек вообще не видит, под кем работает.
- При следующих запусках экран входа не показывать, если сессия сохранена.

**Готово когда.** Первый запуск ведёт по маршруту «настроить адрес → войти»; неверный
пароль внутрь не пускает; после протухания токена приложение продолжает работать без
повторного ввода пароля; в самолётном режиме вход проходит, если последний контакт с
сервером был меньше суток назад, и не проходит, если больше.

**Зависит от.** `apiCurrentUser`, фильтрация `apiTasks`.

**Подсказки.** Текущий экран — `lib/ui/settings_screen.dart`; `isConfigured` (сейчас это
просто «адрес не пуст») — `lib/data/settings.dart:20`; выбор стартового экрана —
`lib/main.dart:36`; сборка заголовка авторизации — `lib/data/api_client.dart:31`;
клиентский фильтр по исполнителю, который удаляется, — `lib/data/task_repository.dart:92`.
Форму URL для `getAuthToken` проверить на месте: в документации пример через
`?action=getAuthToken`, наш клиент строит путь `/exec/<Namespace>.<action>`.

## [Авторизация] Хранение токена и учётных данных в `flutter_secure_storage`

**Цель.** Пароль сейчас лежит в `shared_preferences` открытым текстом — это прямо
признано комментарием в коде как временное решение MVP. Пора закрыть, тем более что
хранить теперь надо три разные вещи с разными сроками жизни.

**Состав.**
- В `flutter_secure_storage` (Keychain и Keystore) уезжают: **токен** (живёт сутки,
  перевыпускается автоматически), **учётные данные** (нужны для перевыпуска) и **хэш
  пароля с солью** (нужен для офлайн-входа). Адрес сервера не секрет, пусть остаётся
  где был.
- Хэш — с солью и медленной функцией (PBKDF2/Argon2), не «просто sha256».
- Миграция при обновлении поверх старой версии: старое значение из `shared_preferences`
  перенести и затереть, иначе оно останется лежать в бэкапе устройства.
- **Токен переживает перезапуск приложения** (решено 2026-08-05): перевыпускать его на
  каждом старте значило бы требовать сеть просто чтобы открыть приложение, а оно
  офлайн-первое. Риск закрыт с другой стороны: токен лежит в защищённом хранилище,
  сам умирает через сутки и стирается при выходе из аккаунта.
- Рядом с токеном хранить отметку времени последнего успешного обращения к серверу —
  по ней экран входа решает, пускать ли без сети.

**Готово когда.** Пароль не читается ни из `shared_preferences`, ни из бэкапа приложения;
обновление поверх старой версии не требует повторного ввода пароля.

**Зависит от.** —. Можно делать параллельно с серверной веткой, ни от чего не зависит.

**Подсказки.** `lib/data/settings.dart` (комментарий про MVP — в шапке файла);
`lib/data/api_client.dart` — там же живёт сборка заголовка.

**Оценка.** S.

«пользователь». Перелогинился — видишь чужой кэш, чужие фото и чужую очередь
неотправленных изменений.

**Состав.**

  `WHERE` — и утечка вернулась. Схема при этом не меняется вообще, изоляция получается
  по построению.
- Ключ — адрес сервера плюс логин: один и тот же человек на тестовом и на боевом
  сервере должен видеть разные данные.
- Фото — в подкаталог с тем же ключом.
- Побочный эффект, который нужно учесть: база сейчас создаётся один раз при старте
  процесса и живёт в репозитории до конца. Придётся научиться переоткрывать её при
  входе и закрывать при выходе.
- **Миграция существующей установки.** Старую базу нельзя просто снести: в ней может
  лежать неотправленная очередь. Её создал единственный пользователь устройства,
  поэтому при первом успешном входе после обновления она просто становится базой
  этого пользователя.
- Очередь отправляется только под своим владельцем — при смене пользователя чужие
  записи физически недоступны, что и требуется.

**Готово когда.** Вход A → его задачи; выход, вход B → ни одной задачи A; возврат в A →
его неотправленная очередь на месте и уходит на сервер под его же учёткой. Обновление
поверх старой версии не теряет неотправленные изменения.

**Зависит от.** экран входа (без установленной личности нет ключа).

**Подсказки.** Все девять таблиц и точки входа — `lib/data/local_db.dart`; открытие базы
— там же, строка 22. `replaceTasks`/`replaceStatuses` чистят таблицу целиком — при
пофайловом варианте их трогать не нужно. Версия схемы (`version: 5`, `_onUpgrade`)
остаётся общей для всех файлов.

**Оценка.** M.

## [Авторизация] Выход из аккаунта: сброс сессии, переоткрытие `LocalDb`, очистка кэшей

**Цель.** Кнопки «Выйти» сегодня нет — она появляется только вместе с входом.

**Состав.**
- Выход стирает токен и возвращает на экран входа.
- Обычный выход данные **не** трогает: человек мог закончить смену в подвале без связи,
  и его очередь должна дождаться сети.
- Отдельным пунктом — «Выйти и удалить данные», с честным предупреждением, сколько
  изменений останутся неотправленными.
- При выходе сбрасывать открытые экраны и кэши заполнения, иначе следующий пользователь
  увидит чужую форму.

**Готово когда.** Выход возвращает на экран входа, ничего чужого на экране не остаётся;
удаление данных удаляет данные ровно этого пользователя.

**Зависит от.** изоляция `LocalDb`.

**Подсказки.** Кэш заполнения — `lib/data/fill_controller.dart`; состояние списка —
`lib/data/task_repository.dart`.

## [Геолокация] Гейт геолокации в сценарии входа (`geolocator`)

**Цель.** По требованию: без доступа к местоположению приложение не пускает внутрь.

**Состав.**
- Разрешение запрашивается сразу после успешного входа; координаты получаются с
  таймаутом.
- **Послабление (решено 2026-08-05):** принимать последнюю известную позицию, если она
  не старше нескольких минут, и уважать серверный признак `geoRequired` из
  `apiCurrentUser` — для ролей, которым геопривязка не обязательна, гейт не включается.
  Без этого работа в морозильной камере или подвале становится невозможной.
- Все четыре способа не получить координаты — разрешение не дано, отозвано навсегда,
  службы геолокации выключены, фикс не пришёл — ведут на один понятный экран с
  объяснением и двумя кнопками: «Повторить» и «Открыть настройки». Внутрь он не пускает.
- Манифесты: разрешения на Android и строка с объяснением на iOS — без неё приложение
  просто падает при первом запросе.

**Готово когда.** При отказе в разрешении в приложение попасть нельзя; при выданном —
координаты получены и сохранены в сессии; для роли с выключенным требованием вход
проходит без геолокации.

**Зависит от.** экран входа, `apiCurrentUser` (признак `geoRequired`).

**Подсказки.** Пакет `geolocator` (он же даёт `openAppSettings()` и
`getLastKnownPosition()`).

**Оценка.** M.

## [Задачи] Фильтр списка по ближайшему объекту и выбор при нескольких рядом

**Цель.** Человек должен видеть, где он, по мнению приложения, находится — и почему
видит именно эти задачи.

**Состав.**
- В шапке списка: название объекта, расстояние до него и кнопка «Обновить

- **Выбор объекта, когда рядом больше одного** (решено 2026-08-05): если

# ИНФРАСТРУКТУРА

## [Инфраструктура] HTTPS для веб-клиента и HTTP API

**Цель.** В подсказке экрана подключения стоит `http://192.168.1.10:9080`. По открытому
HTTP Bearer-токен перехватывается ровно так же, как Basic-пароль, — просто протухает
через сутки. Пока нет TLS, вся работа по авторизации выше даёт половину эффекта.

**Состав.**
- TLS на веб-клиенте (сертификат Let's Encrypt, редирект HTTP → HTTPS).
- Проверить, что мобильный клиент ходит по `https://` и не отключает проверку
  сертификата «чтобы заработало».
- Решить, что делать со стендами в локальной сети без внешнего имени: самоподписанный
  сертификат с пином в приложении или доступ только через VPN.
- Тем же проходом зафиксировать `enableAPI=0` на всех стендах: при этом значении (оно же
  по умолчанию) принимаются только действия с `@@api` и только от аутентифицированного
  пользователя. При `enableAPI=1` любому аутентифицированному становятся доступны
  `/eval` и `/eval/action` — выполнение произвольного кода; при `2` разрешены анонимные
  запросы, и вся работа по правам выше обесценивается. Заодно убедиться, что ни на одной
  ручке не стоит `@@noauth` — эта аннотация обходит и аутентификацию, и сам `enableAPI`.

**Готово когда.** Приложение работает по `https://`, `http://` редиректится, проверка
сертификата не отключена; на каждом стенде зафиксировано `enableAPI=0`, `@@noauth` в
проекте не встречается.

**Зависит от.** —. Не блокирует разработку, но должно быть готово до боевой установки.

**Исполнитель.** Не Буймистров — инфраструктурная задача, назначить отдельно.

**Подсказки.** Готовый рецепт (certbot, редирект, systemd-юниты) есть в скилле деплоя
lsFusion.

**Оценка.** M.

# Порядок работ

Первыми — **`apiCurrentUser`** и **фильтрация `apiTasks`**: обе небольшие, ничего не
ломают и разблокируют всю мобильную ветку. Параллельно можно брать **хранилище учётных
данных** — оно ни от чего не зависит.

Затем две колонны идут параллельно: сервер берётся за **координаты `CheckObject` →
`apiNearbyObjects`**, клиент за **экран входа → изоляция `LocalDb` → выход из аккаунта →
гейт геолокации**. Сходятся на **фильтре списка по ближайшему объекту** — его делать
последним, он собирает всё вместе.

**HTTPS** идёт своим темпом и своим исполнителем, но должен успеть к боевой установке.

Итого примерно полторы-две недели по прикладной части, если стороны не ждут друг друга.
Главный риск по срокам — не код, а открытый вопрос по координатам `CheckObject`:
заполнение координат по реальным магазинам в ERP может оказаться отдельной историей с
чужим владельцем данных.
