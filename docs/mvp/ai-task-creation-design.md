# Постановка задачи текстом (AI) — дизайн и реализация

> Заведующий идёт по залу, видит бардак на витрине и хочет поставить задачу, не заполняя
> форму из десяти полей: «поставь Иванову завтра до 18:00 проверить выкладку Pepsi в
> магазине на Ленина и сфотографировать нарушения».
> Первый AI-сценарий системы. Статус: сценарий целиком в `master` (влит 2026-09-08),
> хвост первого этапа закрыт 2026-09-09 — см. §10.

## 1. Что сделано

Сквозной сценарий целиком:

```
Flutter ──► lsFusion ──► AI-сервис ──► локальная LLM в Docker
   ▲            │
   └── черновик ┘         подтверждает человек, создаёт обычная apiCreateTask
```

1. В меню «+» мобильного клиента появился пункт **AI**.
2. Человек описывает задачу словами.
3. lsFusion собирает контекст (объекты, типы, бланки, исполнители) и зовёт AI-сервис.
4. Сервис строит prompt и обращается к локальной модели.
5. Ответ модели проверяется, подсказки разрешаются в сущности системы.
6. Телефон показывает распознанную задачу; человек правит, подтверждает или переспрашивает.
7. Задача создаётся **обычной ручкой `apiCreateTask`** — тем же механизмом, что и по пресету.

## 2. Три решения, на которых держится всё остальное

### 2.1. lsFusion — единственная точка входа, модель ничего не решает

Телефон не знает адреса модели. Модель не видит базу и не получает SQL. Между ними —
сервер задач, который собирает контекст и разбирает ответ.

Иначе не получится ни ограничить доступ (кто какие магазины видит), ни объяснить, почему
AI выбрал не того человека, ни сменить модель без выпуска APK.

### 2.2. Правила подсистемы — в lsFusion, работа с языком — в сервисе

Граница проведена по одному признаку: **знание о предметной области против знания о тексте**.

| lsFusion | AI-сервис |
|---|---|
| кто может быть исполнителем на объекте | prompt и его размер |
| бланк применим только к бланочному типу | разбор «до пятницы» → дата |
| «подходит несколько магазинов» → вопрос человеку | отсев кандидатов по буквам |
| поиск по всему справочнику (18750 сотрудников) | проверка, что код из ответа вообще существовал в контексте |
| журнал запросов и персональные данные в нём | таймаут и недоступность модели |

Требование «AI service не должен содержать бизнес-логику RetailTaskManager» выполняется
буквально: сервис можно выбросить и написать заново на другом языке, не тронув ни одного
правила системы.

### 2.3. Черновик — не задача, и подтверждение — не отдельная ручка

AI отвечает **черновиком**. Человек его правит и подтверждает, после чего телефон создаёт
задачу той же ручкой и той же очередью, что и создание по пресету, — с `clientId`, равным
ключу разговора.

Отсюда следствие, которое сильно упростило серверную часть: **ручки «подтвердить черновик»
нет и не будет**. Второй путь создания задачи пришлось бы держать в согласии с первым.
Связь «из какого разговора выросла задача» и без него есть — по общему ключу:

```lsf
task (AiRequest r) = taskByClientId(dialogId(r));
```

## 3. Серверная часть: `storeTasks/ai/`

| Модуль | Отвечает за |
|---|---|
| `AiSettings` | адрес сервиса, ключ доступа к нему, таймаут, потолок контекста, кнопка «Проверить связь» |
| `AiTools` | пять инструментов AI: чем модель узнаёт о данных системы |
| `AiRequest` | журнал запросов: что спросили, что уехало, что ответила модель |
| `AiServiceClient` | клиент сервиса: контекст → вызов → разбор ответа по локалям |
| `AiDraftDecision` | **решение**: подсказки → сущности, правила подсистемы, уточняющий вопрос |
| `AiTaskDraft` | сценарий целиком: порядок шагов и журнал |
| `AiTaskApi` | две ручки для телефона |

### 3.1. Инструменты (`AiTools`)

Пять операций из требований, у каждой две стороны: свойства — для сборки контекста и
разбора ответа, ручки `@@api` — те же данные наружу, для отладки.

```
searchObjects           apiAiSearchObjects?query=Ленина
searchTaskTypes         apiAiSearchTaskTypes
searchTemplates         apiAiSearchTemplates?query=выкладка
searchPerformers        apiAiSearchPerformers?query=Иванову
getAvailablePerformers  apiAiAvailablePerformers?objectId=b24
```

**Отбор кандидатов, а не выгрузка справочника.** Каталог Санты — 365 магазинов и 18750
сотрудников; в контекст компактной модели он не влезает, а влезь — утопил бы в себе сам
запрос. Кандидаты отбираются тремя дешёвыми признаками: объект рядом с телефоном, назван
в тексте, на нём есть роль у автора запроса.

**«Огрызок» подсказки.** Модель возвращает «Иванову» и «на Ленина», в справочнике лежит
«Иванов Сергей» и «Санта на Ленина». Полноценная морфология не окупается: у русского
слова меняется хвост, а начало — нет, поэтому ищем по первым буквам, отбросив два
последних символа у слов длиннее шести. Плата — лишние совпадения («Иваненко» на
«Иванову»), и она осознанная: лишний кандидат превращается в вопрос «кого из двоих», а
пропущенный — в «человек не найден», после которого разговор начинается заново.

### 3.2. Решение (`AiDraftDecision`)

Порядок попыток для каждого поля один и тот же: **код из контекста → подсказка по всему
справочнику → умолчание → вопрос человеку**.

| Поле | Умолчание | Когда спрашиваем |
|---|---|---|
| объект | назван в тексте → он; иначе тот, на котором стоит телефон | назван, но не найден или подходит несколько |
| исполнитель | себе (как в `apiCreateTask`) | назван, но не найден или найдено несколько |
| тип | «поручение», а с бланком — «процедура» | никогда: тип всегда выводится |
| бланк | без бланка | никогда: бланк необязателен |
| срок | без срока | никогда |

Правила подсистемы применяются **после** модели, а не вместо неё: бланк на небланочном
типе отбрасывается с замечанием, срок в прошлом снимается, задача без названия получает
названием сам запрос. Модель можно попросить соблюдать правила, но полагаться на просьбу
нельзя — иначе черновик, нарушающий констрейнт, обернулся бы отказом `APPLY` уже после
того, как человек нажал «Создать».

Уточняющий вопрос **один** — первый недостающий. Список из трёх вопросов на экране
телефона — это форма, а от формы человек и уходил в AI.

### 3.3. Журнал (`AiRequest`)

Пишется на каждый запрос, включая неудачный: исходный текст, объект телефона, исход,
разобранные ссылки, ответ модели как есть, модель, время работы модели и всего запроса,
ошибки разбора. Открывается из **Настройка → Журнал AI-запросов**.

Переданный в модель контекст (фамилии, адреса) хранится **только при включённой настройке
«Хранить переданный контекст в журнале»** — тот минимум персональных данных, о котором
говорит требование. Включается на время разбора инцидента.

Сама запись хранится ограниченный срок (#37347): «Хранить журнал AI-запросов, дней» на той
же вкладке настроек, пусто — 30 дней. Старше срока удаляет регламент «Пульс: очистка
журналов» — раз в сутки и при старте сервера, пачками; созданная из запроса задача при этом
остаётся.

Журнал — не только для разбора: `task(AiRequest)` показывает, какая задача выросла из
запроса, а `outcome` — сколько запросов дошло до задачи, сколько потребовало уточнения и
сколько провалилось.

## 4. AI-сервис (`ai-service/`)

FastAPI, четыре сотни строк, ни одного обращения к базе. Подробности запуска и настройки —
в [`ai-service/README.md`](../../ai-service/README.md).

Что он делает сверх «позвать модель»:

- **отсев кандидатов по буквам** (`matching.py`) — из присланных сервером кандидатов
  оставляет самых похожих на текст запроса: сервер отбирает по делу, сервис — по буквам,
  и только он видит текст рядом со списком;
- **проверка ответа** (`postprocess.py`) — код, которого не было в контексте, кодом не
  считается; дата приводится к `YYYY-MM-DD`, в том числе из «завтра» и «до пятницы», если
  модель не справилась сама;
- **разбор кривого JSON** (`llm.py`) — маленькая модель нет-нет да и обернёт ответ в
  ```` ```json ````; выбрасывать из-за этого разобранный запрос жалко.

Модель — `qwen2.5:3b-instruct` в 4-битной квантизации: ~2 ГБ памяти, CPU, сносный русский,
держит формат JSON. Меняется переменной окружения.

## 5. Мобильный клиент

Экран `ui/ai_task_screen.dart` — **лента разговора в одном окне**. Фраза человека стоит
справа, ответ AI слева, собранная задача — карточкой последним сообщением.

- **Первая фраза** уходит из того же поля внизу, из которого потом идут ответы и правки:
  сервер каждый шаг разбирает вместе со всей историей разговора, поэтому разделять ввод,
  ответ и правку на клиенте нечем.
- **Уточнение** остаётся в ленте вместе с ответом на него. Это и есть причина ленты:
  вопрос бывает не один (один за шаг, см. 3.2), и в трёх экранах заданный вопрос исчезал,
  стоило на него ответить, — человек терял, о чём его спрашивали.
- **Варианты** к вопросу — кнопками под ним, и только у последней реплики: отвеченный
  вопрос переспрашивать нечем. Выбор встаёт в ленту как ответ человека и применяется на
  месте, без второго захода в модель.
- **Карточка задачи** правится прямо в ленте: название, тип, объект, исполнитель, срок,
  фото, описание, и «Создать задачу». Она всегда одна и всегда показывает текущий
  черновик — пришло новое уточнение, карточка уходит вместе с ним.
- **Тип** правится плашкой, и список для неё считает сервер (`typeOption`, приезжает с
  черновиком): он отфильтрован тем же правилом подсистемы, каким сервер разбирает ответ
  модели, — бланк живёт только на бланочном типе. Есть бланк — предлагаются бланочные,
  нет — небланочные; заменить нечем — плашка не нажимается. Списка типов на телефоне при
  этом по-прежнему нет: экран AI онлайновый, и список, положенный в кэш при
  синхронизации, разошёлся бы с правилами, по которым собран сам черновик.
- **Правка словами** работает так же, как всё остальное: «перенеси на пятницу» — это шаг
  того же разговора, и в ответ приходит обновлённая карточка.

Пункт «AI» появляется, только когда сервер сказал, что AI у него включён (`apiAiInfo`,
спрашивается при синхронизации вместе с пресетами). Экран онлайновый, в отличие от
создания по пресету, и это честно: за ним стоит модель на сервере. Созданная задача при
этом живёт по общим правилам и уедет из очереди при связи.

## 6. Ошибки: что видит человек

Ни одного технического текста на экране. Каждая ситуация из требований отвечает фразой:

| Ситуация | Что видит человек |
|---|---|
| AI выключен в настройках | «AI-постановка задач выключена в настройках системы» |
| сервис не запущен | «Сервис AI не отвечает. Скорее всего, он не запущен на сервере» |
| модель не успела | «Модель не успела ответить. Попробуйте ещё раз или сформулируйте короче» |
| модель ответила не JSON | «Модель ответила непонятно. Попробуйте переформулировать запрос» |
| объект не найден | «Объект „X“ не найден. В каком магазине выполнить задачу?» |
| подходит несколько объектов | «Уточните объект — подходит несколько: A, B, C» |
| исполнитель не найден | «Исполнитель „X“ не найден. Кому поручить задачу?» |
| данных не хватает | вопрос AI и поле для ответа |

Технически это два решения: ошибка модели — это HTTP 200 с `outcome='error'` (телефону
нужна фраза, а не код состояния), а недоступный хост ловится `TRY` вокруг `EXTERNAL HTTP`
— иначе человек получил бы 500 со стеком Java.

## 7. Чего в первом этапе нет

Ни анализа фотографий, ни прогнозов, ни AI-аналитики, ни голоса, ни общего чата по
системе, ни RAG. И главное — **ни одного действия без подтверждения человека**: модель не
создаёт, не назначает и не закрывает ничего.

## 8. Грабли платформы, на которые наступили

Записаны, потому что каждая стоила отладки и повторится у следующего.

1. **`PARTITION` с параметром встроенного класса не компилируется.** Свойство
   `rank(CheckObject, ISTRING, DOUBLE, DOUBLE)` определено на бесконечном множестве, и
   окно над ним платформа построить не может: «Операция над множеством некорректна».
   Лечится переносом текста запроса и координат в `LOCAL` — их читают свойства отбора,
   а параметром остаётся только объект.

2. **`EXPORT ... TO` пишет только в `FILE` или `JSON`.** Строку он не примет («TO
   expression should return FILE or JSON value»). Для журнала файл читается обратно
   собственной формулой `convert_from($1, 'UTF8')` — `Utils.decodeText`, которым это
   делали раньше, из 7.0 убран.

3. **`APPLY` обнуляет все `LOCAL` вызывающей сессии**, включая записанные до него, — тот
   же урок, что в `apiTakeTask`. Журнал пишется своей сессией, поэтому ответ ручки
   собирается не из локалей, а из только что записанной строки журнала. Заодно ответ и
   журнал не могут разъехаться: это одна запись.

4. **Перечисление строк внутри `JSON FROM` проходит, если множество конечно условием.**
   У значения разреза нет своего класса, и окно над встроенным классом платформа
   отвергает (грабля 1). Внутри `JSON FROM` параметр `ISTRING[150] v` с условием
   `WHERE inAiContext(dm, v)` компилируется и отдаёт значения — конечным множество
   делает условие, как в `ScorecardReport`. Проверено стартом и выгрузкой тела запроса
   (#36992).

5. **`NEWSESSION NESTED (x)` возвращает наверх уже очищенное значение.** `APPLY` внутри
   такой сессии обнуляет и перенесённый локал, и при выходе наверх копируется `NULL`.
   Значение, нужное после блока, перечитывается заново.

6. **Форма читает свою сессию.** Шаг разговора пишется отдельной сессией (журнал —
   `NEWSESSION`), и форма его не видит, пока не перечитана: после шага — `formRefresh()`,
   тот же приём, что в `HypothesisAi`.

7. **Нечёткое сравнение значения ловит соседей.** `matchHint` на «Санта Кэш» подходит всем
   «Санта …» из разреза «Формат», и сервер спрашивал человека, хотя модель назвала
   значение точно. Точное совпадение (`ISTRING` сравнивается без учёта регистра) теперь
   проверяется первым, нечёткое — только когда точного нет.

## 9. Что проверено

- **Сервер**: все пять инструментов, разбор ответа, резолв подсказки «Иванову» →
  «Сергей Иванов» по всему справочнику, журнал, `TRY`-ветка недоступного сервиса.
- **Сервис**: 80 тестов (`pytest`) — отсев кандидатов, проверка кода из контекста, память
  разговора, разбор дат, кривой JSON, все виды отказа модели.
- **Клиент**: `flutter analyze` без замечаний, 354 теста, из них по AI — 17: разбор
  черновика, правка типа в карточке, обращение к ручке, и главное: подтверждение уходит
  обычной ручкой `apiCreateTask` с ключом разговора.
- **Сквозной сценарий на настоящей модели** — `qwen2.5:3b-instruct-q4_K_M`, CPU, без GPU.
  Демонстрационная фраза тикета «Поставь Иванову завтра до 18:00 задачу проверить выкладку
  Pepsi в магазине на Ленина и сфотографировать нарушения» за 18 секунд разбирается в:
  задача «Проверка выкладки Pepsi», объект «Санта на Ленина», исполнитель Сергей Иванов,
  срок 23.08, фото обязательно. «Проверить наличие ценников в магазине Уручье завтра
  утром» — объект «Санта Уручье», срок 23.08. «Проверить выкладку Pepsi» без объекта —
  вопрос «В каком магазине выполнить задачу?».

  Модель поднималась нативной Ollama, а не в контейнере: Docker Desktop на машине
  разработки не стартует. Для сервера штатным остаётся `docker compose` — движок и API
  те же самые, меняется только адрес в `LLM_BASE_URL`.

### Что показала настоящая модель (и что из-за неё исправлено)

1. **Без координат в контекст не попадал ни один объект.** Отбор искал название целиком
   («Санта на Ленина» в тексте), а человек пишет «в магазине на Ленина». Модель
   оставалась без опоры и молчала про объект — сценарий упирался в лишний вопрос там, где
   магазин назван прямо. Лечится `namedInRequest`: объект узнаётся по различающему слову
   названия (последнему), а не по названию целиком.
2. **Пустой список объектов надо назвать вслух.** Когда кандидатов нет, prompt теперь
   прямо просит вернуть подсказку словами. Маленькая модель без этой строки просто
   пропускает поле.
3. **Модель прикладывает бланк к поручению.** Просьба в prompt («бланк — только с типом
   „по бланку“») помогает не всегда: 3B забывает. Правило на сервере отбрасывает такой
   бланк, и это единственно верное поведение — иначе задача упала бы на констрейнте уже
   после нажатия «Создать».
4. **Названный магазин проигрывал тому, где стоит телефон.** «Иванову в Уручье убрать
   вещи», сказанное в магазине на Ленина, уезжало на Ленина: модель утащила «Уручье» в
   название задачи и оставила объект пустым, а сервер применил умолчание «не назвали —
   значит здесь». Умолчание правильное, но оно не должно срабатывать, когда магазин
   назван прямо в тексте, — поэтому теперь перед ним стоит поиск сервером по тому же
   тексту (`countNamedInRequest` / `objectNamedInRequest`), а несколько названных
   объектов превращаются в вопрос. Модель для этого больше не нужна: она может забыть
   про магазин, сервер — нет.

5. **Улица находилась случайно.** Продолжение того же: магазин называют улицей чаще, чем
   названием, но в адресе она в именительном («ул. Советская»), а в запросе в предложном
   («на Советской»). Точное сравнение такую пару не ловит — «на Ленина» находилось лишь
   потому, что форма случайно совпала. Теперь улица ищется основой (`aiStem`), как и
   всё остальное. Заодно закрылась вторая половина той же дыры: код магазина, названный
   моделью, сервер больше не принимает не глядя — «на Ленина» подходит трём Сантам, а
   модель уверенно называет ровно одну, и задача молча уезжала на чужой объект. Порядок
   обратный: сначала текст запроса, потом ответ модели; подошло несколько — вопрос со
   списком, а стоит человек на одном из подходящих — это и есть ответ.

6. **Фото решала модель, а не сказанные слова.** Первой отвечала модель, а разбор текста
   оставался страховкой на случай, когда поля в ответе нет, — но prompt требует `photo`
   всегда, модель его всегда и присылает, поэтому страховка не включалась ни разу. В
   журнале это выглядело случайностью: «обязательно с фото» срабатывало, «обязательно
   прислать фото и координаты» — нет. Теперь порядок обратный: сначала отрицания («без
   фото»), затем упоминание фото в тексте, и только потом ответ модели — она нужна там,
   где фото просят другими словами. Прямо сказанное слово надёжнее догадки.

## 10. Хвост первого этапа

Четыре пункта, оставшиеся после сквозного прогона на живой модели. Три закрыты
2026-09-09, четвёртый — не код.

### 10.1. Тип задачи правится в карточке

Было: модель иногда выбирает из бланочных типов не тот («Пересчёт остатков» вместо
«Процедуры»), а сменить его человек может только переформулировав весь запрос — списка
типов на телефоне нет.

Стало: список приезжает **вместе с черновиком** (`typeOptions` в ответе `apiAiDraft`), а
не в `apiAiInfo` при синхронизации. Экран AI и так онлайновый, а список, положенный в
кэш, разошёлся бы с правилами, по которым собран сам черновик.

Отбирает его правило подсистемы `typeOption (AiRequest, TaskType)` — то же самое, каким
`aiApplyRules` отбрасывает бланк у поручения: бланк живёт только на бланочном типе. Есть
бланк — предлагаются бланочные, нет бланка — небланочные. Второе важнее, чем кажется:
«Процедура» без бланка — это задача, которую исполнителю нечем выполнить, и предложить
её значит дать человеку собрать заведомо мёртвую задачу. Телефон при этом ничего не
решает — он рисует присланное, и смена типа не трогает в черновике больше ничего.

В вебе (#36992) тип — поле карточки черновика, и правится оно тем же выбором из
справочника, что и остальные поля.

Проверено: `ai_draft_check.lsf` (секция P — правило на четырёх случаях) и два теста в
`test/ai_task_test.dart` (подменённый тип уезжает в `apiCreateTask`; плашка открывает
список и меняет тип, бланк при этом остаётся при задаче).

### 10.2. Длинный разговор не теряет начала

Было: в prompt уезжают последние шесть реплик, дальше обрезается. На седьмом шаге первая
фраза — та, в которой сказано, что вообще надо сделать, — до модели уже не доезжает, а
черновик модель собирает каждый шаг заново, из одних реплик.

Стало: рядом с историей едет **свёрнутый черновик прошлого шага** — `draft*` в теле
запроса, блок «УЖЕ СОБРАНО» в prompt и отдельное правило «повтори эти поля, изменив
только то, о чём говорит последняя фраза». Разобранные сервером поля и есть всё, что от
старых реплик остаётся нужного, а возить их дешевле, чем реплики целиком.

Три решения внутри:

- **Черновик считает сервер, словами его излагает сервис.** lsFusion шлёт плоские данные
  (`lastDraft` — последний шаг, на котором черновик собрался), prompt из них собирает
  сервис. Граница ровно та же, что и везде: правила там, язык здесь.
- **`lastDraft`, а не `lastRequest`.** Последний шаг мог кончиться отказом сервиса
  (модель не успела), и его запись пуста — память разговора не должна теряться из-за
  таймаута.
- **Названный в черновике код обязан быть виден модели и в списках.** Кандидатов сервер
  отбирает по НОВОЙ фразе, а «перенеси на пятницу» не похоже ни на один магазин. Без
  этого модель повторила бы код из «уже собрано», а сервис превратил бы его в подсказку
  («кода не было в контексте») — и разговор пошёл бы искать по всему каталогу уже
  выбранный магазин. Не оказалось кандидата в списке — сервис дописывает его сам.

Рассмотрено и отвергнуто: держать память на сервере, подставляя в черновик поля, которых
модель не назвала. Тогда «убери срок» перестаёт работать — «модель забыла» и «человек
снял» становятся неразличимы. Модель остаётся хозяином текущего шага, сервер — памятью о
прошлых.

Чего это не закрывает: вариант, выбранный на телефоне пальцем, в память разговора не
попадает. Он применяется на месте, без обращения к серверу (см. §5), и журнал о нём не
знает — следующая фраза уедет к модели с тем черновиком, который собрал сервер, то есть
без выбранного магазина. Так было и до этой правки; лечится это не памятью, а тем, чтобы
телефон присылал свой черновик вместе с фразой, — но это уже другой контракт ручки.

Проверено: шесть тестов в `ai-service/tests/test_prompt.py` (включая разговор из десяти
шагов при окне в два) и замер на живой модели — `qwen2.5:3b-instruct-q4_K_M`, седьмой шаг
разговора, окно в две реплики, магазина черновика в кандидатах нет:

| | без памяти (как было) | с памятью (как стало) |
|---|---|---|
| задача | «Перенести задачу» | «Проверить выкладку Pepsi» |
| объект | b31 — единственный кандидат | b24 — тот, что выбрали на первом шаге |
| исполнитель | petrov — первый из списка | ivanov |
| фото | потеряно | обязательно |
| срок | пятница | пятница |

Без памяти от черновика не остаётся ничего: модель собирает его заново из последней
фразы, а недостающее берёт из списков кандидатов — то есть выдумывает и магазин, и
человека. Замер заодно подтвердил, что дописанный сервисом кандидат работает: кода `b24`
в присланном списке не было, и без него ответ модели превратился бы в подсказку.

Тем же замером поймана одна поправка в prompt: на правку уже собранного модель отвечала
вопросом «Перенести на пятницу?» — переспрашивала про то, что только что сделала. Правило
9 теперь говорит об этом прямо. Сервер такой вопрос и так отбрасывал (§9, вопрос модели
младше собранного черновика), но confidence из-за него падала, а в журнале шаг выглядел
уточнением.

### 10.3. Уверенность — только низкая, и это решение, а не умолчание

`confidence` остаётся тем, чем был: предупреждением «AI не уверен в разборе» при значении
ниже 0.5 и полем журнала во всех остальных случаях.

Показывать число всегда — значит обещать точность, которой нет: у трёхмиллиардной модели
это не калиброванная вероятность, а привычка отвечать 0.9. Человеку в зале от «0.92»
пользы никакой, а «проверьте внимательнее» — есть. Полное значение при этом никуда не
девается: оно в журнале AI-запросов, где по нему и разбирают, почему разбор вышел таким.

### 10.4. Осталось: прогон в контейнере на сервере заказчика

`docker compose up -d` на машине разработки не проверялся — Docker там не поднимается,
и модель для сквозного прогона поднималась нативной Ollama. Движок и API те же самые,
меняется только адрес в `LLM_BASE_URL`, но проверить связку в штатной установке всё
равно надо (`ai-service/INSTALL.md`).

## 11. Веб и пачка задач по критерию (#36992)

### 11.1. Веб — ещё один потребитель того же сценария

Форма `aiTaskWeb` (`storeTasks/ai/AiTaskWeb.lsf`): пункт «Операции → Поставить задачу
текстом» и кнопка на списке задач, оба только при `aiEnabled`. Лента — шаги `AiRequest`
по ключу разговора, ответ сервера к каждому шагу, уточняющий вопрос остаётся в ленте.
Карточка черновика правится на месте, включая тип. Отдельного разбора у веба нет: шаг
разговора — тот же `aiMakeDraft`, что у телефона, в своей сессии.

Выключение AI в уже открытом сеансе веб-клиента пункт навигатора не убирает — клиент
строит его при входе; форма при этом отвечает «AI-постановка задач выключена в
настройках системы», а в новом сеансе пункта нет.

Лента сделана штатной формой, без `CUSTOM`-компонента: разговор короткий, и список шагов
с полем ввода его показывает.

### 11.2. Пачка

Критерий — пара «разрез + значение» (`batchDimension`/`batchValue` в журнале), а не
выражение. Модель называет её парами «id + подсказка»; разрешает сервер
(`aiResolveCriterion`): разрез по коду или подсказке, не разрешился — по значению.
Значение ищется ступенями, и берётся лучшая ступень, на которой что-то нашлось
(`AiTools.valueTier`):

1. точное совпадение (без регистра, «ё» = «е»);
2. каждое слово подсказки — склонённое слово значения: «Минска» → «Минск»;
3. основа каждого слова подсказки есть в значении: «Гродненской» → «Гродненская».

Слово, совпадающее с названием самого разреза («область», «город», «формат»), в
сравнении не участвует, а остальные слова подсказки обязаны найтись все: «Гродненская
область» больше не подходит к «Московская область». Разрез по значению выбирается той
же лучшей ступенью по всем разрезам: «Гомель» — точно город, а не «Гомельская область».

Пачка или одна задача — решает сервер (`aiResolveBatch`), по порядку:

1. Магазин назван в тексте — ровно один объект по `AiTools.namedInRequest(o, 4)`: полным
   названием, улицей или номером. Полное название ищется с границей — до и после него в
   тексте не буква и не цифра: «в магазине Санта 111» называет «Санта 111» и не называет
   «Санта 11»; спецсимволы в названии («Точка(», «+») экранируются, запрос не падает.
   Номер называет объект, только если стоит сразу после
   слова, начинающегося основой первого слова названия: «в Санте 57», «Санте №26»,
   «Санта-26» (`namedByNumberIn`, основа от 4 букв). Ищется любое вхождение «слово +
   номер», а не слово перед первым числом фразы: «До 26 октября проверить ценники в Санте
   26» называет Санту 26. Число без слова объект не называет: «во всех Сантах Бреста до 26
   октября» — это срок, а не Санта 26. Основа берётся из буквенной части первого слова
   названия, дефис внутри слова — часть слова («в свод-объекте 12»); скобка или другой знак
   в названии слово обрывают. Исключение — название, у которого буквенная часть первого
   слова короче четырёх букв («С - 204», `numberWord` пуст): такой объект номер называет
   один, где бы тот ни стоял. Объект, который вернула модель, в этом правиле не участвует:
   на «по всем магазинам Бреста» 3B возвращает случайный брестский магазин.
   - Назван объект и разрешился критерий — всегда вопрос, входит объект в критерий или
     нет: «Назван объект «Санта 57» (Город: Брест), а критерий — «Город = Брест». Одна
     задача в «Санта 57» или пачка по критерию?». Объект и критерий записываются в
     шаг-вопрос журнала (`draftObject`, `batchDimension`/`batchValue`).
   - Ответ решается относительно шага-вопроса, а не по тому, что модель вернула заново.
     «одну», «одну задачу» — одна задача в объекте вопроса (или в объекте, названном в
     ответе); «пачку», «все магазины» — пачка по критерию вопроса; в ответе только
     объект — одна задача в нём; остальное — тот же вопрос ещё раз. Объект, решённый
     этим шагом, по тексту ответа повторно не узнаётся: ответ «одну задачу в «Санта 111»»
     ставит Санту 111, хотя в её имени есть имя «Санта 11». В ответе названо несколько
     объектов — вопрос «в запросе названо несколько», молча брать объект вопроса нельзя.
     Новая фраза со своим критерием критерий вопроса не затирает: после вопроса про
     Брест «проверить по всем магазинам Бобруйска» — пачка по Бобруйску. Критерий
     вопроса берётся, только когда шаг не принёс своего.
   - В вебе под лентой на этот вопрос две кнопки, «Одна задача» и «Пачка по критерию».
     Выбор уходит признаком (`aiBatchAnswer`: `one` / `batch`), а не текстом с названием
     объекта или критерия: текст шага — подпись кнопки, он не разбирается, объект и
     критерий берутся из шага-вопроса.
   - Шаг-вопрос — последний собранный шаг разговора (`askedBatchOrObject` поверх
     `lastDraft`), а не последняя запись журнала: шаг с ошибкой сервиса между вопросом и
     ответом вопроса не теряет, кнопки остаются.
   - Назван объект, критерия нет — одна задача.
2. Критерий не разрешился — вопрос человеку, а не пачка по всей сети.
3. Критерий разрешился — пачка; число попавших объектов считается сразу. Если текст
   при этом узнаёт несколько магазинов (улица «Минская» во фразе про Минск), пачка
   ставится с замечанием, какие магазины узнаны.
4. Попало больше потолка (`aiBatchLimit`, по умолчанию 50) — вопрос с числами. Пачка
   не обрезается никогда.

Пачка разбирается только в вебе (`aiBatchMode`): телефону разрезы не отправляются, и
prompt у него прежний. Два общих правила при этом действуют и на телефон:

- «номер у слова» (`namedByNumberIn`, для телефона основа от 6 букв, у слов короче
  восьми — слово без последней буквы) — им узнаётся объект
  в тексте (`aiResolveObject`), собирается список вариантов к вопросу «названо несколько»
  (`AiTaskApi`) и ставится приоритет объекта в контексте модели (`aiObjectPriority`).
  Поэтому состав объектов в запросе телефона может отличаться от прежнего: «касса 205»,
  «в магазине 11», «в Санте 26», «в Санте №26» узнаются, как раньше; число, стоящее не
  сразу после слова названия
  («Проверить ценники, Санта, магазин 26», «магазин на Дунина 11»), номером больше не
  узнаётся — такой магазин находит улица, подсказка модели или вопрос;
- бланочный тип без бланка в черновике становится «Поручением» с замечанием (ниже).

Создание (`AiTaskBatch.createBatch`) — одной транзакцией и тем же примитивом, что у
ручки телефона (`StoreTaskCreate.doCreateTask`). Исполнитель — ответственный по объекту
(активная роль на объекте с наименьшим порядком, исполнитель не в архиве); нет
ответственного — задача без исполнителя, в предпросмотре пометка. Выброшенные из пачки
объекты хранятся в журнале (`excluded`), связь задачи с разговором — ссылкой
`aiRequest(Task)`, а не `clientId`. Отказывает сервер, а не спрятанная кнопка: нет права
«Массовое создание задач» (администратор системы проходит, как и с соседними правами),
пачка уже создана, не осталось объектов, перебор потолка. Право выдаётся роли
«Супервайзер» при загрузке данных по умолчанию; у роли, существующей на рабочей базе
до установки подсистемы, его не появится — администратор выдаёт его руками (см. INSTALL,
раздел о загрузке данных).

Правила самой задачи — свойство задачи `StoreTaskCreate.createDenied(Task)`: тип,
название, объект, «бланк только у бланочного типа», «бланочный тип только с бланком»,
исполнитель не в архиве. Проверяет его сам примитив `doCreateTask`: нарушившую правило
задачу он не создаёт и возвращает причину (`createRefusal`). Поэтому правила действуют
для любого вызова: одна задача из веба, пачка (первый отказ отменяет всю пачку, задач 0),
ручка телефона `apiCreateTask` (отказ приходит ошибкой ручки до записи). Модель часто ставит бланочный тип («Проверка ценников», «Проверка по чек-листу»)
без бланка. Черновик чинит это сам, общим правилом для веба и телефона
(`aiApplyRules`): тип меняется на «Поручение» (`aiPlainType`), в черновике замечание
«Тип «Проверка ценников» заполняется по бланку, а бланк не выбран — ставится
«Поручение»». Поэтому черновик с исходом `ok` примитив всегда пропускает. Карточка веба,
где тип и бланк меняют руками, говорит «выберите бланк или другой тип». Выбор типа в карточке — по тому же правилу, что `typeOption` у телефона: с бланком
только бланочные типы, без бланка — только небланочные; выбор бланка у небланочного типа
переводит его в «Процедуру», снятие бланка у бланочного — в «Поручение», те же умолчания,
что у черновика (`aiTemplateType`, `aiPlainType`). Проверки ручки телефона по сырому
запросу и их тексты не менялись, правило примитива срабатывает после них. Для телефона
изменилось одно: бланочная задача без бланка раньше создавалась, теперь ручка отказывает
текстом правила. AI-черновик такой задачи не даёт — он приходит с «Поручением» и
замечанием; отказ получит только запрос, собранный не из черновика.

Уведомления не менялись: каждое назначение — одна запись «назначена задача». Пачка из
10 задач с 7 ответственными дала 7 записей.
