# Черновики задач в Redmine — бэк-офис, отчёты и веб-интерфейс

> Статус: **черновики, в Redmine не заведены**. Дата: 2026-08-06. Ветка `mvp_tasks`.
> Проект: `retail-help-desk` (id 221) · трекер «Изменение» (id 2).
>
> Отбор по одному признаку: **ни одна задача не требует доработки мобильного клиента.**
> Всё делается на сервере и в веб-клиенте lsFusion, Flutter не пересобирается.

## Почему это вообще возможно

Мобильный клиент — не набор экранов на каждый тип задачи, а **рендерер схемы**:
`apiExecution` отдаёт разделы, поля, типы и конфиг, клиент рисует по описанию. Поэтому
доработки требуют только две вещи: новый **тип поля** и новый **жест** на телефоне.

Всё остальное для клиента невидимо:

| Что меняем | Нужен Flutter? |
|---|---|
| Новый шаблон, новый тип задачи, новая шкала вердиктов | нет — приезжает данными |
| Атрибуты объекта проверки, справочники, импорт | нет — телефон их не рисует |
| Отчёты, печатные формы, своды | нет — это выход, а не вход |
| Веб-интерфейс: канбан, дашборды, разбор | нет — другой клиент |
| Расписания, уведомления, эскалация, follow-up задачи | нет — задачи приезжают обычным `apiTasks` |
| Новый тип поля (`table`-строки, подпись, гео) | **да** |

## Про универсальность

Граница «абстрактное против справочника» — единственное решение, которое здесь легко
принять неправильно. Тест один: **если завтра подключим второй хост, у него это уже
есть?**

- **Да → абстрактный класс + мост.** Объект проверки, исполнитель, категория объекта,
  предмет строки. Хост переопределяет свойства своими объектами, копии не заводится.
- **Нет → справочник у нас.** Шкала вердиктов, шаблоны, статусы и приоритеты задач,
  состав ролей процесса проверок — этого в ERP или WMS нет и не будет.
- **И то и другое → гибрид.** Состав ролей наш, а кто на роли — знает хост: абстрактное
  свойство с локальным запасным (см. тикет 1).

Копия чужого классификатора у себя — всегда ошибка: она разъезжается с источником
на второй же неделе.

Кейс «Санты» покрывается целиком, но **ни одна задача ниже не называет Санту в коде**.
Везде, где у заказчика конкретика (девять ролей, восемь форматов, пять градаций,
40 пунктов), в системе — справочник или настройка шаблона. У каждого тикета для этого
отдельная строка **Универсально**; если её нельзя написать честно, тикет спроектирован
неправильно.

# A. МАСТЕР-ДАННЫЕ

## 1. [Справочники] Категория и роли объекта проверки — ЗАВЕДЕНО #36708

**Цель.** У `CheckObject` сегодня только название и адрес. В шапку акта нужны
ответственные, а в отчёты — разрез по типу объекта. При этом у хоста и то и другое
как правило **уже есть**, и заводить у себя копию классификатора нельзя: она разъедется.

**Состав.**

Категория — **абстрактный класс**, ровно как сам `CheckObject`:

```lsf
CLASS ABSTRACT ObjectCategory 'Категория объекта';
id '{ID}' = ABSTRACT ISTRING[30] (ObjectCategory) CHARWIDTH 10;
name '{Name}' = ABSTRACT ISTRING[100] (ObjectCategory) CHARWIDTH 20;
category = ABSTRACT ObjectCategory (CheckObject);
```

Хост подключает свой существующий классификатор — новых данных не заводится:

```lsf
EXTEND CLASS StoreFormat : ObjectCategory;   // формат торгового объекта, уже есть в ERP
id (StoreFormat f) += ...; name (StoreFormat f) += ...;
category (Location l) += format(l);
```

Standalone получает тонкий собственный справочник `CheckCategory : ObjectCategory` с
формой в навигаторе — так же, как `CheckAsset` закрывает `CheckObject` без ERP.

Роли — **гибрид**, потому что это две разные сущности. Состав ролей задаёт заказчик
процесса, в хосте такого справочника нет → обычные данные у нас. Кто стоит на роли —
хост часто знает (заведующий магазином в ERP есть) → абстрактное с локальным запасным:

```lsf
CLASS ObjectRole 'Роль на объекте';                                // code, name, порядок
responsible = ABSTRACT TaskPerformer (CheckObject, ObjectRole);    // знает хост
responsibleData = DATA TaskPerformer (CheckObject, ObjectRole);    // ведём сами
person (CheckObject o, ObjectRole r) = OVERRIDE responsible(o, r), responsibleData(o, r);
```

Хост в приоритете: иначе однажды введённое руками ФИО навсегда перекроет актуальные
данные ERP. На форме роли, которые отдаёт хост, показываются `READONLY`, остальные
вводятся; какие именно — видно из того, вернул ли `responsible` значение.

**Готово когда.** Категория объекта в ERP-сборке приезжает из ERP без ввода и без
импорта; в standalone ведётся своим справочником; роли настраиваются произвольным
набором, добавление десятой роли не требует правки кода; отчёты фильтруются по категории.

**Универсально.** Ни одного классификатора-копии: то, что у хоста уже есть как объекты
(объект, исполнитель, категория), подключается переопределением свойств; данными у нас
остаётся только то, чего в хосте нет в принципе — состав ролей процесса проверок.

**Зависит от.** Ничего. Пересекается с #36682 (координаты `CheckObject`) — тот же класс,
разумно делать подряд.

**Заменяет** черновик «[Справочники] Роли на объекте проверки» из
`_redmine-drafts-checklist-engine.md` — заводить только один из двух, этот шире
(добавлена категория объекта).

**Подсказки.** `task/CheckObject.lsf:10` (абстрактный класс), `meta/TaskPerformer.lsf:14`
(кто такой ответственный — тоже абстрактный), `erp/CheckObjectLocation.lsf:9`
(`EXTEND CLASS Location : CheckObject` + `name(Location l) += Inventory.name(l)` — готовый
образец моста, категория делается им же), `fillable/CheckAsset.lsf` (тонкая реализация
для standalone).

**Вложения к задаче.** Бланк проверки заказчика — скрытый лист «Данные» содержит
справочник объектов (≈263 строки) с форматами и ролевыми ФИО, из которого шапка бланка
тянется через `VLOOKUP`. Это и есть состав ролей и категорий, который нужно покрыть.

**Риск.** Правила графика (тикет 11) будут ссылаться на объекты категории, живущие в
хосте. Если хост пересоздаёт свой классификатор (переимпорт с удалением), ссылки поедут.
Если это возможно — хранить в правиле `id` категории, а не ссылку.

**Оценка.** M.

## 2. [Интеграция] Синхронизация справочника объектов — В REDMINE НЕ ЗАВОДИТСЯ

> **Решение 2026-08-07: тикет не заводим.** Объекты проверки приезжают от хоста — из ERP
> или из MITE, — а загрузка из файла нужна была бы только контуру, где хоста нет. Для
> демо объекты заводит seed-скрипт стенда. Текст оставлен на случай, если контур
> заказчика окажется без интеграции; тогда обязательное требование — `id` из файла
> заказчика, см. «Риск переезда» ниже.

**Цель.** У заказчика 279 объектов, у каждого адрес, категория и девять ответственных.
Магазины живут **не в WMS, а в отдельной системе** (уточнено 2026-08-06), поэтому моста
из тикета 1 недостаточно: подключать нечего, данные надо принимать снаружи. Без них нет
ни отчётов, ни графика, ни адресатов уведомлений — тикет блокирующий.

**Загрузка — не альтернатива мосту, а источник для собственной реализации.**
`CheckObject` абстрактный и своих данных не имеет никогда: в ERP-сборке его закрывает
`Location`, в MITE — прибор, в standalone — `CheckAsset` с собственными атрибутами
(`erp/CheckObjectLocation.lsf`, `StoreTaskStandalone.lsf`). Загрузка пишет **только в
`CheckAsset`** и больше никуда. Там, где объекты приезжают от хоста, модуль загрузки
просто не подключается — как `erp/` не подключается в standalone.

**Проектировать как синхронизацию, а не как разовый залив.** Операция одна —
идемпотентный upsert по стабильному `id`; XLSX только первый источник. Когда у системы
заказчика найдётся выгрузка или API, меняется источник, а не логика приёма. Разовый
импорт пришлось бы переписывать целиком.

**Состав.** Форма загрузки: файл, лист, маппинг колонок на атрибуты, категорию и роли;
режим «создать и обновить» по `id`. Отчёт о загрузке: создано / обновлено / строк с
ошибками и почему. Сопоставление людей — по стабильному ключу (табельный номер, при
отсутствии — нормализованное ФИО), иначе один региональный менеджер на двадцати
магазинах превратится в двадцать разных людей.

**Ответственные — не пользователи «Пульса».** Технолог, СОФ, региональный получают акт,
но в систему не заходят. Предлагается заводить их как `CustomUser` без права входа
(`TaskPerformer` в standalone реализован именно через него), а не отдельным справочником
людей: ответственный вполне может стать исполнителем корректирующего действия (тикет 13),
и два параллельных справочника людей придётся сливать. Решение зафиксировать в тикете.

**Готово когда.** Файл заказчика загружается целиком, повторная загрузка не плодит ни
объектов, ни людей, изменения в файле доезжают до существующих записей.

**Универсально.** Маппинг колонок — данные, а не код: у другого клиента свой файл со
своим порядком колонок и своим набором ролей. Приёмник один и тот же для файла и для
будущего API.

**Риск переезда — решается одной строкой сейчас.** Если позже к системе магазинов
заказчика появится мост, объекты станут **другими** объектами (реализация сменится с
`CheckAsset` на класс хоста), а история проверок останется на старых. Перепривязка
дешёвая ровно в одном случае: если `assetId` при загрузке — это код магазина заказчика,
по которому мост потом сойдётся. Выдуманный или порядковый `id` делает переезд ручной
работой на 279 объектов. Поэтому: **`id` берём из файла заказчика, не генерируем.**

**Зависит от.** Тикет 1 (категория и роли — есть куда класть).

**Подсказки.** `IMPORT XLS ... TO` со staging-локалами, затем два прохода: сначала
создание отсутствующих по ключу, отдельно — обновление атрибутов (смешивать в одном
цикле нельзя). `HEADER` обязателен, иначе сдвиг колонки молча даёт `NULL`.

**Оценка.** M.

## 3. [Чек-листы] Импорт шаблона из XLSX — В REDMINE НЕ ЗАВОДИТСЯ

> **Решение 2026-08-07: тикет не заводим.** Формат бланка у заказчика меняется, и импорт
> под него пришлось бы вести следом — продуктовый код на разовую по сути операцию.
> Заводить шаблоны продукт и так умеет: формы `Template`/`Section`/`Field` есть, клиент
> вводит свой бланк сам. Ускорение сделаем **скиллом**: агент читает xlsx-бланк и
> заводит шаблон через API, без изменений в продукте. Текст ниже — исходные требования,
> пригодятся скиллу.

**Цель.** Бланк заказчика — 8 разделов и 40 пунктов, и это только один из бланков.
Вбивать их руками через форму шаблона — часы на каждый, а при правке бланка всё заново.

**Состав.** Импорт «разделы + пункты» из файла: раздел, номер, текст пункта, максимум
балла (норма), шаг, обязательность, критичность. Создание нового шаблона или обновление
существующего по коду пункта. Проверка суммы максимумов и предупреждение, если она не
сходится с ожидаемой (у заказчика ровно 100).

**Готово когда.** Бланк из файла заказчика загружается в шаблон, сумма максимумов
совпадает, проверка по нему заполняется на телефоне без единой правки кода.

**Универсально.** Импортируется структура, а не смысл: тип поля и механика начисления
берутся из настроек шаблона, которые уже есть.

**Вложения к задаче.** Бланк проверки заказчика: лист «чек лист 100» — 8 разделов,
40 пунктов, веса разделов формулой; скрытый лист «Зона допеканя» — второй бланк на
5 пунктов со своей шкалой, на нём проверяется, что импорт не заточен под первый.

**Зависит от.** Ничего.

**Подсказки.** `fillable/Template.lsf` (`Template`/`Section`), `fillable/Field.lsf`
(`code` пункта — стабильный ключ обновления), правила импорта: создание и обновление
разными проходами.

**Оценка.** M.

## 4. [Чек-листы] Подытоги по разделам — ЗАВЕДЕНО #36709

**Цель.** В бланке заказчика вес раздела = сумма максимумов его пунктов, и раздел
показывается со своим итогом. У нас балл считается только по заполнению целиком.

**Состав.** Агрегаты «максимум по разделу» и «факт по разделу» над (`Filling`, `Section`);
вывести в форму заполнения и в акт. Процент по разделу — там же.

**Готово когда.** В форме разбора и в акте у каждого раздела свои «из скольких» и
«сколько», сумма разделов сходится с итогом.

**Универсально.** Обычный агрегат по существующему `Section` — работает для любого
шаблона, включая процедурные без оценки (там просто пусто).

**Вложения к задаче.** Бланк заказчика: вес раздела считается формулой `=SUM(...)` по
максимумам его пунктов, итог — простая сумма фактов. Это и есть требуемая арифметика.

**Зависит от.** Ничего.

**Подсказки.** `fillable/Filling.lsf` — `totalScore`/`totalMax` рядом, делать той же
формой; `fillable/Template.lsf:18` (`CLASS Section`).

**Оценка.** S.

# C. ОТЧЁТЫ

## 5. [Отчёты] Печатная форма акта проверки

**Цель.** Результат проверки должен выходить документом: сегодня его нет вообще, а у
заказчика акт — то, что реально уходит ответственным и обсуждается.

**Состав.** Печатная форма по заполнению: шапка (объект, категория, адрес, ответственные
по ролям, дата, проверяющий), разделы с подытогами, пункты с фактом и примечанием,
отдельный блок несоответствий с фото, итог, процент и вердикт. Кнопка печати на форме
заполнения и в списке.

**Готово когда.** По разобранной проверке печатается акт, совпадающий по составу с
образцом заказчика; по процедурной задаче без оценки печатается тот же акт без блока
баллов.

**Универсально.** Одна печатная форма на все шаблоны: структура акта — это данные
(разделы, пункты, шкала), а не вёрстка под конкретный бланк.

**Вложения к задаче.** Бланк заказчика: лист «чек лист 100» — состав и порядок акта;
лист «Результаты проверки 100» — как оформлен итог. Область печати в бланке задана
(`A1:K80`), по ней и верстать.

**Зависит от.** Тикеты 1 (роли в шапке) и 4 (подытоги). Тикет 0 **не нужен**: состав акта
берём из бланка заказчика, который уже разобран (шапка с ролями через `VLOOKUP`, разделы
с весами, пункты «норма / факт / примечание», итог и вердикт).

**Подсказки.** `FORM filling` в `fillable/Filling.lsf` — основа для печатной. Имя
jrxml-шаблона обязано совпадать с каноническим именем формы, иначе платформа молча
переходит на автоматический дизайн и все шаблоны отчёта игнорируются.

**Оценка.** M.

## 6. [Отчёты] Свод результатов по объектам и периодам

**Цель.** Заказчик ведёт помесячный свод баллов по объектам в отдельном файле руками.
Это должно считаться само.

**Состав.** Форма-отчёт: строки — объекты проверки, колонки — периоды (месяц/квартал),
в ячейке процент и вердикт, подсветка по цвету уровня шкалы. Фильтры: категория объекта,
шаблон, проверяющий, период. Итоги по колонке и по строке. Экспорт в XLSX.

**Готово когда.** Свод за период собирается по данным системы и сходится с ручным
файлом заказчика за тот же месяц.

**Универсально.** Разрез — по любому шаблону и любой категории; периодичность —
параметр, а не константа.

**Зависит от.** Тикет 0 (структура свода), тикет 1 (категория для фильтра).

**Подсказки.** `fillable/Filling.lsf` — `percent`, `verdictLevel`, `rgbColorLevel` уже
есть; группировка по `checkObject(task(e))` и периоду от `dateTime`.

**Оценка.** M.

## 7. [Отчёты] Свод нарушений

**Цель.** Второй файл заказчика — повторяющиеся нарушения по пунктам и объектам. Это
то, ради чего проверки и проводятся: балл говорит «плохо», свод нарушений — «что чинить».

# Демо для заказчика — приоритет №1

Цель ближайшего этапа: провести проверку заказчика от начала до конца на его собственных
данных. Три тикета плюс стенд: **1 ‖ 4 → 5**, стенд параллельно. Презентацию-отчёт не
разбираем, акт проектируется по бланку; загрузку объектов и импорт шаблона не делаем —
объекты в бою приезжают от хоста, бланк заводится формами продукта, а для стенда и то и
другое кладёт seed-скрипт.

**Сценарий показа.** Объекты заказчика с форматами и ответственными и их бланк «РЫБА»
уже в системе → задача на конкретный магазин → проверяющий
заполняет с телефона, включая шаг 0.5 и примечания → на объекте виден процент, вердикт
по их пятиуровневой шкале и подытоги разделов → печатается акт с ответственными в шапке.

**Коробочность — критерий приёмки каждого тикета, а не пожелание.** Демо собирается
из продуктовых механизмов, иначе оно не масштабируется на второго клиента:

1. Всё, что показывается, настраивается **из интерфейса**, без правки `.lsf`: бланк,
   роли, категории, шкала вердиктов, показатели главной.
2. В `src/main/lsfusion/storeTasks/` — ни одного упоминания заказчика, его форматов,
   ролей и чисел. Данные заказчика живут только в `scripts/`.
3. Тест «второй клиент» перед сдачей тикета: другой бланк, другой набор ролей, другая
   шкала — работает без единой строки кода.
4. Стенд воспроизводим с нуля: чистая база + скрипт + два файла = рабочая система.
   Если демо держится на руками наведённых данных, оно разваливается при первом же показе.

**Сборка стенда — обязательная работа, а не факультатив.** Раз ни загрузки объектов, ни
импорта шаблона нет, seed-скрипт остаётся единственным источником данных для показа:
объекты заказчика с категориями и ответственными, **бланк «РЫБА» целиком** (8 разделов,
40 пунктов, веса, шаг 0.5, пятиуровневая шкала), задачи в разных статусах и история
проверок за несколько месяцев — иначе на дашборде и в сводах пусто. Идемпотентный, сроки
относительные, как уже сделано в `scripts/testdata.lsf`.

Из-за бланка оценка выросла с S до **M**: сорок пунктов с нормами — это основной объём
скрипта. Ровно эту работу потом снимет скилл, превращающий xlsx в шаблон.
