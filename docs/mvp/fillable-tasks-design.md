# Заполняемые задачи — единый движок (дизайн)

> Доменная модель для пользовательского заполнения задач разных типов
> (обслуживание оборудования, замена SIM, ремонт, инспекции по чек-листу, …).
> Статус: **дизайн согласован**, первый слайс в работе. Ветка `mvp_tasks`.

## 1. Идея

Всё «заполняемое» — это **Шаблон → Разделы → Поля**; **Исполнение** хранит значение
на каждое поле. Чек-лист перестаёт быть отдельной сущностью: это шаблон, у которого
поля типа `scale`/`number`. Новый бизнес-тип задачи = **конфигурация** (шаблон + опц.
finish-эффект), **без нового кода клиента и без нового API**.

Разделяем два понятия:
- **Вид исполнения (движок, код, мало):** единый заполняемый движок (`Filling`). Пересчёт
  и проверка ценника пока живут отдельно (line-item), вольются позже через тип поля `table`.
- **Бизнес-тип задачи (`TaskType`, данные, много):** имя/иконка/цвет + ссылка на шаблон.

## 2. Согласованные решения

| # | Решение |
|---|---------|
| 1 | **Unify** — один движок полей; чек-лист = частный случай (scale/number поля). |
| 2 | Цель задачи — **простой абстрактный объект** (`Asset`), без тяжёлого мастера серийников/атрибутов. |
| 3 | **Варианты → `code`** (стабильный код, не позиционный индекс). |
| 4 | **Resolution — фиксированный enum.** |
| 5 | **`table` (строки/запчасти) откладываем**; так же multichoice/подпись/гео. |
| 6 | Раз `Asset` без атрибутов — **write-back в мастер-объект откладываем** (SIM: ICCID пишется в `FieldValue`, не в прибор). |
| 7 | Эталон приёмки первого слайса — **«Замена SIM»** end-to-end на телефоне + существующий чек-лист на новом движке. |

## 3. Доменная модель

```
TaskType ── шаблон ──► Template ──1..*──► Section ──1..*──► Field ──► OptionSet ──1..*──► Option
   ▲                      (порог, note,        (раздел)     (тип, code,   (для scale/     (code, score,
   │ тип                 resolutionRequired)                 вес, флаги)   choice)         nonconformity)
  Task ── объект ──► CheckObject «abstract» ◄── Location (магазин)
   │                                        ◄── Asset (объект/прибор, тонкий)
   └── исполнение ──► Filling : Execution ──► FieldValue (значение на Filling × Field)
                       (resolution, % и вердикт — только по scored-полям)
```

- `CheckObject` — абстрактная цель (уже есть, мост к `Location`); добавляем мост к `Asset`.
- `Asset` — тонкий: имя + опц. родительская локация. Без атрибутов/истории (реш. 2/6).
- `Template/Section/Field` — конфигурация шаблона. `Field.code` и `Option.code` — стабильные.
- `Filling : Execution` — заполнение наряда по шаблону. Значения — свойства над (`Filling`,`Field`).

## 4. Каталог типов полей (`FieldType`)

| Тип | Хранит | Конфиг на `Field` | Оценка |
|-----|--------|-------------------|--------|
| `scale` | `Option` | `optionSet` (со баллами) | да: `score × weight` |
| `number` | число | `unit`, `minNorm`/`maxNorm`, знаки | да: в норме → `weight`, иначе 0 |
| `boolean` | да/нет | какой = несоответствие | опц. |
| `choice` | `Option` | `optionSet` | только если у вариантов есть балл |
| `text` / `longtext` | строку | `maxLen` | нет |
| `date` | дату | `min`/`max` | нет |
| `photo` | 1 фото (MVP; 0..N позже) | — | нет |
| `scan` | строку | формат/длина/regex | нет |
| `objectref` | ссылку на объект | целевой класс + фильтр | нет |
| `table` *(отложено)* | строки | колонки = под-поля | опц. |

**Сквозные флаги (любой тип):** `required`, `requirePhoto` (доп. фото-свидетельство при
несоответствии), `requireComment`, `critical` (для scored → крит-фейл), `weight`, `hint`, `order`.

**Разграничение:** `photo`-*тип* — фото и есть ответ; `requirePhoto`-*флаг* — доп. свидетельство
к любому полю. Хранилище одно (`IMAGEFILE(decode(base64))` + оффлайн-очередь).

**Оценка:** % по полям `scale`/`number`/`boolean-scored` с весом; крит-несоответствие →
«не пройдено». Нет scored-полей → процента нет, итог задаёт `resolution`.

## 5. Resolution (фиксированный enum)

| code | Подпись | На finish |
|------|---------|-----------|
| `done` | Выполнено | закрыть |
| `doneWithIssues` | Выполнено с замечаниями | закрыть + корректирующее действие |
| `needsParts` | Нужна запчасть | закрыть + follow-up «поставка/установка» |
| `revisit` | Повторный визит | follow-up «новый визит» |
| `failed` | Не выполнено | закрыть как невыполнено |

Оценочные шаблоны (чек-лист) резолюцию **не требуют** (итог = вердикт); процедурные —
требуют. Флаг `resolutionRequired` — на шаблоне.

## 6. Обобщённый API (мутации — JSON-тело)

| Метод | Тело | Назначение |
|-------|------|-----------|
| `POST apiStartExecution` | `{id}` | создать `Filling`, если нет |
| `GET  apiExecution` | `?id=` | схема + значения + варианты + resolution (один вызов, кэш оффлайн) |
| `POST apiSetField` | `{id, field, value}` | значение поля (тип диктует value) |
| `POST apiSetFieldPhoto` | `{id, field, photo}` | прикрепить/очистить фото |
| `POST apiSetResolution` | `{id, resolution}` | зафиксировать исход |
| `POST apiFinishExecution` | `{id}` | валидация + finish-эффект + закрытие |

**`value` по типам:** scale/choice → `code` варианта · number → число · boolean → true/false ·
text/scan → строка · date → ISO · objectref → id объекта.

**Адресация — по `field` (код)**, не позиционно. `apiExecution` = слияние сегодняшних
`apiChecklistItems + apiChecklistOptions + apiInspectionInfo`.

## 7. Клиент

Один **schema-рендерер** вместо экрана-на-тип. `apiExecution` → секции/поля с типом/конфигом/
значением. Виджеты: scale/number (есть) + text/scan/photo/choice/date/objectref. Оффлайн-очереди
и фото переиспользуются — ключ `(si,ii)` → `field`.

## 8. Первый слайс

**Сервер:** `FieldType`/`Resolution` (static enum), `Asset` (+мост к `CheckObject`),
`OptionSet`/`Option(code)`, `Template`/`Section`/`Field`, `Filling : Execution` + значения полей;
обобщённый API; абстрактный finish-хук (реализации — потом).
**Миграция:** чек-лист (`Inspection`/`ChecklistItem`/`Scale`) → новый движок; демо пересобрать.
**Клиент:** экран чек-листа → общий рендерер; добавить виджеты новых типов; ключ очередей → `field`.
**Приёмка:** «Замена SIM» заполняется на телефоне end-to-end (скан + число+норма + фото +
resolution); существующий чек-лист работает как прежде на новом движке.

**Отложено:** `table`/запчасти, write-back в мастер-объект, multichoice/подпись/гео,
мульти-фото на поле, настраиваемые резолюции.
