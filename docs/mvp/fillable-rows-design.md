# Строки табличных полей — предмет строки (дизайн)

> Продолжение [fillable-tasks-design.md](fillable-tasks-design.md): раскрываем тип поля
> `table`, который в первом слайсе был отложен (решение 5). Закрывает roadmap 29
> (строки неоткуда взять) и «итоги по колонкам» из черновиков движка чек-листов.
> Статус: **отложено на подумать 2026-08-06**, не реализовано. Ветка `mvp_tasks`.
> Нерешённое — в разделе 12, там же вопрос, от которого зависит первый шаг работ.

## 1. Идея

Таблица — это не «товарная часть». Это **список предметов с замерами**: строка говорит,
о чём она (предмет), колонки — что по нему померили. Товар — лишь один вид предмета.

Сегодня предмета в модели нет вообще: `FillRow` — это `filling + tableField + index`
и ячейки. Отсюда и тупик: строку неоткуда взять, потому что непонятно, чем она является.

Ядро не должно знать слов «товар», «остаток», «цена», «штука». Слово «номенклатура»
в `storeTasks/` не должно встречаться ни разу — это забота хоста (ERP, MITE), как уже
устроено с `CheckObject`.

## 2. Какие бывают предметы

| Предмет | Кейс | Колонки | Хост |
|---|---|---|---|
| Товар / SKU | пересчёт, ценники, изъятие просрочки, некачественная рыба (Санта) | факт, система, цена, сумма | ERP |
| Прибор / оборудование | обход, снятие показаний, состояние узлов | показание, состояние, дата поверки | MITE |
| Зона / камера / витрина | температурный лист, обход помещений | температура, чистота, отметка | любой |
| Сотрудник | форма, бейдж, медкнижка на смене | набор булевых | ERP |
| Документ / чек | выборочная проверка кассовых операций | сумма, соответствие | ERP |
| Свободная строка | нарушение, замечание, «прочее» | текст + оценка | нет справочника |
| Без предмета | пять замеров подряд, строка = просто номер | любые | — |

Отдельный случай: **один справочник в двух ролях**. В MITE прибор — объект задачи;
в обходе «задача на магазин, строки — холодильники этого магазина» тот же прибор
становится предметом строки. Поэтому предмет — не `CheckObject`, а своя абстракция,
хотя конкретные классы могут совпадать.

## 3. Три оси

Универсальность упирается не в «товар или не товар», а в три независимых вопроса.
Каждый — своя точка расширения; сегодня закрыт только вариант «ничем/ничего».

| Ось | Варианты | Механизм |
|---|---|---|
| **A. Чем строка идентифицируется** | ничем (индекс) · свободным текстом · ссылкой в справочник | абстрактный класс `RowSubject` |
| **B. Откуда берётся список** | задан шаблоном · приезжает от хоста при старте · добавляет исполнитель · скан ШК | `rowSource` + абстрактное `fillRows` |
| **C. Что с результатом** | ничего · write-back в ERP/MITE · итоги в акт | finish-хук (roadmap 27) |

## 4. Модель

```
Field (type=table) ──1..*──► Column               (конфиг колонок — есть)
   │  subjectKind, rowSource, allowManual,
   │  allowFreeSubject, uniqueSubject
   │
Filling ──1..*──► FillRow ──► RowSubject «abstract» ◄── Sku      (ERP)
                    │  rowKey (uuid клиента)      ◄── Device   (MITE)
                    │  subjectName (снимок)       ◄── CheckAsset
                    └──► ячейки на (FillRow, Column) — есть
```

Абстракция ровно того же вида, что уже работает с `CheckObject`:

```lsf
// fillable/RowSubject.lsf
CLASS ABSTRACT RowSubject 'Предмет строки';
id '{ID}' = ABSTRACT ISTRING[50] (RowSubject) CHARWIDTH 15;
name '{Name}' = ABSTRACT ISTRING[150] (RowSubject) CHARWIDTH 25;
// канал: 'sku', 'device', 'employee' — шаблон просит канал, хост его отдаёт
kind = ABSTRACT STRING[30] (RowSubject);
// доступен ли предмет на этом объекте: в ERP — номенклатура магазина, в MITE — приборы объекта.
// ВАЖНО: это подсказка для поиска, а НЕ запрет — см. раздел 12, вопрос 5
available = ABSTRACT BOOLEAN (RowSubject, CheckObject);
// поиск по штрихкоду/серийнику: одна точка — и скан работает во всех каналах
subjectByCode = ABSTRACT RowSubject (ISTRING[50]);
```

Хост подключается, не трогая ядро — `EXTEND CLASS` умеет добавить родителя уже
существующему классу:

```lsf
EXTEND CLASS Sku : RowSubject;
kind (Sku s) += 'sku';
available (Sku s, CheckObject o) += TRUE IF stock(s, o);
```

Строка получает и ссылку, и имя. Свободное имя обязательно: без него «прочее нарушение»
и товар не из списка не вносятся, а это ровно те кейсы, ради которых пересчёт и делают.

```lsf
subject = DATA RowSubject (FillRow);
subjectName 'Предмет' = DATA ISTRING[150] (FillRow);
name 'Предмет' (FillRow r) = OVERRIDE subjectName(r), name(subject(r));
```

**Снимок важнее живой ссылки** (порядок в `OVERRIDE` не случаен): `subjectName`
заполняется при создании строки. Заполнение — документ, а не отчёт: переименование или
удаление товара не должно менять акт задним числом. Тот же довод, что в roadmap 20 про
версионирование шаблонов, только дешевле.

## 5. Конфигурация поля

Всё настройкой шаблона, не кодом — новый клиент правится данными.

| Свойство `Field` | Смысл |
|---|---|
| `subjectKind` | канал справочника: `sku` / `device` / … · пусто = строки без предмета |
| `rowSource` | `none` · `template` (заготовки в шаблоне) · `host` (`fillRows`) |
| `allowManual` | исполнитель может добавить строку |
| `allowFreeSubject` | можно ввести предмет текстом, не выбирая из справочника |
| `uniqueSubject` | запретить две строки на один предмет |

`uniqueSubject` — именно настройка, а не жёсткое правило: для пересчёта две строки на
один товар = двойной учёт, а для «товаров с истёкшим сроком» один товар с двумя разными
сроками — норма.

Для `rowSource = template` нужен класс заготовок `TemplateRow (Field)` — пять холодильных
камер, пять зон допекания: список известен заранее и одинаков для всех проверок.

## 6. Точки расширения

```lsf
fillRows ABSTRACT LIST (Filling, Field);   // хост кладёт остатки магазина / приборы объекта
```

Вызов — из `startExecution` после создания `Filling`, по всем табличным полям шаблона.
Реализация хоста фильтрует по `checkObject(task(f))`: остатки именно этого магазина.

Вычисляемые колонки (`кол-во × цена`, `факт − система`) — **не мини-язык формул**,
а `ABSTRACT CASE` по образцу оценки чек-листов (`ScoreByNorm`/`ScoreByOption`/…):
`calcKind` на колонке + модуль-плагин на каждую арифметику. Новая арифметика = новый
модуль, ядро не меняется.

```lsf
calcCell = ABSTRACT CASE NUMERIC[18,4] (FillRow, Column);
cellValue (FillRow r, Column c) = OVERRIDE cellNumber(r, c), calcCell(r, c);
columnTotal (Filling e, Column c) = GROUP SUM cellValue(FillRow r, c) IF filling(r) = e;
```

Итог по колонке закрывает шапку акта Санты («изъято, кг» и «на сумму, руб.»).

**Операнд бывает двух видов, и второй обязателен** (решено 2026-08-11). Колонка этой же
строки — это «количество × цена», где оба множителя в строке. Но «расход × тариф» так не
выражается: тариф один на всю таблицу, и колонка, повторяющая одно число в каждой строке,
— это не модель, а костыль. Поэтому операнд — либо код колонки, либо **константа из
настройки самой колонки**. Без второго вида половина реальных расчётов не описывается.

**Оговорка, без которой формулировка «новая арифметика = новый модуль» вводит в
заблуждение.** Она верна только для сервера. Телефон обязан показать стоимость сразу
после ввода количества — офлайн, без запроса, — значит ту же арифметику считает и он.
Набор `calcKind` это **контракт с приложением**: каждый новый вид требует релиза клиента,
а не только модуля на сервере. Отсюда же и главный довод против мини-языка формул: его
пришлось бы интерпретировать дважды, и две реализации одной семантики разойдутся. С
фиксированным набором обе стороны пишут один и тот же `CASE` из нескольких веток.

### Показания приборов: операнд из прошлой проверки

Отдельный случай, который не сводится к арифметике внутри строки. Расход = текущее
показание − предыдущее, и только потом × тариф. Предыдущее лежит не в соседней колонке, а
в прошлом заполнении.

Подпись `calcCell(FillRow, Column)` это выдерживает: от строки модуль доходит до
заполнения, задачи, объекта и предмета, а оттуда — до прошлой проверки по тому же объекту
и шаблону (тот же `GROUP LAST`, что в #36718). Менять модель не нужно.

Но появляется жёсткое условие: **у строки обязан быть предмет-ссылка** — конкретный
счётчик. Иначе сопоставить строки двух проверок нечем, и «предыдущее» не найти: индекс
строки для этого не годится, порядок между проверками не гарантирован. То есть для
показаний ось A («чем строка идентифицируется») перестаёт быть опциональной, хотя для
пересчёта и ценников она опциональна.

Если счётчик **один**, таблица не нужна вовсе: это числовое поле, и прошлое значение к
нему приезжает механизмом #36718 / #36778. Таблица — когда счётчиков несколько.

## 7. Ключ строки и офлайн

Сейчас строка адресуется индексом (`rowByIndex` в `api/FillApi.lsf:22`). Как только
строки можно добавлять и удалять — тем более офлайн — индекс поедет: клиент создал две
строки в самолёте, синхронизировался дважды, получил дубли или запись не в ту строку.

Ключ генерирует клиент (uuid), сервер принимает его как идентичность. Уникальность —
существующей идиомой проекта (`column = GROUP AGGR Column c BY tableField(c), code(c)`):

```lsf
rowKey = DATA STRING[36] (FillRow);
row = GROUP AGGR FillRow r BY filling(r), rowKey(r);
```

Отсюда два следствия, оба нужные:
1. **`apiAddRow` идемпотентно** — повтор с тем же ключом не создаёт вторую строку,
   поэтому ретрай офлайн-очереди безопасен.
2. **`apiSetCell` по неизвестному ключу создаёт строку** (если поле разрешает ручное
   добавление). Тогда очередь операций не зависит от порядка: `setCell` может доехать
   раньше `addRow`. Если ручное добавление запрещено — по-прежнему `Row not found`,
   иначе опечатка в ключе молча плодит строки.

## 8. API

| Метод | Тело / параметры | Назначение |
|---|---|---|
| `POST apiAddRow` | `{id, field, rowKey, subjectId?, subjectName?}` | добавить строку, идемпотентно по `rowKey` |
| `POST apiDeleteRow` | `{id, field, rowKey}` | удалить строку |
| `POST apiSetCell` | `{id, field, rowKey, column, …}` | ключ вместо индекса; upsert по п. 7 |
| `GET apiRowSubjects` | `?id=&field=&query=&all=` | кандидаты канала: по умолчанию доступные на объекте, при `all` — весь справочник |
| `GET apiExecutionRows` | `?id=` | добавить `rowKey`, `subjectId`, `subject`, итоги |

Клиент один и наш, поэтому индексную адресацию не тащим для совместимости — переводим
на `rowKey` целиком.

## 9. Клиент

Таблица получает: имя предмета строкой-заголовком, «Добавить позицию» (поиск по каналу +
скан ШК + свободный ввод, если разрешён), удаление свайпом, итоги по колонкам внизу.
`rowKey` — uuid, сгенерированный на телефоне; очередь операций та же, что для полей.

Отдельно чинится сегодняшнее: `fill_field_tile.dart` рисует подписью всё, что не `number`,
независимо от `readonly`, — текстовые колонки не набрать. Read-only «В системе» при этом
задумана: системный остаток сверяют, а не правят.

## 10. Чего сознательно не делаем

- **Оценку по таблице (решено 2026-08-11).** Табличное поле остаётся «отвечено / не
  отвечено» (`tableAnswered`), в `totalScore` и процент проверки не входит, `scoreable`
  для него не включается. Балл пришлось бы выводить из числа расхождений или из итога
  колонки — величин, которые в разных шаблонах значат разное, и один и тот же пересчёт
  давал бы разный процент в зависимости от настройки. Понадобится — отдельной задачей и с
  явным правилом.
- Мини-язык формул в колонках — только набор арифметик модулями.
- Товарные атрибуты (`quantity`, `price`, `barcode`) в классах ядра. Сверка «факт против
  системы» уже выражается существующим `compareTo` на колонке — и это хороший признак,
  что модель верная.
- Версионирование справочника предметов — снимок имени в строке решает 90% за 0 усилий.
- Историю изменений строк.

## 11. Порядок работ

Разложено на две задачи 2026-08-11, обе заведены в Redmine без исполнителя:
[#36779](http://support.luxsoft.by/issues/36779) и
[#36780](http://support.luxsoft.by/issues/36780). Порядок против
первоначального: вычисляемые колонки идут вторыми, а не третьими, потому что они не
зависят от источника строк — стоимость считается одинаково, что строку добавил человек,
что положил хост.

**Задача 1** (#36779) — строки заполняются и считаются:

1. `RowSubject` + `SubjectItem` + `subjectName` + `rowKey` +
   `apiAddRow`/`apiDeleteRow`/upsert `apiSetCell`, ручной ввод в клиенте. Без этого не
   заполняется ничего.
2. `rowSource` с вариантами `none` / `template` и класс заготовок `TemplateRow`.
   Заготовки от хоста не зависят — их заводит администратор в конструкторе, и работают
   они там же, где ручной ввод, поэтому здесь, а не во второй задаче.
3. Вычисляемые колонки и итоги (закрывает шапку акта), включая разность с прошлой
   проверкой для показаний.

**Задача 2** (#36780) — строки приезжают от хоста: третий вариант `rowSource = host`,
`fillRows`, `apiRowSubjects`, скан по `subjectByCode`.

Обе правят пересекающиеся файлы (`FillRow`, `Column`, `FillApi`, `fill_field_tile`),
поэтому параллельно их вести нельзя — только подряд и лучше одним исполнителем.

**Write-back** отдельной задачей не выделяется: это одна из реализаций на точке
«проведения» задачи (`onProceed`), см. тикет 10 в `_redmine-drafts-next-10.md` и
переосмысленный roadmap 27.

## 12. Открытые вопросы

1. **Справочник предметов в standalone — РЕШЕНО 2026-08-11: нужен, и он не альтернатива
   абстракции, а вторая её реализация.** Номенклатура бывает двух происхождений:
   абстрактная (хост подключает своё — `Sku` в ERP, `Device` в MITE) либо пользовательская
   (справочник ведёт сам заказчик в бэк-офисе). Второе едет в артефакте тонким
   `SubjectItem : RowSubject` — ровно тем же приёмом, что `CheckAsset` для `CheckObject`.
   Оба канала сосуществуют: какой брать, решает `subjectKind` в шаблоне. Свободного текста
   при этом не отменяет — он третий, самый дешёвый вариант, и остаётся всегда.
   Следствие: пересчёт показывается на стенде без всякого ERP.
2. **Канал строкой или классом.** Строка (`'sku'`) настраивается в шаблоне и матчится
   хостом через `+=`; ссылка на класс в ядре недоступна. Предлагается строка.
3. **`rowSource = template`** — делать сразу или после `host`? Санте нужен `manual`
   (её таблицы заполняются по факту), температурному листу — `template`.
4. **Единицы и точность.** `cellNumber` сейчас `NUMERIC[14,3]`. Килограммы рыбы и суммы
   в рублях помещаются, штуки тоже; проверить на ценах с 4 знаками у ERP.

5. **`available` — подсказка, а не фильтр.** Самая ценная находка при пересчёте — товар,
   которого в остатках магазина быть не должно; если поиск жёстко ограничен доступными,
   её физически не внести. То же в MITE: прибор, стоящий не там, где числится, — это и
   есть повод для задачи. Поэтому поиск двухэшелонный (см. `apiRowSubjects`), а строка,
   найденная за пределами доступного, помечается внесистемной. **Не превращать
   `available` в запрет** — самая вероятная ошибка реализации этого дизайна.

6. **Свободный текст — это долг, а не решение.** Он обязателен, иначе исполнитель
   встанет, но строка со свободным именем не агрегируется по сети. У Санты
   «некачественная рыба» — конкретный товар, и если проверяющие набьют его руками,
   месячный свод по нарушениям не соберётся ни за один месяц. Значит несопоставленные
   строки надо помечать и давать бэк-офису сматчить их со справочником постфактум.
   Иначе универсальность куплена ценой отчётности — а отчётность у Санты и есть продукт.
   В модели раздела 4 этого пока нет.

7. **Иерархия предметов — решено: не делаем.** Для MITE напрашивается «строка = узел
   прибора», а узлы дерево. Дерево остаётся у хоста: `RowSubject` плоский (id + имя),
   ядро дерево не рисует и не агрегирует.

8. **Пересчёт — сверка или слепой подсчёт?** Вопрос заказчику, от него зависит
   `rowSource` по умолчанию и весь экран. Сверка → строки обязаны приезжать от хоста,
   иначе не с чем сравнивать, ручное добавление только под находки. Слепой подсчёт →
   исполнитель набирает список с нуля, системный остаток подставляется при разборе.
   Это два разных экрана и два разных первых шага работ.
