# Черновики задач в Redmine — универсальность движка чек-листов

> ⚠ СТАТУС 2026-08-05: **ядро механики реализовано и проверено на живом сервере**, в
> Redmine эти пять задач не заводились. Реализовано: точка расширения, тип `score`,
> булево поле, шкала вердиктов, дефект 28. Не сделано: мобильный рендер и два
> отложенных тикета (итоги таблиц, роли объекта) — их и стоит завести.
>
> Три утверждения ниже реализация ОПРОВЕРГЛА, читать с поправкой:
> 1. «Объявлять явно `EXCLUSIVE`» — **неверно**. `EXCLUSIVE` проверяет взаимоисключаемость
>    по классам параметров, а не по условиям `WHEN`. Все правила имеют одну сигнатуру
>    `(Field)` и различаются значением `type(f)`, поэтому `EXCLUSIVE` валит старт с
>    `signature intersection of property`. Нужен обычный `CASE` (= `OVERRIDE FIRST`),
>    «одно правило на тип» остаётся соглашением.
> 2. Реализация абстрактного свойства над `(Filling, Field)` обязана связать **оба**
>    параметра в условии: `WHEN e IS Filling AND type(f) = ...`. Иначе сигнатура не
>    сходится (подсказал пользователь).
> 3. Значение абстрактного объявлено `NUMERIC[18,4]`, а не `[8,2]`: реализация должна
>    помещаться в класс абстрактного свойства, неявного приведения нет, а
>    `score(Option)[10,2] * weight[8,2]` даёт `[18,4]`.
>
> Проект: `retail-help-desk` (id 221) · трекер «Изменение» (id 2).
> Дата: 2026-08-05. Ветка: `mvp_tasks`.

Восемь тикетов. Пять — про механику движка (это и есть «универсальность»), один
клиентский, два — про полноту кейса, их можно отложить.

## Откуда требования

Разбор реального чек-листа клиента «Санта» — `D:\clients\santa\Tasks\92 чек лист

  некачественная рыба в кг), их итоги подставляются в шапку акта.
- Справочник: 279 магазинов, 8 форматов и **девять ролевых ФИО на каждый** —
  операционный руководитель, региональный менеджер, технолог, товародвижение, СОФ,
  мерчендайзинг, обслуживание, менеджер по персоналу, заведующий.

## Во что это упирается в коде

Ровно в две зашитые строки в `fillable/Filling.lsf`:

```
itemScore = IF type(f) = FieldType.number
                THEN (IF inNorm(e, f) THEN weight(f) ELSE 0)
                ELSE score(optionValue(e, f)) * weight(f);
scored (Field f) = scoreable(f) AND (type(f) = FieldType.scale OR type(f) = FieldType.number);
```

Способ начисления балла зашит `IF`-ом по типу поля, а перечень оцениваемых типов —
списком из двух. Поддержаны ровно две механики: «попал в диапазон нормы → полный вес»
и «очки варианта × вес». Санте нужна третья — «введённое значение и есть балл,
максимум = норма пункта», и любая новая механика сегодня означает правку ядра.

## Решение по архитектуре (2026-08-05)

Начисление балла выносится в **абстрактную точку расширения**, каждая механика —
отдельный модуль-плагин. Ровно как «тип задачи = плагин» в остальном проекте; приём
уже применяется — `readonly = ABSTRACT CASE BOOLEAN (Task)` в `task/StoreTaskCore.lsf:15`,
`startExecution ABSTRACT LIST (Task)` с реализацией в `fillable/FormTask.lsf:36`.

Важно не перепутать две вещи: **абстрактное — не вместо типа поля, а вместо
`IF`-цепочки**. Тип `score` всё равно нужен, он задаёт что пользователь видит и вводит.
Оси ортогональные: тип — про ввод и валидацию, абстрактное — про то, где живёт правило
начисления.

И граница применимости: абстрактное там, где различие в **коде** (арифметика начисления);
справочник там, где различие в **настройке клиента** (пять градаций вердикта — это
данные, которые заказчик правит сам, а не модуль, который пишет разработчик).

# ЯДРО МЕХАНИКИ

## [Чек-листы] Начисление балла — вынести в абстрактную точку расширения

**Цель.** Убрать из ядра `IF`-цепочку по типу поля, чтобы новая механика оценки
добавлялась модулем, а не правкой `Filling.lsf`. Задача поведение не меняет — это
подготовка почвы, после которой всё остальное в блоке становится дешёвым.

**Состав.**
- Два абстрактных свойства вместо зашитой арифметики (эскиз, синтаксис уточнить по
  документации при реализации):

```
fieldMax  = ABSTRACT CASE EXCLUSIVE NUMERIC[8,2] (Field);           // максимум пункта
itemValue = ABSTRACT CASE EXCLUSIVE NUMERIC[8,2] (Filling, Field);  // набранный балл

scored (Field f) = scoreable(f) AND fieldMax(f) > 0;
itemScore (Filling e, Field f) = itemValue(e, f) IF scored(f) AND answered(e, f) AND NOT notApplicable(e, f);
itemMax   (Filling e, Field f) = fieldMax(f)     IF scored(f) AND answered(e, f) AND NOT notApplicable(e, f);
```

- Существующие две механики переезжают в отдельные модули без изменения смысла:
  `ScoreByNorm` — `WHEN type(f) = FieldType.number THEN (IF inNorm(e,f) THEN weight(f) ELSE 0)`;
  `ScoreByOption` — `WHEN type(f) = FieldType.scale THEN score(optionValue(e,f)) * weight(f)`.
- Диспетчеризация здесь **по значению** `type(f)`, а не по классу: `Field` — один класс,
  тип лежит в нём атрибутом. Поэтому `MULTI` (полиморфизм по сигнатуре) не подходит,
  нужен `CASE` с явным условием в реализации.
- ⚠ У `CASE` по умолчанию `OVERRIDE FIRST`: несколько реализаций могут сработать
  одновременно, и молча победит загруженная последней. Для правила начисления это
  недопустимо — два модуля на один тип поля должны быть ошибкой, а не гонкой по порядку
  модулей. Объявлять явно `EXCLUSIVE`.
- Ключевое слово `FULL` здесь не поможет: оно проверяет полноту по наследникам классов
  аргументов, а у нас диспетчеризация по значению атрибута. Полнота выражается через
  `fieldMax`: нет правила — нет максимума — поле просто не участвует в оценке. Это
  безопасный отказ, а не молчаливый ноль в знаменателе.
- Побочная выгода, ради которой это и делается: `scored` перестаёт быть списком «scale
  или number» и начинает означать «для поля есть правило начисления». И `itemMax`
  избавляется от ложной зависимости от `Filling` — максимум пункта от заполнения не
  зависит, там сейчас только гейт «отвечено / не применимо».

**Готово когда.** В `Filling.lsf` нет ни одного `IF` по `FieldType`. Существующие
чек-листы считаются ровно как раньше — проверяется на демо-наборе: проценты 88.89 /
58.82 / 64.29 и критический провал воспроизводятся до цифры (это те же значения, по
которым сверяли миграцию на единый движок).

**Зависит от.** Ничего. Блокирует остальные тикеты блока.

**Подсказки.** `fillable/Filling.lsf:34-59` (весь блок scoring), `fillable/Field.lsf:37-43`
(вес и `scored`). Синтаксис реализации: `prop(params) += WHEN условие THEN выражение;` —
для `CASE` блок `WHEN ... THEN` обязателен.

**Оценка.** M.

## [Чек-листы] Тип поля `score` — оценка «N из максимума» с настраиваемым шагом

**Цель.** Дать механику, которой нет: проверяющий ставит пункту балл от 0 до максимума,
и этот балл идёт в оценку как есть. Это самый распространённый формат бумажного
чек-листа, и именно на нём построен весь бланк Санты.

**Состав.**
- Новый `FieldType.score` «Оценка» + стабильный код `'score'` для API.
- Модуль-плагин `ScoreByValue`: `fieldMax += WHEN type(f) = FieldType.score THEN weight(f)`,
  `itemValue += WHEN type(f) = FieldType.score THEN numberValue(e, f)`. То есть вес поля
  выступает максимумом — это и есть «норма» в терминах клиента.
- Шаг ввода настройкой на поле (`step`), Санте нужен 0.5. Валидация: значение в
  диапазоне 0..максимум и кратно шагу.
- ⚠ Терминологическая ловушка, из-за которой легко сделать неправильно: у Санты
  «Норма» — это **максимальный балл пункта**, а у нас `minNorm`/`maxNorm` — **диапазон
  допустимых значений** измерения. Это разные вещи с одинаковым названием. У score-поля
  `minNorm`/`maxNorm` не используются вообще.
- В конструкторе шаблона поля `minNorm`/`maxNorm`/`step`/`optionSet` показывать по
  релевантности типа, иначе форма превращается в набор граф, из которых в каждом
  сценарии работают две.

**Готово когда.** Шаблон с score-полями считает сумму баллов и процент; поле с
максимумом 7 принимает 6.5 и не принимает 7.5 или 6.3; чек-лист Санты «РЫБА»
заводится штатным конструктором и даёт на разобранной проверке те же 70.5 балла.

**Зависит от.** Абстрактная точка расширения.

**Оценка.** M.

## [Чек-листы] Оцениваемое булево поле: отмечено → полный вес

**Цель.** Сейчас булево поле не может участвовать в оценке вообще (`scored` — только
scale и number). Между тем «сделано / не сделано» на N баллов — самый простой и частый
пункт чек-листа; второй бланк Санты («Зона допекания», 5 пунктов на 10/25/15/25/25)
выглядит именно так.

**Состав.** Модуль-плагин `ScoreByFlag`: максимум = вес, балл = вес при отмеченном
поле и 0 при неотмеченном. Ядро не трогается — это и есть проверка, что точка
расширения настоящая: третий плагин пишется за час и не требует ничьего разрешения.

**Готово когда.** Булево поле с включённым «Учитывать в оценке» даёт свой вес в итог;
шаблон только из булевых полей считает корректный процент.

**Зависит от.** Абстрактная точка расширения.

**Оценка.** S.

## [Чек-листы] Шкала вердиктов справочником вместо одного порога

**Цель.** Вердикт сейчас бинарный: один порог `passThreshold`, `passed`, и
`nameVerdict` = «Пройдено» / «Не пройдено». Клиенту нужно пять градаций, причём у
второго чек-листа того же клиента — своя шкала из четырёх с другими границами. Это
данные, а не код: заказчик правит их сам.

**Состав.**
- Справочник: шкала оценок + её уровни (граница в процентах, название, цвет, флаг
  «считается пройденным»). Шаблон ссылается на шкалу.
- Уровни задавать **в процентах, а не в баллах**. У Санты максимум ровно 100 и одно
  совпадает с другим один в один, но шаблон с максимумом 60 или 250 на процентной шкале
  заработает без переделки.
- Текущее поведение становится частным случаем — шкала из двух уровней. `passed`
  сохраняется и продолжает работать: на нём висит #36473 («все выполнения успешны →
  задача Выполнено») и `resultSummary`.
- Миграция существующих шаблонов: `passThreshold` разворачивается в двухуровневую
  шкалу автоматически, вручную ничего перезаводить не нужно.
- Цвет уровня отдать в API — мобильный клиент и печатная форма покажут градацию, а не
  «пройдено/нет».

**Готово когда.** Шаблон со шкалой из пяти уровней показывает «Удовлетворительно» на
70.5 балла; шаблон без явной шкалы ведёт себя ровно как сегодня; `passed` не сломан.

**Зависит от.** Ничего (можно параллельно с точкой расширения).

**Подсказки.** `fillable/Filling.lsf:62-65` (`threshold`, `passed`, `nameVerdict`),
`passThreshold` — в `fillable/Template.lsf`.

**Оценка.** M.

## [Чек-листы] Дефект: number-поле без норм всегда считается несоответствием

**Цель.** `nonconformity` для number-поля = `numberValue AND NOT inNorm`, а
`inNorm = value >= minNorm AND value <= maxNorm`. При незаданных нормах `inNorm` = NULL,
`NOT NULL` = TRUE → любое введённое значение помечается несоответствием. В мобильном
клиенте оно краснеет, а при включённых `requirePhoto`/`requireComment` ещё и блокирует
завершение. По той же причине не работает односторонняя норма (задан только `minNorm`
или только `maxNorm`).

**Состав.** Обусловить числовую ветку наличием хотя бы одной границы; сравнения
развести, чтобы односторонняя норма работала; проверить `cellInNorm(FillRow, Column)` —
там та же форма записи; учесть влияние на `itemScore` (scoreable number без норм сейчас
даёт 0 баллов).

**Готово когда.** Заполненное number-поле без норм не помечается несоответствием;
поле только с верхней границей корректно ловит превышение.

**Зависит от.** Ничего, но дешевле сразу после точки расширения — правится тот же код.
Это тикет 28 из `roadmap.md`, в Redmine до сих пор не заводился.

**Подсказки.** `fillable/Filling.lsf:34-37`, `fillable/FillRow.lsf`.

**Оценка.** S.

## [Справочники] Роли на объекте проверки

**Цель.** У `CheckObject` сегодня только название и адрес. Санте нужны формат торгового
объекта и девять ролевых ФИО на каждый из 279 магазинов; в бланке они подставляются в
шапку через `VLOOKUP`, а по факту это ответственные, которым потом уходит результат
проверки.

**Состав.** Не девять свойств, а справочник ролей плюс связь «объект + роль → человек»:
следующему клиенту понадобятся свои пять ролей, и код меняться не должен. Формат
объекта — отдельным атрибутом (у Санты 8 значений: 400, 600, 200, 1000, Кэш, Мини,
1500, Фиш), он же пригодится как признак, по которому различаются шаблоны проверок.
Роли объекта показывать в шапке заполнения и отдавать в API.

**Готово когда.** У объекта проверки настраивается произвольный набор ролей с
ответственными; шапка акта заполняется ими автоматически; добавление новой роли не
требует правки кода.

**Зависит от.** Ничего. Пересекается с задачей про координаты `CheckObject` (#36682) —
обе расширяют один класс, разумно делать подряд.

**Оценка.** M.

# Порядок работ

Первой — **точка расширения**: она поведение не меняет, но после неё три следующих
тикета становятся дешёвыми, а без неё каждый из них снова правит ядро. Сразу за ней —
**дефект 28**, пока правится тот же код.

Дальше **тип `score`** и параллельно **шкала вердиктов** (они друг от друга не зависят),
затем **булево поле** как проверка, что расширение настоящее. Клиентский рендер — после
обоих серверных, иначе нечего показывать.

**Итоги таблиц** и **роли объекта** — отдельным заходом, к моменту, когда понадобится
печатная форма акта и рассылка результата.

Итого по ядру примерно неделя, с клиентом — полторы.

Не входит в этот блок и остаётся в `roadmap.md`: печатная форма акта (тикет 10),
рейтинг и динамика объектов (тикет 9), эскалация результата по градации — «до 84 баллов
комментарии магазина операционному руководителю, ниже 70 — региональный менеджер
замдиректора и в СВК, срок 3 дня». Последнее ложится на finish-хук (тикет 27) и
уведомления (тикет 15), отдельной механики не требует.
