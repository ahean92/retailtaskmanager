# Сценарии пользовательского тестирования

> Ручная приёмка подсистемы «Задачи для магазинов»: бэк-офис lsFusion + мобильный клиент
> «Пульс». Написано по состоянию `origin/master` (`6a18a1d3`, 2026-08-26).
> Стенд ни разу не проходил сквозную проверку целиком — это первый полный прогон.

---

## 0. Как этим пользоваться

**Кто что делает.** Первичные данные — стенд, справочники, шаблоны, роли, учётки, задачи
в нужных состояниях, история проверок, уведомления — **заполняет Claude** скриптами и через
API: это весь раздел 1 и всё, что в сценарии стоит в строке *предусловия*. **Человек делает
только пользовательские действия** — то, что в строке *шаги*: клики в бэк-офисе и работа в
приложении. Если для сценария не хватает данных, это не задача тестировщика — вернуть
сценарий на подготовку.

**Формат сценария.** У каждого — *предусловия* (что Claude готовит в базе до начала),
*шаги* (что делает человек) и *ожидаемо* (что он должен увидеть). Сценарий считается
пройденным, только если совпало **всё** ожидаемое, а не «в целом работает».

**Роли.** Сценарии написаны от лица четырёх людей — под каждого нужна своя учётная
запись, иначе половина проверок прав не проверяется:

| Обозначение | Кто | Роль (SID) | Что должно быть настроено |
|---|---|---|---|
| **АДМ** | администратор системы | `systemAdmin` | все права |
| **СУП** | супервайзер / руководитель | `supervisor` | «Видеть все задачи», «Назначать исполнителя», «Закрывать чужую задачу», «Видеть журнал координат» |
| **ПРВ** | проверяющий (полевой) | `inspector` / `executor` | обычный исполнитель, геопривязка обязательна |
| **ЗАВ** | заведующий магазином | `storeManager` | исполнитель, привязан к своим объектам |
| **ИНТ** | учётка внешней системы | своя роль | «Разрешить импорт показателей извне» |

**Обозначения.**
`[Б]` — бэк-офис (веб-клиент lsFusion), `[М]` — мобильное приложение,
`[API]` — проверка ручкой HTTP (когда глазами результат не виден).
`(вне master)` — функциональность есть только в локальном рабочем дереве, в `master` её
пока нет; такие сценарии прогонять, только если модуль подключён.

**Навигатор бэк-офиса** — папка **«Управление персоналом»**: «Операции», «Справочники»,
«Отчёты», «Настройка».

**Дефекты** заводить в Redmine, проект `retail-help-desk`
(http://support.luxsoft.by/projects/retail-help-desk/issues), в теле — номер сценария,
шаг, что ожидали, что получили, скриншот. Форма протокола — раздел D.

## 1. Подготовка стенда — выполняет Claude

Весь раздел закрывается до того, как человек садится за прогон: сервер, данные, учётки,
каналы. Человеку остаётся убедиться, что «ожидаемо» выполнено, и начинать с блока A.

### П1. Сервер поднят и API живой
- *Шаги:* поднять сервер (`lsfdev.ps1 start -ProjectDir D:\dev\lsf\retailtaskmanager`);
  открыть `http://localhost:9080/`; выполнить
  `curl -s "http://localhost:9080/exec/StoreTask.apiStatuses"`.
- *Ожидаемо:* веб-клиент отдаёт форму входа; `apiStatuses` возвращает JSON-массив статусов.
- *Внимание:* «web up» в скрипте не означает, что стартовал сервер приложений — верить
  только ответу API; при пустом ответе смотреть `logs/stderr.log` на `ERROR StartLogger`.

### П2. Демо-данные засеяны
- *Шаги:* прогнать по очереди `scripts/testdata.lsf` (объекты, наборы вариантов, три
  шаблона, задачи всех типов), `scripts/homedemo.lsf` (главная страница, роли), при
  необходимости `scripts/ticket36835_demo.lsf` (подразделения), `ticket36842_demo.lsf`
  (фото проблемы), `ticket36872_demo.lsf` (поручения), `ticket36840_demo.lsf` (внешние
  приложения), `ticket36841_demo.lsf` (поле-ссылка):
  ```bash
  curl -u admin: -H "Content-Type: text/plain; charset=utf-8" --data-binary @scripts/testdata.lsf http://localhost:7671/eval/action
  ```
- *Ожидаемо:* ответ `OK`; в «Справочники → Объекты проверки» семь магазинов «Санта» с
  кодами и координатами; в «Шаблоны» — «Приёмка товара», «Пересчёт остатков», «Проверка
  ценников»; в «Задачи» — 9 задач, среди них просроченная и на сегодня.
- *Внимание:* HTTP 200 сам по себе ничего не доказывает — упавший APPLY тоже отдаёт 200.
  Проверять счётчики на формах.

### П3. Учётные записи и роли заведены
- *Шаги:* завести четыре учётки (АДМ/СУП/ПРВ/ЗАВ) и раздать им роли из таблицы выше;
  каждой (кроме АДМ) проставить связь с исполнителем; ЗАВ привязать к 1–2 объектам.
- *Ожидаемо:* `GET /exec/StoreTask.apiCurrentUser` под каждой из них отдаёт
  `{login,name,id,geoRequired}`; под учёткой без исполнителя — 403 `notPerformer`.

### П4. Приложение установлено и подключено
- *Шаги:* собрать APK (`flutter build apk --release`) либо взять готовый; установить на
  телефон в одной сети со стендом; на экране подключения указать `http://<LAN-IP>:9080`
  и нажать «Проверить подключение».
- *Ожидаемо:* проверка проходит, на экране входа появляются название и цвета заказчика.
- *Внимание:* без входящего правила брандмауэра на порт 9080 телефон не достучится.

### П5. Каналы уведомлений настроены (для блока A7/B11)
- *Шаги:* «Настройка → Настройки → Пуш (Firebase Cloud Messaging)» — загрузить JSON
  сервисного аккаунта, нажать «Проверить связь с Firebase»; в «Настройка → Каналы
  уведомлений» включить нужные события для каналов «Пуш» и «Почта»; в планировщике
  завести `processDeliveries` (10–15 с) и `processNotifications` (раз в сутки).
- *Ожидаемо:* «Связь есть. Проект: …»; если ни одно событие не включено — сообщение
  отдельно предупреждает об этом.

### Состояния данных под блоки A–C

Сценариям ниже нужны не просто справочники, а данные в определённом состоянии. Это тоже
готовит Claude — до прогона, а не по ходу.

**П6. История проверок для отчётов** — за последние шесть месяцев есть завершённые
заполнения по нескольким объектам и шаблонам, с разбросом процентов и вердиктов, с
критичным провалом хотя бы у одного и с повторяющимся несоответствием по одному пункту;
иначе A6.1–A6.5 нечего показывать.

**П7. Задачи во всех состояниях** — просроченная, со сроком сегодня, будущая, закрытая,
отменённая, частично заполненная (сценарий «продолжить»), назначенная на подразделение,
взятая коллегой, с фото проблемы, поручение с обязательным фото.

**П8. График с прошедшим и будущим периодом** — активное правило, по которому часть
периодов отработана (задачи созданы), а ближайший ещё впереди: календарь A4.4 должен
показывать и факт, и прогноз.

**П9. Уведомления и доставки** — в журнале есть прочитанные и непрочитанные записи,
доставка со временем отправки и доставка, исчерпавшая попытки: фильтр «Не доставлено»
(A7.5) не должен быть пустым.

**П10. Чистка после прогона** — Claude возвращает стенд в исходное состояние или
пересоздаёт данные заново, чтобы следующий прогон начинался с того же места.

## Блок A. Бэк-офис (lsFusion)

### A1. Справочники и оргструктура

**A1.1 Объект проверки** `[Б]`
- *Шаги:* «Справочники → Объекты проверки» → создать объект: код, название, адрес,
  широта/долгота, категория.
- *Ожидаемо:* объект сохраняется; без кода он не адресуем (не приедет в `objectId`), без
  координат не виден в `apiNearbyObjects` — проверить оба факта на созданном объекте
  через `GET /exec/StoreTask.apiNearbyObjects?lat=&lon=`.

**A1.2 Роли на объекте и ответственные** `[Б]`
- *Предусловия:* заведены роли «Заведующий», «Проверяющий» («Справочники → Роли на объекте»).
- *Шаги:* назначить на объекте ответственного по каждой роли.
- *Ожидаемо:* ответственные видны в карточке заполнения (блок «Ответственные»); роль в
  архиве из списков пропадает; порядок ролей — по полю «Порядок», новая роль встаёт в конец.

**A1.3 Подразделения** `[Б]`
- *Шаги:* «Справочники → Подразделения» → создать подразделение с кодом, вложить в него
  второе, включить в состав двух исполнителей.
- *Ожидаемо:* дубль кода отменяет сохранение с внятным сообщением; исполнитель, входящий
  в дочернее подразделение, считается входящим и в родительское.

**A1.4 Исполнители** `[Б]`
- *Шаги:* «Справочники → Исполнители» → проверить состав, снять активность у одного.
- *Ожидаемо:* архивный исполнитель не предлагается при назначении задачи и не приезжает
  в `apiPerformers`; у исполнителя с e-mail работает почтовый канал (A7.4).

**A1.5 Доступ к объектам** `[Б]` *(вне master)*
- *Шаги:* «Настройка → Доступ к объектам» → отметить ЗАВ два объекта.
- *Ожидаемо:* в приложении под ЗАВ выбор объекта на главной ограничен отмеченными
  (плюс те, где у него есть задача); исполнитель без единой отметки видит всё, как раньше.

### A2. Шаблоны бланков

**A2.1 Конструктор шаблона** `[Б]`
- *Шаги:* «Справочники → Шаблоны» → новый шаблон: код, название, порог прохождения;
  добавить два раздела и в них поля всех типов (`scale`, `choice`, `number`, `boolean`,
  `date`, `photo`, `longtext`, `scan`, `table`, `score`).
- *Ожидаемо:* поля сохраняются с кодами; порядок разделов и полей соблюдается; поле без
  кода сохранить нельзя (иначе клиент не сможет его адресовать).
- *Внимание:* коды полей не делать «словарными» английскими словами (`lines`, `name`) —
  проект реверс-транслейтит такие литералы, код станет локале-зависимым.

**A2.2 Наборы вариантов** `[Б]`
- *Шаги:* «Справочники → Наборы вариантов» → набор «Соответствие»: варианты с баллами,
  флагами «несоответствие» и «не применимо»; привязать к `scale`-полю.
- *Ожидаемо:* вариант из чужого набора в поле подставить нельзя (сообщение «Выбранный
  вариант не относится к набору поля»); «не применимо» исключает пункт из оценки.

**A2.3 Шкала оценок и порог** `[Б]`
- *Шаги:* «Справочники → Шкалы оценок» → уровни с диапазонами и цветами; привязать к шаблону.
- *Ожидаемо:* в заполнении вердикт и цвет соответствуют набранному проценту; при проценте
  ниже порога — «Не пройдено».

**A2.4 Табличное поле** `[Б]`
- *Шаги:* в шаблоне создать поле типа `table` с колонками «Товар» (text), «В системе»
  (number, только чтение), «Факт» (number, `compareTo` = системная колонка, обязательная);
  задать строки шаблона.
- *Ожидаемо:* строки сеются в заполнение; расхождение факта с планом подсвечивается;
  редактировать колонку «только чтение» нельзя.

**A2.5 Ограничения целостности** `[Б]`
- *Шаги:* попробовать привязать шаблон к небланочному типу задачи; сделать активным пресет
  с бланком и назначением «на другого».
- *Ожидаемо:* оба действия отклоняются сообщениями («Шаблон применим только к типам задач,
  выполняемым по бланку»; «Бланочный пресет назначается только „Себе“»).

### A3. Задачи

**A3.1 Создание задачи вручную** `[Б]`
- *Шаги:* «Операции → Задачи» → новая: тип «Проверка по бланку», объект, шаблон, срок,
  приоритет, исполнитель ПРВ; сохранить.
- *Ожидаемо:* присвоен номер `ST……`; автор — текущий пользователь; статус — первый
  допустимый для типа; дата начала — сегодня.

**A3.2 Статусы и их допустимость** `[Б]`
- *Шаги:* сменить статус задачи на недопустимый для её типа.
- *Ожидаемо:* сообщение «Статус недопустим для выбранного типа»; смена типа переводит
  задачу в первый статус нового типа.

**A3.3 Назначение на подразделение и взятие** `[Б]`
- *Предусловия:* A1.3; ПРВ входит в подразделение.
- *Шаги:* назначить задачу на подразделение; под ПРВ открыть её и нажать «Взять на себя»;
  затем «Снять».
- *Ожидаемо:* после взятия видно, кто и когда взял; снять может взявший или автор; на
  закрытой задаче пометка «кто брал» остаётся и не стирается.

**A3.4 Конфликт взятия** `[Б]`
- *Шаги:* двумя пользователями одновременно нажать «Взять на себя» на одной задаче пула.
- *Ожидаемо:* побеждает первый; второй получает «Задачу уже взял …» с временем, а не
  ошибку приложения; запись победителя не затирается.

**A3.5 Канбан-доска** `[Б]`
- *Шаги:* «Операции → Задачи» → вкладка канбана: перетащить карточку в другую колонку;
  применить фильтры справа; создать задачу из колонки.
- *Ожидаемо:* статус меняется по факту переноса; фильтры сужают доску; созданная из
  колонки задача открывается карточкой и уже имеет статус этой колонки.

**A3.6 Печать задачи** `[Б]`
- *Шаги:* в карточке задачи — печать; при наличии заполнения — печать акта проверки.
- *Ожидаемо:* формируется документ с номером, объектом, исполнителем, ответами по пунктам
  и координатами начала/завершения работы (если они есть).

**A3.7 Видимость задач по правам** `[Б]`
- *Шаги:* открыть «Задачи» под СУП (право «Видеть все задачи») и под ПРВ.
- *Ожидаемо:* СУП видит все; ПРВ — только те, где он участник (назначен с учётом
  иерархии либо автор); чужая задача не открывается и по прямой ссылке.

**A3.8 Переписка и файлы в карточке** `[Б]`
- *Шаги:* добавить комментарий с вложением; загрузить фото проблемы.
- *Ожидаемо:* сообщение появляется в ленте с автором и временем; вложение скачивается;
  на телефоне у участников загорается бейдж непрочитанного (см. B6.3).

### A4. График проверок

**A4.1 Правило авто-создания** `[Б]`
- *Шаги:* «Справочники → Правила авто-создания задач» → правило: шаблон, тип, категория
  объектов, дата начала, период (дней), «за N дней до срока», «срок выполнения», роль на
  объекте для назначения.
- *Ожидаемо:* период ≤ 0 и срок ≤ 0 отклоняются сообщением; правило сохраняется.

**A4.2 Генерация по одному правилу** `[Б]`
- *Шаги:* нажать «Сгенерировать» в карточке правила.
- *Ожидаемо:* по каждому объекту нужной категории создана задача с исполнителем по роли,
  сроком и ссылкой на правило; повторное нажатие ничего не задваивает.

**A4.3 Массовая генерация** `[Б]` `[API]`
- *Шаги:* Claude выполняет `generateAll` (вручную или через планировщик) — человек смотрит результат в списке задач.
- *Ожидаемо:* задачи созданы по всем активным правилам; правило в архиве пропущено; сбой
  на одном правиле не отменяет остальные.

**A4.4 Календарь «График проверок»** `[Б]`
- *Шаги:* «Операции → График проверок» → выбрать месяц, категорию, тип; кликнуть по
  заполненной ячейке, по ячейке с прогнозом и по ячейке с несколькими элементами.
- *Ожидаемо:* цвет ячейки отражает состояние; клик открывает задачу / правило / диалог
  со списком соответственно; пустая ячейка ничего не делает.

**A4.5 Происхождение задачи** `[Б]`
- *Шаги:* в списке задач включить фильтр «Авто-создана» / «Заведены вручную».
- *Ожидаемо:* колонка «График» и период заполнены только у сгенерированных; фильтры
  делят список без пересечений.

### A5. Заполнение и оценка

**A5.1 Заполнение бланка на форме** `[Б]`
- *Шаги:* открыть задачу с бланком → «Начать» → ответить на пункты разных типов.
- *Ожидаемо:* создаётся заполнение; ответы сохраняются; процент и вердикт пересчитываются
  (в т.ч. после переоткрытия формы).

**A5.2 Оценка, вердикт, критичный провал** `[Б]`
- *Шаги:* заполнить шаблон с известными весами так, чтобы получить ≥ порога, затем
  провалить критичный пункт.
- *Ожидаемо:* процент считается по весам; при провале критичного пункта вердикт —
  «Не пройдено» независимо от процента.

**A5.3 Нормы числовых полей** `[Б]`
- *Шаги:* ввести значение внутри нормы, вне нормы, и в поле с односторонней нормой
  (задан только минимум).
- *Ожидаемо:* вне нормы — несоответствие и подсветка; внутри — чисто; односторонняя норма
  работает как ограничение с одной стороны, а не помечает несоответствием любое значение.
- *Внимание:* исторический дефект — число без заданных норм помечалось несоответствием
  всегда; проверить отдельно.

**A5.4 Блокировка завершения** `[Б]`
- *Шаги:* попытаться завершить заполнение (а) с незаполненным обязательным полем,
  (б) без фото/комментария по несоответствию, (в) без исхода у шаблона, где он обязателен.
- *Ожидаемо:* три разных сообщения, завершения не происходит; после устранения — завершается.

**A5.5 Исход процедуры** `[Б]`
- *Шаги:* у шаблона с обязательным исходом выбрать исход и завершить.
- *Ожидаемо:* исход сохранён и виден в списке заполнений и в акте.

**A5.6 Корректирующие задачи из несоответствий** `[Б]`
- *Шаги:* в завершённом заполнении с несоответствиями нажать «Создать корректирующие задачи».
- *Ожидаемо:* по каждому несоответствию создана задача типа «Корректирующее действие» с
  названием «Устранить: …», объектом проверки, обязательным фото и перенесённым
  комментарием проверяющего; повторное нажатие дублей не создаёт.

**A5.7 Шапка заполнения** `[Б]`
- *Ожидаемо:* видны категория объекта и ответственные по ролям на этом объекте.

### A6. Отчёты

**A6.1 Свод баллов по объектам** `[Б]`
- *Шаги:* «Отчёты → Свод баллов по объектам» → задать период (по умолчанию — 6 месяцев),
  переключить помесячно/поквартально, включить «Скрыть без проверок».
- *Ожидаемо:* по каждому объекту средний балл и число проверок; колонки по периодам;
  итоги по периодам справа; объекты без проверок скрываются/показываются флагом.

**A6.2 Разрезы и переход в данные** `[Б]`
- *Шаги:* задать фильтр по шаблону, категории, исполнителю; вызвать из ячейки период
  контекстное меню и кнопку «Заполнения за диапазон».
- *Ожидаемо:* цифры пересчитываются под каждый фильтр; из ячейки открывается список
  заполнений именно этого объекта и периода; вердикт и цвет — по шкале выбранного шаблона.

**A6.3 Экспорт в XLSX** `[Б]`
- *Шаги:* «Экспорт в XLSX».
- *Ожидаемо:* файл открывается, состав колонок и подытоги совпадают с экраном.

**A6.4 Повторяющиеся несоответствия** `[Б]`
- *Шаги:* «Отчёты → Повторяющиеся несоответствия» → период, фильтры; открыть пункт с

- *Ожидаемо:* по каждому пункту — число проверок, несоответствий, доля и критичные;

**A6.5 Ведомость снятых баллов по пунктам** `[Б]`
- *Шаги:* вкладка ведомости в том же отчёте: посмотреть итоги по пунктам, открыть данные

- *Ожидаемо:* снятые баллы по пунктам с весами (без «нулевых» строк-пустышек); переход из

### A7. Уведомления

**A7.1 Назначена задача** `[Б]`
- *Шаги:* назначить задачу на ПРВ от имени СУП; затем переназначить на ЗАВ.
- *Ожидаемо:* в «Операции → Уведомления» появились записи «Вам назначена задача …» для

**A7.2 Регламент по срокам** `[Б]` `[API]`
- *Предусловия:* есть задача со сроком «завтра» и просроченная.
- *Шаги:* Claude выполняет `processNotifications` дважды подряд — человек проверяет журнал.
- *Ожидаемо:* созданы «Срок завтра …» и «Просрочена …»; повторный прогон дублей не даёт

**A7.3 Матрица «событие × канал»** `[Б]`

- *Ожидаемо:* строки доставки создаются только для включённых пар; у отключившегося

**A7.4 Почтовый канал** `[Б]`
- *Предусловия:* у получателя заполнен e-mail; настроен SMTP.
- *Шаги:* включить канал «Почта»; задать окно отправки (например, 8–20); вызвать событие
  вне окна и внутри окна; завершить успешную проверку.
- *Ожидаемо:* вне окна письмо ждёт, внутри — уходит; по успешной проверке письмо не
  отправляется (подавление), по проваленной — отправляется.

**A7.5 Пуш через FCM** `[Б]`
- *Шаги:* «Проверить связь с Firebase»; вызвать событие с включённым пушем; посмотреть
  «Уведомления → Доставки»; временно испортить ключ и повторить.
- *Ожидаемо:* при успехе — время отправки в доставке; при ошибке — текст ошибки и счётчик
  попыток, после исчерпания лимита строка попадает в фильтр «Не доставлено» (F9).

**A7.6 Реестр устройств** `[Б]`
- *Шаги:* войти в приложение на телефоне; посмотреть «Операции → Устройства для
  уведомлений»; выйти из аккаунта; войти другим пользователем на том же телефоне.
- *Ожидаемо:* при входе строка появляется/обновляется («Последний контакт»); при выходе
  удаляется; после входа другого сотрудника строка одна и принадлежит ему.

**A7.7 Комментарий к задаче** `[Б]`
- *Шаги:* написать комментарий к задаче другого исполнителя.
- *Ожидаемо:* создано уведомление «Новый комментарий …» участникам, кроме автора
  сообщения; второй комментарий за тот же день новой записи не создаёт.

**A8.5 Внешние приложения** `[Б]` + `[М]` *(модуль подключается хостом)*

## Блок B. Мобильное приложение «Пульс»

### B1. Установка и подключение

**B1.1 Первый запуск** — приложение открывается на экране «Подключение»; после ввода
адреса и «Проверить подключение» показывает название и цвета заказчика.

**B1.2 Неверный адрес / нет сети** — проверка подключения сообщает о недоступности, внутрь
не пускает; исправление адреса решает проблему без переустановки.

### B2. Вход и сессия

**B2.1 Вход по токену** — логин/пароль → внутрь; повторный запуск приложения входа не
требует (токен живёт сутки в защищённом хранилище).

**B2.2 Учётка не исполнитель** — при входе внятное сообщение «учётная запись не является
исполнителем», а не пустые списки.

**B2.3 Вход без сети** — при выключенной сети вход по сохранённому паролю проходит, если
последний удачный обмен с сервером был меньше суток назад; иначе — отказ с объяснением.

**B2.4 Перевыпуск токена** — после смены пароля на сервере (или по истечении суток)
приложение один раз молча меняет токен; повторный отказ сбрасывает сессию и возвращает на
вход, закрывая открытые экраны.

**B2.5 Выход и смена пользователя** — «Выйти» и «Выйти и удалить данные»; вход другим
сотрудником на том же телефоне.
- *Ожидаемо:* задачи, очереди и кэш первого сотрудника второму не видны; после «удалить
  данные» локальная база пуста; регистрация устройства переезжает на нового (A7.6).

### B3. Геолокация

**B3.1 Гейт после входа** — приложение спрашивает разрешение и определяет координаты;
мимо гейта пройти нельзя, выйти из учётной записи с него — можно.

**B3.2 Четыре отказа** — по очереди: выключена геолокация в телефоне; разрешение не
выдано; запрещено навсегда; таймаут определения.
- *Ожидаемо:* на каждый случай своё объяснение, кнопки «Повторить» и «Открыть настройки»
  ведут туда, куда надо.

**B3.3 Роль без геопривязки** — см. A10.2: гейта нет.

**B3.4 «Обновить местоположение»** — нажатие в шапке списка перестраивает список под
текущий объект; если объект тот же, приложение прямо об этом говорит.

**B3.5 Несколько объектов рядом** — на паре магазинов в одном ТЦ (`b23`/`b24` из демо):
по умолчанию выбран ближайший, остальные доступны из шапки с расстоянием; списки задач у
них разные.

**B3.6 Пустой список объясняет себя** — четыре ситуации, четыре разных текста: «на объекте
задач нет», «рядом нет объектов с координатами», «ближайший в N км», «неизвестно, где вы».

### B4. Главная страница

**B4.1 Состав и порядок блоков** — соответствует настройке A8.2 и роли вошедшего.

**B4.2 Плитки и переходы** — плитка показывает «здесь» и «всего», когда числа расходятся;
тап открывает список ровно с тем фильтром и объектом, которые она считает (число и список
не должны расходиться).

**B4.3 Новости и регламент** — блок «Новости» показывает ленту (свежие сверху), блок
«Текст» — форматированный регламент.

**B4.4 Объект и прошлая проверка** — выбор объекта в шапке; переход «последняя проверка
объекта» открывает завершённую проверку только для чтения.

**B4.5 Внешние приложения** — секция появляется, только если сервер её отдал (A8.5).

**B4.6 Шапка** — колокольчик с числом непрочитанных, бейдж «Не отправлено» с числом
операций в очереди, шестерёнка настроек, кнопка «Создать».

### B5. Список задач

**B5.1 Свои и чужие объекты** — задачи объекта, где человек стоит, — сверху и рабочие;
задачи других объектов — ниже, по расстоянию, только для чтения (открываются, но не
редактируются).

**B5.2 Пул подразделения и взятие** — задача подразделения видна всем его участникам;
«Взять» делает её рабочей; взятая коллегой не исчезает, а уходит в свёрнутую группу
«Взяты коллегами»; при одновременном взятии проигравший получает объяснение, а не ошибку.

**B5.3 Разбор списка** — поиск по названию/объекту, сортировка (по маршруту, сроку,
приоритету), фильтры по статусу и приоритету; разбор «Моих задач» помнится между
запусками, а список, открытый с плитки, стартует чистым.

**B5.4 Карточка в списке** — объект жирным, шаблон/детали, адрес, срок, приоритет, бейдж
непрочитанных сообщений.

**B5.5 Обновление** — ручное обновление подтягивает изменения сервера; при отсутствии сети
список остаётся из кэша и об этом сказано.

### B6. Карточка задачи

**B6.1 Что поставили** — описание, автор и дата постановки, фото проблемы (миниатюры,
тап — полный размер).

**B6.2 Смена статуса офлайн** — статус меняется сразу, уходит в очередь и подтверждается
сервером; до подтверждения виден «эффективный» статус.

**B6.3 Переписка** — сообщение отправляется из карточки, офлайн встаёт в ленту с пометкой
«не отправлено» и уезжает при связи; открытая лента гасит бейдж непрочитанного (в том
числе на карточке в списке).

**B6.4 Дозагрузка фото к задаче** — снимок добавляется к задаче после её создания.

**B6.5 Чем открывается задача** — бланк или экран фотоотчёта выбирает сервер
(`executionKind`); новый тип задачи не требует пересборки приложения.

### B7. Заполнение бланка

**B7.1 Ход заполнения** — «Начать» создаёт заполнение; шаги по разделам; в шапке — бегущая
оценка, вердикт и счётчик отвеченных пунктов (считается локально, работает офлайн).

**B7.2 Поля всех типов** — на демо-шаблоне «Приёмка товара» пройти все типы: варианты,
число, да/нет, дата, фото, длинный текст, скан, таблица, балл.

**B7.3 Нормы** — числовое поле показывает бейдж нормы; значение вне нормы подсвечивается и
помечается несоответствием.

**B7.4 Свидетельства по несоответствию** — где требуется фото/комментарий, завершение без
них не проходит, и приложение говорит, каких именно пунктов не хватает.

**B7.5 Табличные поля** — строки приезжают заполненными по шаблону; ввод факта считает
расхождение; обязательная колонка контролируется при завершении.

**B7.6 Скан кода камерой** — поле `scan` заполняется камерой; при отказе камеры остаётся
ручной ввод.

**B7.7 Прошлая проверка** — из бланка открывается прошлая проверка того же объекта и
шаблона (прокрученная к тому же пункту), только для чтения; у пункта видно прошлое значение.

**B7.8 Завершение** — сервер проверяет обязательные поля, свидетельства и исход; отказ
показывается причиной, успешное завершение закрывает бланк и меняет статус задачи.

**B7.9 Координаты работы** — после начала и завершения в карточке задачи в бэк-офисе
заполнены «Работа начата/завершена», широта, долгота и расстояние от объекта; работа,
начатая офлайн, несёт координаты места работы, а не места, где появилась связь; отсутствие
координат (подвал) завершению не мешает.

**B7.10 Просмотр завершённого** — повторное открытие завершённой проверки не создаёт
второго заполнения и ничего не даёт изменить.

### B8. Поручение и корректирующее действие

**B8.1 Экран фотоотчёта** — снимки серией (камера не закрывается между кадрами), лишний
кадр удаляется сразу, комментарий, кнопка «Выполнено».

**B8.2 Обязательное фото** — если задача его требует, «Выполнено» недоступно до снимка
(проверка на телефоне, а не только отказом сервера).

**B8.3 Офлайн-порядок** — созданная офлайн задача с фотоотчётом уезжает в порядке
создание → старт → фото → комментарий → завершение; отказ сервера показывается причиной.

### B9. Создание задачи в поле

**B9.1 Пресеты** — кнопка «Создать» показывает пресеты своей роли; поручение себе
создаётся в два-три касания.

**B9.2 Назначение** — «Себе», «Выбрать из списка», «По роли на объекте»: исполнители и их
роли на объектах доступны офлайн (предзагрузка).

**B9.3 Фото проблемы** — к создаваемой задаче прикладывается несколько снимков.

**B9.4 Офлайн и идемпотентность** — задача, созданная без связи, живёт в списке под своим
UUID и после синхронизации получает `ST`-номер, не задваиваясь; повторная отправка той же
задачи второй не создаёт; открытая карточка при подмене строки не закрывается.

**B9.5 Ошибки** — если сервер отверг создание (нет типа/объекта/шаблона), причина видна,
операция остаётся в очереди и не теряется.

### B10. Офлайн и очереди

**B10.1 Полный офлайн-цикл** — режим полёта: пройти заполнение целиком, снять фото,
завершить; включить сеть.
- *Ожидаемо:* всё уезжает без вмешательства; на сервере ответы, фото и завершение
  совпадают с тем, что было на телефоне.

**B10.2 Экран «Не отправлено»** — состав очередей по-человечески («Бланк: 12 ответов,
3 фото»), время постановки, причина последней неудачи, кнопка «Отправить сейчас» с видимым
результатом; строки исчезают по мере отправки, бейдж шапки считает то же самое.

**B10.3 Серия быстрых ответов** — быстро ответить на 10–15 пунктов подряд при живой сети.
- *Ожидаемо:* ни один ответ не потерян (проверка фикса гонки синхронизации).

**B10.4 Битая запись не блокирует очередь** — одна операция, отвергнутая сервером, не
останавливает отправку остальных.

**B10.5 Перезапуск с непустой очередью** — закрыть приложение с неотправленными
операциями, открыть снова: очередь на месте и дожимается.

### B11. Уведомления и пуш

**B11.1 Лента** — «Уведомления» показывают записи за 30 дней, непрочитанные выделены;
открытие ленты отмечает прочтение (бейдж гаснет).

**B11.2 Пуш при открытом приложении** — приходит и обновляет ленту, не мешая работе.

**B11.3 Пуш при свёрнутом и убитом приложении** — тап открывает приложение и переводит на
задачу; если гейт геолокации не пройден, уведомление просто открывает приложение.

**B11.4 Пуш о задаче другого объекта** — если задачи нет в списке, открывается лента с
записью, а не пустая карточка.

**B11.5 Выход снимает регистрацию** — после выхода уведомления на этот телефон не приходят
(проверить, что чужие названия объектов и тексты задач не попадают предыдущему владельцу).

### B12. Оформление и устойчивость

**B12.1 Тема** — «Настройки → Тема»: «Система», «Светлая», «Тёмная»; применяется сразу,
переживает перезапуск; в тёмной теме читаемы все экраны (бланк, лента, плитки, диалоги).

**B12.2 Бренд** — см. A8.1.

**B12.3 Устойчивость интерфейса** — поворот экрана на бланке и в ленте, длинные названия
объектов и пунктов, маленький экран: ничего не обрезается до нечитаемости и не теряет
введённое.

**B12.4 Обновление поверх** — установить новую сборку поверх старой с непустой очередью и
живой сессией: повторный вход не требуется, очередь и заполнения на месте.

## Блок C. Сквозные истории

Эти сценарии прогоняются целиком, двумя-тремя людьми, и именно они считаются приёмкой:
блоки A и B проверяют детали, блок C — что из деталей собирается работа.

**C1. Плановая проверка: от графика до свода баллов**
График создаёт задачу на объект → ПРВ видит её в приложении на объекте → заполняет бланк с
фото и несоответствиями → завершает → СУП видит проверку в «Своде баллов» с процентом и
вердиктом, а пункт-нарушитель — в «Повторяющихся несоответствиях».

**C2. Несоответствие → устранение**
Из завершённой проверки создаются корректирующие задачи → ЗАВ получает уведомление (пуш и
почта) → открывает задачу в приложении → закрывает фотоотчётом → задача переходит в
«Выполнено», фото и комментарий видны в бэк-офисе.

**C3. Внеплановая задача, созданная в поле без связи**
ПРВ в магазине без сети создаёт задачу по пресету с фото → работает дальше офлайн →
на выходе из магазина связь появляется → задача уезжает, получает номер, приходит
уведомление назначенному; дублей нет.

**C4. Задача на подразделение**
СУП назначает задачу на подразделение → двое исполнителей видят её в пуле → один берёт →
у второго она уходит в «Взяты коллегами» → взявший выполняет; в карточке видно, кто и
когда взял.

**C5. Просроченная задача**
Наступает срок → ночной регламент создаёт уведомления → приходит пуш и письмо → исполнитель
закрывает задачу → на следующем прогоне повторных напоминаний по ней нет.

## D. Протокол и известные ограничения

### D1. Форма протокола

| № сценария | Дата | Кто прогонял | Стенд | Результат | Дефект |
|---|---|---|---|---|---|
| A3.4 | | | | ✅ / ❌ / ⛔ (не проверялось) | #… |

Дефект описывать так: номер сценария и шаг → что ожидали → что получили → как
воспроизвести → скриншот/лог. Для мобильных дефектов обязательно: версия сборки, модель и
версия Android, было ли соединение.

### D2. Что заведомо не проверяем

- **iOS** — сборки и канала раздачи нет; все мобильные сценарии прогоняются на Android.
- **Подпись релиза** — APK до сих пор подписывается debug-ключом; это вопрос выпуска, а не
  функциональности.
- **Постановка задачи текстом через локальную модель** — ветка
  `claude/ai-task-creation-tool-…`, в `master` не влита.
- **Доступ к объектам** (A1.5) и **показатели задачи из внешней системы** — есть только в
  локальном рабочем дереве; прогонять, когда попадут в `master`.

### D3. Места, где ошибались раньше (проверять внимательнее)

- Число без заданных норм ранее помечалось несоответствием всегда, односторонние нормы не
  работали — A5.3.
- `apiSetStatus` при недопустимом статусе отвечает HTTP 500, и запись остаётся в очереди —
  B6.2, B10.4.
- Явно переданный `objectId` в `apiTasks` однажды не срабатывал при объекте в радиусе —
  B3.4, B3.5.
- Имя магазина длиннее 30 символов не помещается в поле хоста-ERP — A1.1.
- Идемпотентные генераторы не обновляют уже созданный шаблон: после правки шаблона в коде
  его нужно удалить и пересоздать — П2.
