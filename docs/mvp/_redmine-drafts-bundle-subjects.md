> специализация «Общий функционал».
> Откуда: разбор explain/explainapp-логов со стенда ERP-хоста (10.40.0.81) от 20.10.2026:
> после добавления строки в заполнение (apiAddRow, 12:28:51) бандл отвечает 125,8 с
> (12:31:20, p1387115), те же INSERT'ы с JSONB_AGG повторяются при каждом обновлении

## Тема

**[API] apiExecutionBundle: предзагрузка subjects тянет доступность всего каталога
(echelon) — тяжёлые материализации на каждый запрос** — оценка S (артефакт) /
M (с мобильной частью).

## Фактура (логи 20.10, ERP-хост, каталог ~311 тыс. товаров)

- 12:28:51 `apiAddRow` (3,5 с) → дальше всё разваливается:
  - 12:28:57 `apiHome` 33,7 с SQL (утром то же — 7,7 с);
  - 12:30:10 залп из 5 параллельных `apiRowSubjects` по ~40 с: в каждом материализация
    `LAST(price) BY sku` по прайс-регистру отдела — EXPLAIN: Index Scan 916 428 строк,
    Sort external merge 37 МБ, 54,6 с (t_112/t_17/t_22/t_53/t_29 — по копии на вызов);
  - 12:31:15 `apiHome` 174 с SQL (p1386998 — метрики главной, отдельная история);
  - 12:31:20 `apiExecutionBundle` **125,8 с** app (p1387115: материализация изменений +
    JSONB_AGG subjects + прайс внутри);
  - 12:31:20→12:36:36 — 5 минут тишины, сервер фактически не отвечает.
- Свежие логи: то же самое «сыпется» на каждый бандл с subjects=1 (p1387987).

## Причина в коде (цепочка)

- `storeTasks/api/FillReadApi.lsf:366-376` — блок subjects агрегата: колонка
  `available` (:371) и фильтр `echelon` в WHERE (:375);
- `storeTasks/fillable/HostRow.lsf:13-20` — `echelon = available(v,o) OR NOT
  availableAny(o,kind)`, где `availableAny = GROUP SUM … по ВСЕМУ каналу` — глобальный
  агрегат доступности в WHERE;
- шов `available` — `storeTasks/fillable/RefValue.lsf:16`; на ERP-хосте его реализует
  мост `TaskItemRowErp` (erp-logics): `available = остаток ИЛИ цена`, цена =
  `prevPriceA` (`pricelist/PriceListCalc.lsf:135-136`, LAST(price) по регистру) —
  отсюда 916 тыс. строк прайса на отдел в плане;
- после #37192 `echelon`/`availableAny` имеют ровно одного потребителя — этот блок.

## Предлагаемое решение (артефакт)

Предзагрузка не должна трогать доступность:

- убрать `echelon` из WHERE блока и колонку `available` из выдачи — плоский срез
  справочника канала (алфавит);
- `echelon` и `availableAny` удалить из HostRow; заодно поправить комментарий
  `FillReadApi.lsf:241` («общий с apiRowSubjects») — после #37192 общности нет;
- доступность остаётся в поиске `apiRowSubjects` (ранжирование) и в `offSystem` по
  добавленным строкам.

Открытый вопрос (продуктовый): пикер показывает по предзагруженным кандидатам бейдж
«нет в остатках объекта» (`mobile/pulse_tasks/lib/ui/widgets/pickers/row_subject_sheet.dart:350`,
разбор тем же `RefCandidate.fromJson`, `fill_controller.dart:192`). Без `available`
в предзагрузке бейдж либо пропадёт, либо (дефолт false) соврёт всем «нет» — нужно
решение: не показывать в первичном списке / лениво по видимой странице / показывать
только для кандидатов из поиска. Мобильная часть — мини-релиз.

Отдельная ветка (мост, erp-сторона, другая задача): дешёвая доступность
(MATERIALIZED в мосту / кэш) — без неё поиск `apiRowSubjects` после записи так и
остаётся ~40 с.

## Критерии приёмки

- На ERP-стенде с каталогом ~300 тыс.: `apiExecutionBundle` с subjects=1 — единицы
  секунд; в explain-логе вызова нет материализаций прайс/остаток по всему каталогу;
  до и после записи строки — одинаково.
- Выдача subjects совместима (fieldCode/subjectId/name/kind/barcodes); изменение по
  колонке available согласовано с мобильным релизом.
- `echelon`/`availableAny` удалены; ядро не тянет хост-свойств сверх шва `available`.
