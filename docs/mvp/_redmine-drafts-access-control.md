## Цель

Подсистема не поставляет ни одной политики доступа. Любой сотрудник с учётной записью,
вошедший в веб-клиент, видит и правит всё: чужие задачи, шаблоны проверок, справочники,
нумератор, настройки и журнал координат коллег.

Это не недосмотр в одном месте, а отсутствующий слой: в артефакте нет ни одного
`securityPolicy`, ни одного `forbid`/`permit`. Роли используются трижды, и все три раза
разрешительно, а не запретительно — две настройки роли через `@addRoleApplicationSetting`
и матрицы видимости пунктов АРМ и блоков главной.

Мобильное API при этом режет: `apiTasks` фильтрует по `assignedTo(t, currentUser())`, и
чужие задачи на телефон не приезжают. Веб не режет ничего — то есть дыра ровно там, куда
заходит человек с браузером. Хост уже вынужден чинить это сам: MITE дописывает фильтр по
организации прямо в форму задач. Каждый следующий хост напишет свой вариант.

## Что делаем

Развести три плоскости, не смешивая их: **навигатор** (какие разделы видит роль),
**данные** (чьи задачи и заполнения видно) и **действия** (кто назначает, закрывает чужое,
правит справочники и настройки). Если их смешать, «скрытый пункт меню» начнёт считаться
защитой.

Артефакт не знает оргструктуру заказчика и готовую политику привезти не может. Поэтому
даёт три вещи:

- **Именованные права** тем же приёмом, что уже прижился (`@addRoleApplicationSetting`):
  видеть все задачи · назначать исполнителя · закрывать чужую задачу · править шаблоны и
  справочники · править настройки · видеть журнал координат.
- **Точку расширения области видимости** — `visibleTask = ABSTRACT BOOLEAN (Task)` с
  реализацией по умолчанию «моё, моего подразделения (транзитивно) и где я автор». Хост
  дорезает своим измерением: MITE переносит сюда фильтр по организации вместо латания
  формы. Область супервайзера — по объектам, за которые он отвечает.
- **Профиль по умолчанию как данные**: исполнитель, супервайзер, администратор — чтобы на
  чистой базе всё сразу вело себя разумно, а заказчик правил, а не собирал с нуля.

## Фильтр формы — это удобство, а не защита

Самая вероятная ошибка реализации. `FILTERS` сужает выборку, но не мешает открыть соседнюю
форму, где тот же объект показан без фильтра, или дёрнуть ручку API напрямую. Ограничившись
фильтрами, получим систему, которая **выглядит** закрытой, оставаясь открытой. Барьер —
политика на действия и свойства плюс те же ограничения внутри ручек.

## API — проверить руками, а не предположить

- `apiNearbyObjects` отдаёт весь каталог объектов любому исполнителю. Для сети в сотни
  точек это выгрузка её структуры одним запросом; возможно приемлемо, но это должно быть
  решением, а не побочным эффектом.
- Ручки заполнения (`apiExecutionFields`, `apiSetField`, `apiSetFieldPhoto`,
  `apiFinishExecution`) адресуются по id задачи. Убедиться, что с чужим id они отвечают
  отказом, а не данными и записью.

## Чего не делаем

Своей системы ролей поверх платформенной. В lsFusion уже есть роли, политики и
`has(user, role)`; вторая система прав рядом — вечная поддержка двух правд о том, кому что
можно.

## Готово когда

Исполнитель видит в вебе свои задачи и задачи своего подразделения, не видит чужих и не
видит настроек. Супервайзер видит свои объекты, администратор — всё. Открыть чужую задачу
по прямому идентификатору не удаётся ни в вебе, ни через API. На чистой базе профиль по
умолчанию уже разумен без ручной настройки.

## Зависит от

Ничего жёстко. #36835 (транзитивное членство) и #36708 (ответственные по ролям) делают
задачу лучше: без них «своё» сужается до назначенного лично, а область супервайзера
задаётся перечислением объектов.
