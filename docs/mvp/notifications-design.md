# Уведомления и журнал (дизайн)

> Своевременно доводить события до людей: назначили задачу, срок завтра, просрочено,
> проверка на объекте завершена с плохим вердиктом.
> Решение по объёму принято 2026-08-07: **журнал без пуша**; пуш через FCM для iOS и
> Android — отдельной задачей после демо.
> Закрывает roadmap 15 и заменяет черновик 12 из [бэк-офиса](_redmine-drafts-backoffice.md).
> Статус: дизайн, не реализовано. Ветка `mvp_tasks`.
> Нерешённое — в разделе 9.

## 1. Три слоя, и путать их — главная ошибка

1. **Событие** — что произошло в предметной области.
2. **Уведомление** — запись, адресованная человеку. **Это и есть журнал.**
3. **Доставка** — как оно вышло наружу: почтой, пушем, в мессенджер.

Ключевая мысль: **журнал не пристраивается рядом с пушем — пуш является проекцией
журнала.** Сделав слой 2, получаем работающий центр уведомлений в приложении без
единого внешнего сервиса; каналы потом добавляются, ничего не трогая.

Обратный порядок — сначала пуш, потом «а где посмотреть, что мне приходило» — приводит
к тому, что журнал пишется вторым и параллельным механизмом, с собственной моделью и
собственными расхождениями с тем, что реально доставлено.

**«В приложении» — не канал.** Уведомление существует — значит в журнале оно есть.
Заводить для этого строку доставки значило бы отдельно хранить факт, что запись, которая
уже лежит в базе, в базе лежит. Каналы — это только внешние: почта, пуш, мессенджер.

## 2. Модель

```lsf
// Каталоги, а не статические классы: событие или канал добавляются модулем —
// в том числе модулем хоста, — как это уже сделано с TaskType в Corrective/FormTask.
CLASS NotificationEvent 'Событие';
id '{ID}' = DATA STRING[30] (NotificationEvent);
name '{Name}' = DATA ISTRING[100] (NotificationEvent) NONULL;
notificationEvent = GROUP AGGR NotificationEvent e BY id(e);

CLASS NotificationChannel 'Канал';
id '{ID}' = DATA STRING[30] (NotificationChannel);
name '{Name}' = DATA ISTRING[50] (NotificationChannel) NONULL;
notificationChannel = GROUP AGGR NotificationChannel c BY id(c);

CLASS Notification 'Уведомление';
performer = DATA TaskPerformer (Notification) NONULL;
event     = DATA NotificationEvent (Notification) NONULL;
task      = DATA Task (Notification);
dateTime 'Дата/время' = DATA DATETIME (Notification) IN id;
title 'Заголовок' = DATA ISTRING[100] (Notification) IN id;
body 'Текст'      = DATA ISTRING[500] (Notification);
viewed 'Прочитано' = DATA BOOLEAN (Notification);

CLASS Delivery 'Доставка';
notification = DATA Notification (Delivery) NONULL DELETE;
channel = DATA NotificationChannel (Delivery) NONULL;
sent 'Отправлено' = DATA DATETIME (Delivery);
error 'Ошибка' = DATA ISTRING[250] (Delivery);
attempts 'Попыток' = DATA INTEGER (Delivery);

// канал подключается модулем — тот же приём, что startExecution и onFinish
send ABSTRACT LIST (Delivery);
```

## 3. Дедупликация — структурным ключом, а не строкой

«Срок завтра» должен сработать один раз, а не на каждом тике планировщика. Приём тот
же, что везде в подсистеме, — уникальность через `GROUP AGGR`:

```lsf
date (Notification n) = DATE(dateTime(n));
notification = GROUP AGGR Notification n BY performer(n), event(n), task(n), date(n);
```

Ключ **структурный, а не склеенная строка**. Строковый ключ вида `event + '/' + id(t)`
выглядит гибче, но ломается ровно там, где это дороже всего: `id(Task)` в момент
создания задачи может быть ещё не присвоен, ключ окажется NULL, уникальность
отключится, и уведомления начнут дублироваться — то есть именно тот отказ, ради
которого ключ и заводили.

Семантика получается явная: **одно уведомление на (человек, событие, задача, день)**.
Планировщик, отработавший повторно, ничего не портит:

```lsf
notify (TaskPerformer p, NotificationEvent e, Task st) {
    IF NOT notification(p, e, st, currentDate()) THEN
        NEW n = Notification {
            performer(n) <- p; event(n) <- e; task(n) <- st;
            dateTime(n) <- currentDateTime();
            title(n) <- title(e, st); body(n) <- body(e, st);
        }
}
```

Это та же защита от дублей, что нужна расписанию проверок в **#36710**. Одна проблема —
один приём; писать её дважды не нужно, и тикеты стоит делать с оглядкой друг на друга.

Ограничение, которое надо принять сознательно: уведомления без задачи из-под
дедупликации выпадают (NULL в `BY` исключает строку из агрегата). Для событий по
задачам, а это все события первой версии, вопрос не стоит.

## 4. Текст уведомления живёт с событием

```lsf
title = ABSTRACT CASE ISTRING[100] (NotificationEvent, Task);
body  = ABSTRACT CASE ISTRING[500] (NotificationEvent, Task);

title (NotificationEvent e, Task t) += WHEN id(e) = 'taskAssigned' AND t IS Task THEN
    ISTRING[100]('Вам назначена задача: ' + name(t));
```

`AND t IS Task` — **обязательно, а не для красоты**. Над двумя параметрами условие
реализации должно связывать оба; диспетчеризация только по значению первого не работает.
Ровно так это уже написано в
[`HomeScreen.lsf:201`](../../src/main/lsfusion/storeTasks/mobile/HomeScreen.lsf)
(`calcValue(HomeMetric m, CheckObject o) += WHEN code(m) = 'myOpen' AND o IS CheckObject`).
Грабли известные, наступать второй раз не надо.

Приведение к `ISTRING[100]` тоже обязательно: конкатенация складывает длины операндов,
и без явного каста реализация окажется шире объявленного класса — сервер не стартует.

## 5. Что данные, а что код

Честная граница, без попыток построить движок правил:

| | Где живёт | Почему |
|---|---|---|
| Условие срабатывания | **код** — `WHEN` в модуле события | у каждого события оно своё; DSL под них — месяц работы и никто им не воспользуется |
| Кому адресовано | **данные** — роли на объекте (#36708), автор, исполнитель | это то, что меняется у каждого заказчика |
| Каким каналом | **данные** — матрица `on(NotificationEvent, NotificationChannel)` | включить почту для одного события — настройка |
| Отключение | **данные** — `mute(TaskPerformer, NotificationEvent)` | иначе первым делом отключат всё целиком |
| Текст | **код рядом с событием** — `+=` (раздел 4) | текст неотделим от того, что произошло |

Новое событие = одна реализация `title`/`body` плюс один `WHEN` с вызовом `notify()`.
Журнал, доставки, API и клиент при этом не трогаются вообще. В этом и состоит
универсальность — не в конфигурируемости условий, а в том, что добавление события
не расходится по системе.

## 6. Доставка асинхронна

Отправка **не** должна происходить в той же сессии, что бизнес-операция. Если SMTP
не отвечает, откатится назначение задачи — то есть сбой почты станет сбоем работы.

Поэтому: событие создаёт `Notification` и строки `Delivery` по включённым каналам;
регламентное задание разгребает неотправленные и вызывает `send`. Ошибка пишется
в строку доставки и остаётся видимой, попытки считаются.

События первой версии:

| Код | Когда | Кому |
|---|---|---|
| `taskAssigned` | назначен исполнитель | исполнителю |
| `deadlineNear` | срок наступает завтра | исполнителю |
| `overdue` | срок прошёл, задача открыта | исполнителю, затем по цепочке ролей |
| `fillingFinished` | проверка завершена | ответственным ролям объекта |
| `correctiveCreated` | создано корректирующее действие | исполнителю |

Первое и последнее — обычные `WHEN`. Остальные три — регламентное задание, и именно
им нужна дедупликация из раздела 3.

## 7. Приложение

```lsf
apiNotifications () {
    EXPORT JSON FROM
        event = id(event(Notification n)),
        dateTime = dateTime(n),
        title = title(n),
        body = body(n),
        taskId = id(task(n)),
        viewed = viewed(n)
        WHERE performer(n) = currentPerformer()
            AND dateTime(n) >= subtract(currentDate(), 30);
} @@api;
```

* **Адресация для «прочитано»** — по паре (событие, задача, дата), той же, что образует
  ключ. Внутренние идентификаторы объектов наружу не отдаём.
* **Глубина 30 дней.** Журнал растёт неограниченно, и «отдать всё» однажды станет
  ответом на мегабайт. Старое чистится регламентом.
* **Счётчик непрочитанного считает клиент** — полный список у него и так есть, и
  отдельная ручка ради числа не нужна.
* Экран — лента с переходом на задачу. Клиент сейчас обновляется по возврату связи и
  pull-to-refresh ([`task_repository.dart:107`](../../mobile/pulse_tasks/lib/data/task_repository.dart));
  таймер добавляется тривиально, и уведомление, доехавшее за минуту, на демо от пуша
  неотличимо.

## 8. Пуш — отдельно и позже

> Сделано в #36720: `PushDevice.lsf` (реестр), `NotificationDelivery.lsf` (матрица
> событие × канал и регламент отправки), `PushFcm.lsf` (канал), `DeviceApi.lsf` (ручки),
> `FcmAssertionAction.java` (подпись JWT). Что завести и включить —
> [push-fcm-setup.md](push-fcm-setup.md). Раздел ниже — исходный разбор, он же и есть
> объяснение принятых решений.

Настоящий пуш — это только FCM. Что он потребует:

* **Инфраструктура заказчика:** проект Firebase на его Google-аккаунте,
  `google-services.json`, для iOS — платный Apple Developer и APNs-ключ.
* **Аутентификация к FCM.** Простой серверный ключ (`Authorization: key=...`) выключен;
  HTTP v1 требует OAuth2-токена сервисного аккаунта, то есть подписи JWT. В lsFusion это
  либо небольшой `INTERNAL`, либо отдельное действие обновления токена. **Это главный
  технический риск задачи**, и оценивать её без этого пункта нельзя.
* **Реестр устройств:** `CLASS Device` (токен, исполнитель, платформа, версия, последний
  контакт), `apiRegisterDevice` / `apiUnregisterDevice`, обработка протухших токенов.
* **Клиент:** `firebase_core` + `firebase_messaging`, запрос разрешения (iOS и Android 13+),
  обработчики в фоне и на переднем плане, переход на задачу из уведомления.

Мина безопасности: токен привязан к паре «устройство + пользователь». Выход из аккаунта
**обязан** снимать регистрацию, иначе уведомления следующего сотрудника уедут на телефон
предыдущего — вместе с названиями объектов и содержанием задач.

Промежуточного варианта нет: локальные уведомления с фоновым опросом на Android душатся
оптимизацией батареи, а на iOS не работают вовсе. Разбудить убитое приложение без FCM
нельзя, и обещать это не следует.

Зато сам канал встаёт в готовую конструкцию одной реализацией `send(Delivery)` — ничего
из разделов 2–7 при этом не меняется. Ради этого разделение на слои и делалось.

## 9. Нерешённое

1. **Кто получает `overdue` вторым шагом.** Эскалация «исполнителю, потом руководителю»
   требует иерархии ролей на объекте, а #36708 даёт плоский набор. Либо порядок ролей
   как данные, либо эскалация ограничивается одним шагом.
2. **Почта: адрес исполнителя.** У `TaskPerformer` нет email — он есть у пользователя
   хоста. Нужно абстрактное свойство и реализации в мостах, как `id` и `name`.
3. **Вложение акта в письмо** — зависит от печатной формы (черновик 5 бэк-офиса).
   До неё письмо о завершённой проверке несёт только вердикт и ссылку.
4. **Тихие часы.** Проверки идут днём, но просрочка считается ночным регламентом.
   Отправлять в 03:00 не стоит; окно отправки — настройка канала, не события.
5. **Что делать с уведомлением о задаче, которую потом удалили.** `DELETE` на ссылке
   удалит и уведомление; возможно, правильнее сохранить его без ссылки.
