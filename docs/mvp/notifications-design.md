# Уведомления и журнал (дизайн)

> Своевременно доводить события до людей: назначили задачу, срок завтра, просрочено,
> проверка на объекте завершена с плохим вердиктом.
> Решение по объёму принято 2026-08-07: **журнал без пуша**; пуш через FCM для iOS и
> Android — отдельной задачей после демо.
> Закрывает roadmap 15 и заменяет черновик 12 из [бэк-офиса](_redmine-drafts-backoffice.md).
> Статус: дизайн, не реализовано. Ветка `mvp_tasks`.
> Нерешённое — в разделе 9.

## 1. Три слоя, и путать их — главная ошибка

1. **Событие** — что произошло в предметной области.
2. **Уведомление** — запись, адресованная человеку. **Это и есть журнал.**
3. **Доставка** — как оно вышло наружу: почтой, пушем, в мессенджер.

Ключевая мысль: **журнал не пристраивается рядом с пушем — пуш является проекцией
журнала.** Сделав слой 2, получаем работающий центр уведомлений в приложении без
единого внешнего сервиса; каналы потом добавляются, ничего не трогая.

Обратный порядок — сначала пуш, потом «а где посмотреть, что мне приходило» — приводит
к тому, что журнал пишется вторым и параллельным механизмом, с собственной моделью и
собственными расхождениями с тем, что реально доставлено.

**«В приложении» — не канал.** Уведомление существует — значит в журнале оно есть.
Заводить для этого строку доставки значило бы отдельно хранить факт, что запись, которая
уже лежит в базе, в базе лежит. Каналы — это только внешние: почта, пуш, мессенджер.

## 2. Модель

```lsf
// Каталоги, а не статические классы: событие или канал добавляются модулем —
// в том числе модулем хоста, — как это уже сделано с TaskType в Corrective/FormTask.
CLASS NotificationEvent 'Событие';
id '{ID}' = DATA STRING[30] (NotificationEvent);
name '{Name}' = DATA ISTRING[100] (NotificationEvent) NONULL;
notificationEvent = GROUP AGGR NotificationEvent e BY id(e);

CLASS NotificationChannel 'Канал';
id '{ID}' = DATA STRING[30] (NotificationChannel);
name '{Name}' = DATA ISTRING[50] (NotificationChannel) NONULL;
notificationChannel = GROUP AGGR NotificationChannel c BY id(c);

CLASS Notification 'Уведомление';
performer = DATA TaskPerformer (Notification) NONULL;
event     = DATA NotificationEvent (Notification) NONULL;
task      = DATA Task (Notification);
dateTime 'Дата/время' = DATA DATETIME (Notification) IN id;
title 'Заголовок' = DATA ISTRING[100] (Notification) IN id;
body 'Текст'      = DATA ISTRING[500] (Notification);
viewed 'Прочитано' = DATA BOOLEAN (Notification);
image 'Вложение'  = DATA TaskFile (Notification);   // картинка события, #37125

CLASS Delivery 'Доставка';
notification = DATA Notification (Delivery) NONULL DELETE;
channel = DATA NotificationChannel (Delivery) NONULL;
sent 'Отправлено' = DATA DATETIME (Delivery);
error 'Ошибка' = DATA ISTRING[250] (Delivery);
attempts 'Попыток' = DATA INTEGER (Delivery);

// канал подключается модулем — тот же приём, что startExecution и onFinish
send ABSTRACT LIST (Delivery);

// дополнительные адресаты события по задаче — подписка (#37135)
notifyWatchers ABSTRACT LIST (NotificationEvent, Task);
```

`notifyWatchers` зовётся производителем события **рядом** с `notify()`, а не изнутри
него, и это несущая стена. Основного адресата у события может не оказаться вовсе:
проверка завершена, а ответственные роли на объекте не назначены; срок подходит у
задачи, которую ещё ни на кого не повесили. Внутри `notify()` наблюдатель в этих
случаях не услышал бы ничего — а ради завершения проверки в основном и подписываются.

Событие `taskAssigned` наблюдателям не уходит, и это исключение **структурное**: его
производитель `notifyWatchers` просто не зовёт, никакого сравнения `id(e)` со строкой.
Назначение говорит про исполнителя и наблюдателю не сообщает ничего.

Запись, которую родил шов, помечается **`viaWatch` — «по подписке»** (#37136), если
адресата с задачей больше ничего не связывает: не исполнитель и не автор. Лента телефона
показывает это пометкой на пузыре — уведомление по своей задаче и по задаче, за которой
лишь следишь, человек читает по-разному. Пометка — поле записи, а не вычисление при
чтении, по той же причине, что `title`/`body`/`image`: отписка или закрытие задачи не
должны стирать объяснение у записи, которая уже лежит в ленте. Слияние события в
цепочку (3.1) переписывает текст, но не пометку: почему запись пришла, решено при её
рождении и от числа сообщений не зависит.

`correctiveCreated` наблюдателям стал доходить только с #37136: шов зовётся с НОВОЙ
корректирующей задачей, у которой подписчиков не было. Теперь корректирующая при
создании получает наблюдателей исходной (`Corrective.createCorrective`) — и уведомление
доходит, и тап по нему открывает задачу, которую наблюдатель теперь видит.

## 3. Дедупликация — структурным ключом, а не строкой

«Срок завтра» должен сработать один раз, а не на каждом тике планировщика. Приём тот
же, что везде в подсистеме, — уникальность через `GROUP AGGR`:

```lsf
date (Notification n) = DATE(dateTime(n));
notification = GROUP AGGR Notification n BY performer(n), event(n), task(n), date(n);
```

Ключ **структурный, а не склеенная строка**. Строковый ключ вида `event + '/' + id(t)`
выглядит гибче, но ломается ровно там, где это дороже всего: `id(Task)` в момент
создания задачи может быть ещё не присвоен, ключ окажется NULL, уникальность
отключится, и уведомления начнут дублироваться — то есть именно тот отказ, ради
которого ключ и заводили.

Семантика получается явная: **одно уведомление на (человек, событие, задача, день)**.
Планировщик, отработавший повторно, ничего не портит:

```lsf
notify (TaskPerformer p, NotificationEvent e, Task st) {
    IF NOT notification(p, e, st, currentDate()) THEN
        NEW n = Notification {
            performer(n) <- p; event(n) <- e; task(n) <- st;
            dateTime(n) <- currentDateTime();
            title(n) <- title(e, st); body(n) <- body(e, st);
        }
}
```

Это та же защита от дублей, что нужна расписанию проверок в **#36710**. Одна проблема —
один приём; писать её дважды не нужно, и тикеты стоит делать с оглядкой друг на друга.

Ограничение, которое надо принять сознательно: уведомления без задачи из-под
дедупликации выпадают (NULL в `BY` исключает строку из агрегата). Для событий по
задачам, а это все события первой версии, вопрос не стоит.

### 3.1. Второй режим: цепочка (2026-09-16)

Суточный ключ хорош для событий регламента и плох для переписки: комментарий получал
один пуш в день на задачу, и второе за день сообщение человек не видел, пока сам не
откроет список. #36844 принял это осознанно («сколько там нового — на карточке»); при
живой переписке это оказалось потерей сообщений, а не экономией шума.

Режим — свойство события, код, а не данные: `threaded = ABSTRACT CASE BOOLEAN
(NotificationEvent)`, комментарий объявляет себя потоковым в `NotificationComment`.
Правила потокового режима:

* **одна запись на непрочитанную цепочку** — `openThread(n)`, уникальность
  `openNotification = GROUP AGGR … WHERE openThread(n) BY performer, event, task`;
  из суточного ключа такие записи выпадают (`dayKey(n) = date(n) IF NOT threaded`);
* **каждое событие — своя редакция**: `revision(n)` растёт, текст пересобирается со
  счётчиком и последним сообщением («3 новых · Пётр: …»), запись снова непрочитанная и
  снова наверху ленты (`dateTime`); у редакции своя строка доставки (раздел 6);
* **слияние идемпотентно в пределах сессии по данным**, а не по локали: производитель
  зовёт `notify` на одного человека дважды (исполнитель и автор, назначенный и
  наблюдатель) — второй вызов гасит `CHANGED(revision(n))`;
* **закрывает цепочку прочтение переписки**, а не тап по ленте: отметка
  `commentsReadAt`, дошедшая до последнего сообщения (`NOT unreadComments`), зовёт
  `closeThread` — запись становится прочитанной историей, следующее сообщение начнёт
  новую. Тап по ленте открывает карточку задачи, чья переписка отметку и ставит.
  Десктоп отметки не ставит: цепочка его пользователя живёт до чистки журнала.

`currentNotification(p, e, t)` — «запись, в которую сейчас попадёт событие» в любом
режиме; это то, что нужно шву наблюдателей, чтобы ставить `viaWatch` только рождённой
им записи.

## 4. Текст уведомления живёт с событием

```lsf
title = ABSTRACT CASE ISTRING[100] (NotificationEvent, Task);
body  = ABSTRACT CASE ISTRING[500] (NotificationEvent, Task);
image = ABSTRACT CASE TaskFile (NotificationEvent, Task);   // #37125

title (NotificationEvent e, Task t) += WHEN id(e) = 'taskAssigned' AND t IS Task THEN
    ISTRING[100]('Вам назначена задача: ' + name(t));
```

`AND t IS Task` — **обязательно, а не для красоты**. Над двумя параметрами условие
реализации должно связывать оба; диспетчеризация только по значению первого не работает.
Ровно так это уже написано в
[`HomeScreen.lsf:201`](../../src/main/lsfusion/storeTasks/home/HomeScreen.lsf)
(`calcValue(HomeMetric m, CheckObject o) += WHEN code(m) = 'myOpen' AND o IS CheckObject`).
Грабли известные, наступать второй раз не надо.

Приведение к `ISTRING[100]` тоже обязательно: конкатенация складывает длины операндов,
и без явного каста реализация окажется шире объявленного класса — сервер не стартует.

> **Картинка (#37125)** — тем же приёмом и по той же причине: значение считается в
> `notify()` и записывается в `image(Notification)`, а не вычисляется при чтении.
> Уведомление — документ о том, что случилось, а не окно в текущее состояние:
> переименовали задачу, дописали в переписку — запись в журнале этого не замечает.
> Поле — уведомления, а не «комментария»: любое будущее событие с картинкой показывается
> тем же способом, и клиент про виды событий по-прежнему не знает.
>
> **Исключение — цепочка (3.1).** Открытая запись потокового события переписывает
> `title`/`body`/`image` и сбрасывает «прочитано» на каждое слитое событие: она и есть
> «что нового в переписке», и застывший текст первого сообщения дня в ней был бы ошибкой
> (возврат #36717: утреннее «принято» вместо вечернего «срочно перезвоните»). Меняет её
> только своё следующее событие, не чтение состояния; миниатюра — от последнего
> сообщения, и сообщение без снимка её снимает. Записи суточных событий не меняются
> вовсе.

## 5. Что данные, а что код

Честная граница, без попыток построить движок правил:

| | Где живёт | Почему |
|---|---|---|
| Условие срабатывания | **код** — `WHEN` в модуле события | у каждого события оно своё; DSL под них — месяц работы и никто им не воспользуется |
| Кому адресовано | **данные** — роли на объекте (#36708), автор, исполнитель, наблюдатели (#37135) | это то, что меняется у каждого заказчика |
| Каким каналом | **данные** — матрица `on(NotificationEvent, NotificationChannel)` | включить почту для одного события — настройка |
| Отключение | **данные** — `mute(TaskPerformer, NotificationEvent)` | иначе первым делом отключат всё целиком |
| Текст | **код рядом с событием** — `+=` (раздел 4) | текст неотделим от того, что произошло |

Новое событие = одна реализация `title`/`body` плюс один `WHEN` с вызовом `notify()`
и, если о событии стоит знать и подписанным, `notifyWatchers()` рядом. Журнал,
доставки, API и клиент при этом не трогаются вообще. В этом и состоит
универсальность — не в конфигурируемости условий, а в том, что добавление события
не расходится по системе.

## 6. Доставка асинхронна

Отправка **не** должна происходить в той же сессии, что бизнес-операция. Если SMTP
не отвечает, откатится назначение задачи — то есть сбой почты станет сбоем работы.

Поэтому: событие создаёт `Notification` и строки `Delivery` по включённым каналам;
регламентное задание разгребает неотправленные и вызывает `send`. Ошибка пишется
в строку доставки и остаётся видимой, попытки считаются.

Строка доставки — на (уведомление, канал, **редакция**), и создаёт её
`WHEN SETCHANGED(revision(n))`: первая редакция — рождение записи, каждая следующая —
слияние события в цепочку (3.1), и обе уходят наружу. Новая строка, а не сброс
`sent`/`attempts` у старой: старую в этот момент может отправлять регламент в своей
сессии, и его `APPLY` затёр бы сброс — второе сообщение уехало бы в никуда молча.
Строка прошлой редакции, до которой регламент не дошёл, помечена `supersededDelivery`
и не отправляется: текст берётся из записи в момент отправки, и она ушла бы вслед за
новой тем же текстом.

**Недоставленное ищется в списке уведомлений**, а не в доставках выделенной записи
(возврат #36717): `failedDeliveries(Notification)` — счётчик строк, исчерпавших попытки,
— даёт колонку «Не доставлено» в журнале (пусто — всё ушло) и фильтр «Есть
недоставленные» на самом списке. Фильтр на блоке доставок список не сужал: чтобы найти
две сотни проваленных доставок, пришлось бы перебрать все записи по одной, а «уходят ли
уведомления вообще» администратор хочет увидеть первым делом.

События первой версии:

| Код | Когда | Кому |
|---|---|---|
| `taskAssigned` | назначен исполнитель | исполнителю |
| `deadlineNear` | срок наступает завтра | исполнителю |
| `overdue` | срок прошёл, задача открыта | исполнителю, затем по цепочке ролей |
| `fillingFinished` | проверка завершена | ответственным ролям объекта |
| `correctiveCreated` | создано корректирующее действие | исполнителю |
| `taskClosed` | задача закрыта или отменена — проведение (#36987) | исполнителю и автору, кроме закрывшего; наблюдателям |
| `acceptancePending` | результат сдан на приёмку (#37157) | принимающему, кроме сдавшего |
| `taskAccepted` | результат принят — вместо `taskClosed` (шов `suppressClosed`) | исполнителю и автору, кроме принявшего; наблюдателям |
| `taskReturned` | возвращено на доработку, причина в теле | исполнителю, кроме вернувшего; наблюдателям |

Первое и последнее — обычные `WHEN`. Остальные три — регламентное задание, и именно
им нужна дедупликация из раздела 3.

`taskClosed` (2026-09-24) — реакция точки проведения `onProceed` (`StoreTaskCore`,
#36987): одна на закрытие любым путём — по выполнению, сменой статуса на карточке, в
списке, на доске и с телефона, кнопкой «Провести», — и ни одной на повторное закрытие
переоткрытой задачи (`proceeded`). Отмена — та же точка и те же адресаты, другой текст
(`canceledTask`). Реакция живёт внутри транзакции закрытия и потому только пишет журнал;
наружу запись несёт доставка (раздел 6) — отклонённый `APPLY` не оставляет ни записи, ни
письма, а повтор транзакции после конфликта не даёт второго. Закрывший исключается по
`currentUser()`, как написавший в `NotificationComment`.

## 7. Приложение

```lsf
apiNotifications () {
    EXPORT JSON FROM
        event = id(event(Notification n)),
        dateTime = dateTime(n),
        title = title(n),
        body = body(n),
        taskId = id(task(n)),
        viewed = viewed(n),
        imageId = LONG(image(n)),                              // #37125
        watching = viaWatch(n),                                // #37136
        today = (currentDate() IF n IS Notification)           // #37125
        WHERE performer(n) = currentPerformer()
            AND dateTime(n) >= subtract(currentDate(), 30);
} @@api;
```

* **Адресация для «прочитано»** — по паре (событие, задача, дата), той же, что образует
  суточный ключ. Внутренние идентификаторы объектов наружу не отдаём. Сервер отмечает
  перебором по адресу, а не через ключ: у цепочки (3.1) ключа по дню нет, и записей с
  одним адресом за день бывает две — закрытая утром и открытая вечером. Саму цепочку
  тап не закрывает — закрывает прочтение переписки.
* **Глубина 30 дней.** Журнал растёт неограниченно, и «отдать всё» однажды станет
  ответом на мегабайт. Старое чистится регламентом.
* **Счётчик непрочитанного считает клиент** — полный список у него и так есть, и
  отдельная ручка ради числа не нужна.
* **Прочитанным делает тап, а не открытие ленты** (#37125). Сначала было наоборот —
  открыл список, значит прочитал всё; с пузырями это перестало годиться: непрочитанное
  теперь заливка всей записи, главный признак экрана, и терялся он после первого же
  взгляда. Событиям, которые открывать незачем («просрочена», «проверка завершена»), —
  «Отметить все прочитанными» в шапке.
* **Миниатюра — идентификатором, а не байтами** (#37125): `imageId` качается ручкой
  `apiTaskFile?id=&thumb=1` тем же правом `canDownload`, что и вложения переписки.
* **`today` — серверное «сегодня»** (#37125). Заголовки ленты («Сегодня», «Вчера», «На
  этой неделе», «На прошлой неделе», «Ранее») считаются от него: телефон в чужом часовом
  поясе или со сдвинутой датой иначе разложил бы записи по чужим заголовкам — та же
  ловушка, что #36944 закрыл для «на сегодня» и «просрочено». Полем в каждой строке, а не
  конвертом `{today, items}`: ответ остаётся массивом, и клиент прежней версии на новом
  сервере читает ленту, как читал.
* Экран — лента пузырей с заголовками по датам и переходом на задачу (#37125;
  непрочитанное — заливкой пузыря, а не точкой справа). Клиент сейчас обновляется
  по возврату связи и pull-to-refresh ([`task_repository.dart:107`](../../mobile/pulse_tasks/lib/data/task_repository.dart));
  таймер добавляется тривиально, и уведомление, доехавшее за минуту, на демо от пуша
  неотличимо.

## 8. Пуш — отдельно и позже

> Сделано в #36720: `PushDevice.lsf` (реестр), `NotificationDelivery.lsf` (матрица
> событие × канал и регламент отправки), `FcmAuth.lsf` (OAuth2-токен Google), `PushFcm.lsf`
> (канал), `DeviceApi.lsf` (ручки), `FcmAssertionAction.java` (подпись JWT). Что завести и включить —
> [push-fcm-setup.md](push-fcm-setup.md). Раздел ниже — исходный разбор, он же и есть
> объяснение принятых решений.

Настоящий пуш — это только FCM. Что он потребует:

* **Инфраструктура заказчика:** проект Firebase на его Google-аккаунте,
  `google-services.json`, для iOS — платный Apple Developer и APNs-ключ.
* **Аутентификация к FCM.** Простой серверный ключ (`Authorization: key=...`) выключен;
  HTTP v1 требует OAuth2-токена сервисного аккаунта, то есть подписи JWT. В lsFusion это
  либо небольшой `INTERNAL`, либо отдельное действие обновления токена. **Это главный
  технический риск задачи**, и оценивать её без этого пункта нельзя.
* **Реестр устройств:** `CLASS Device` (токен, исполнитель, платформа, версия, последний
  контакт), `apiRegisterDevice` / `apiUnregisterDevice`, обработка протухших токенов.
* **Клиент:** `firebase_core` + `firebase_messaging`, запрос разрешения (iOS и Android 13+),
  обработчики в фоне и на переднем плане, переход на задачу из уведомления.

Мина безопасности: токен привязан к паре «устройство + пользователь». Выход из аккаунта
**обязан** снимать регистрацию, иначе уведомления следующего сотрудника уедут на телефон
предыдущего — вместе с названиями объектов и содержанием задач.

Промежуточного варианта нет: локальные уведомления с фоновым опросом на Android душатся
оптимизацией батареи, а на iOS не работают вовсе. Разбудить убитое приложение без FCM
нельзя, и обещать это не следует.

Зато сам канал встаёт в готовую конструкцию одной реализацией `send(Delivery)` — ничего
из разделов 2–7 при этом не меняется. Ради этого разделение на слои и делалось.

**Замена в шторке** (2026-09-16): `android.notification.tag` и заголовок
`apns-collapse-id` = `событие:задача` (`PushFcm.pushTag`). Пуш новой редакции цепочки
встаёт на место прежнего, а не рядом с ним — шторка держит одну строку с растущим
счётчиком; суточным событиям тоже не вредит: сегодняшняя «просрочена» встаёт на место
вчерашней. Замену делает система телефона, приложению для неё не нужно ни строчки.
Повторный пуш беззвучным сделать нельзя — звук решает канал `pulse_tasks`, и каждое
сообщение цепочки звучит.

## 9. Нерешённое

1. **Кто получает `overdue` вторым шагом.** Эскалация «исполнителю, потом руководителю»
   требует иерархии ролей на объекте, а #36708 даёт плоский набор. Либо порядок ролей
   как данные, либо эскалация ограничивается одним шагом.
2. **Почта: адрес исполнителя.** У `TaskPerformer` нет email — он есть у пользователя
   хоста. Нужно абстрактное свойство и реализации в мостах, как `id` и `name`.
3. **Вложение акта в письмо** — зависит от печатной формы (черновик 5 бэк-офиса).
   До неё письмо о завершённой проверке несёт только вердикт и ссылку.
4. **Тихие часы.** Проверки идут днём, но просрочка считается ночным регламентом.
   Отправлять в 03:00 не стоит; окно отправки — настройка канала, не события.
5. **Что делать с уведомлением о задаче, которую потом удалили.** `DELETE` на ссылке
   удалит и уведомление; возможно, правильнее сохранить его без ссылки.
