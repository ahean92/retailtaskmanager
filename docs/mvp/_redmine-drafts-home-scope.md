## 1. [Мобильный] Плитка сводки: «здесь» и «всего», когда числа расходятся — ЗАВЕДЕНО #36751

**Цель.**

Плитка и список отвечают на разные вопросы, а пользователь об этом не предупреждён.
«Открытых: 6» считается по всей сети — все задачи, назначенные исполнителю. Тап по плитке
открывает список задач **одного** магазина, потому что `apiTasks` дополнительно режет по
гео. На демо-наборе это видно в чистом виде: шесть открытых задач лежат по одной на шести
разных объектах, и список в любом из них показывает одну строку против шести на плитке.

Расхождение не косметическое. Человек видит «6», приходит в магазин, открывает список,
находит одну задачу и делает вывод, что приложение потеряло пять. Дальше он либо звонит,
либо перестаёт верить цифре — оба исхода дороже, чем показать вторую цифру рядом.

Правильный ответ — не выбрать одну из цифр, а показать обе: «сколько здесь» и «сколько
всего». Первая говорит, что делать сейчас, вторая — сколько работы осталось по маршруту.

**Состав.**

- Блок `myKpi` считается в разрезе объекта: флаг `byObject`. Сервер уже умеет считать
  `calcValue(m, o)` по объекту для всех трёх показателей и уже кладёт их в `values`
  ответа `apiHome` — новый запрос не нужен, число «здесь» приезжает тем же ответом.
- Плитка показывает вторую, сетевую цифру **только когда она отличается**: «3 здесь ·
  6 всего». Совпали — одно число, без хвоста. Иначе на исполнителе с одним магазином
  плитка вечно дублирует сама себя и превращается в шум.
- Тап ведёт в список того же магазина, что и цифра «здесь». Плитка и список обязаны
  отвечать на один вопрос — ради этого всё и делается.
- **Объект без задач обязан давать ноль, а не сетевую цифру.** Сегодня в `values`
  попадают только объекты с непустым значением (`WHERE ... AND (value(m, po) OR
  target(m, po) OR previous(m, po))`), а `GROUP SUM` при нуле возвращает `NULL` — то есть
  магазин, где у исполнителя задач нет, в ответ не попадает вовсе. Клиентский
  `valueFor()` в этом случае откатывается на сетевое число, и плитка покажет «6 здесь ·
  6 всего» вместо «0 здесь · 6 всего». Чинить с одной из двух сторон: либо отдавать
  объекты блока целиком (условие непустоты снять), либо на клиенте различать «объекта нет
  в ответе» и «значение отсутствует» и в первом случае показывать ноль. Первое проще и
  честнее: разрез по объекту на то и разрез, чтобы в нём были все объекты.

**Готово когда.**

На демо-наборе (шесть открытых задач по шести объектам) плитка «Открытых» показывает
«1 здесь · 6 всего»; при переключении на магазин без задач исполнителя — «0 здесь ·
6 всего»; на объекте, где лежат все его задачи (здесь 4 = всего 4), — просто «4», без
второй половины. Тап в каждом случае открывает список ровно той длины, что и цифра
«здесь».

**Зависит от.**

Формально — ни от чего, плитку можно сделать и проверить отдельно. Практически проверка
«тап открывает список той же длины» **не пройдёт**, пока не закрыт баг из раздела ниже:
клиент зовёт `apiTasks` без координат, и для исполнителя с обязательной геолокацией
список сейчас приходит пустым при любой цифре на плитке. Либо вести тикеты вместе, либо
принимать этот по первым двум критериям, а сверку со списком отложить.

**Подсказки.**

Сервер: `mobile/HomeScreen.lsf:201-206` — `calcValue(m, o)` по объекту для `myOpen` /
`myToday` / `myOverdue`, уже написаны; `:254-261` — вложенный `values` в `apiHome` и то
самое условие непустоты; `:108` — флаг `byObject`; `:408` — блок `myKpi` в
`loadDefaultData`, где флаг проще всего проставить по умолчанию.

Клиент: `models/home.dart:248` — `valueFor(objectId)` с откатом на сетевое число (место
ловушки с нулём); `models/home.dart:193-219` — разбор `values`; `data/task_repository.dart:287`
— выбранный объект с откатом на первый присланный; `data/settings.dart:25` — он же в
хранилище; `ui/home_screen.dart:131` — переход по тапу.

**Риск.**

Формулировка «3 здесь · 6 всего» на узкой плитке. Для трёх показателей в ряд места мало,
и вторая цифра может не влезть на маленьком экране. Вёрстка — за исполнителем; смысловое
требование только одно: обе цифры читаются, и видно, какая из них какая.

**Оценка.** S.

## Не входит: два оставшихся расхождения

Найдены в том же разборе, здесь **не решаются**, нужны отдельные тикеты.

**1. Клиент не шлёт координаты в `apiTasks` — список пуст.** Регрессия от ветки
`mvp_tasks`: у ручки появилась сигнатура `(lat, lon, objectId)`, а `api_client.dart:62`
по-прежнему зовёт её без параметров с комментарием «parameterless by design». Для
исполнителя с обязательной геолокацией `chosenObject(NULL, NULL, NULL)` пуст, условие
`checkObject(t) = chosenObject(...)` не выполняется никогда, и список приходит пустым при
любом содержимом базы. Это самое срочное из трёх: сегодня полевой сценарий не работает
вовсе. Журнал координат (`api/GeoLog.lsf`) фиксирует такие обращения — записи с пустыми
широтой и долготой и есть они.

**2. «Сегодня» и «просрочено» считаются в двух местах.** Сервер для показателя берёт
`currentDate()` (`mobile/HomeScreen.lsf:197`), клиент для списка — `DateTime.now()`
устройства (`data/task_repository.dart:44`). Разные часовые пояса и переход через полночь
дают разный ответ, причём поверх уже разных наборов задач. Лечится переносом признаков на
сервер: `apiTasks` отдаёт по задаче готовые `dueToday` / `overdue`, клиент фильтрует по
ним, а не пересчитывает. Тогда дата остаётся одна на всю систему.
