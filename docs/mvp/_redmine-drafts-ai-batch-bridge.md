## Тема

**[#37494](http://support.luxsoft.by/issues/37494) [Задачи] Массовая постановка задач:
механизм и мостик с erp; AI — потребитель** — оценка M–L.

## Цель

Срез #36992 — его пункт 2 «Пачка по критериям», но в правильном порядке зависимостей:
**механизм массовой постановки существует сам по себе и работает без AI**, AI — один из
его потребителей. Механизм живёт в артефакте (`StoreTaskLib`), а не в `ai/`; постановка
текстом лишь вынимает из фразы критерий и общие поля и отдаёт механизм остальное.

Эталонный пример на весь тикет, два входа в один механизм:

1. *Руками, без AI*: в вебе выбраны тип/бланк, текст «Снять с продажи товар
   „Товар 1“», критерий «все активные магазины» → предпросмотр → N задач одним
   подтверждением.
2. *Через AI*: та же работа одной фразой «Срочно снять с продажи товар „Товар 1“ во
   всех активных магазинах» — «срочно» → приоритет, «во всех активных магазинах» →
   критерий, который модель возвращает, остальное делает тот же механизм.

Критерий, под который не попал ни один объект, — вопрос человеку, а не пустая пачка
(правило #36992).

## Что уже есть и не переписывается

- Задача создаётся обычным механизмом (`apiCreateTask` и его десктопный путь),

- Шов разрезов: `ObjectDimension.dimensionValue` — `ABSTRACT (CheckObject,

  erp-хост — из своих данных); разрез уже используется для отбора и группировки в
  `report/ScorecardReport.lsf`.
- Решения #36992, которые наследуются: предпросмотр пачки обязателен и со списком;
  потолок пачки настройкой; право на массовое создание — именованное (#36839);
  веб-форма AI — потребитель общей логики, второй разбор не плодить.

## 1. Мостик с erp: критерий «активные магазины»

У `CheckObject` сегодня нет признака активности, и «во всех активных магазинах» на
сервере не во что превратить. У исполнителя такой шов есть — `archived 'В архиве' =
ABSTRACT BOOLEAN (TaskPerformer)` (`storeTasks/meta/TaskPerformer.lsf`); у объекта
проверки его нет.

- В `task/CheckObject.lsf` — шов по образцу существующих: `archived = ABSTRACT VALUE
  OVERRIDE BOOLEAN (CheckObject)` (имя — как у `TaskPerformer.archived`), артефактная
  реализация `+= FALSE` («все объекты активны» — standalone ничего не замечает),
  erp-мост добавляет свой признак закрытого магазина `+=`. Форма ровно та же, что у
  `dimensionValue +=` в `ObjectDimensionValue`: непустая поздняя реализация побеждает,
  пустая откатывается на умолчание.
- erp-сторона — в `erp-logics`, модуль `StoreTaskErp`: там свой объект проверки `Store`
  и свои мосты, артефактные `erp/`-модули на стенде не подключены.
- **Про `ABSTRACT LIST` из постановки.** В платформе это форма абстрактного *действия*
  — выполняются все реализации по очереди (в подсистеме так устроены `onCreate`,
  `onProceed`, `seedRequiredData`, `fillRows`). Для отдачи списков значений она не
  годится: реестр критериев строится на абстрактных *свойствах* и `+=`, как
  существующие швы. `ABSTRACT LIST` оставить про запас на точку расширения «хост
  дополняет созданную пачку своей реакцией» — сейчас не закладывать.

Не в объёме: ассортиментный критерий («по магазинам, где товар в продаже») — шва для
товарных данных в артефакте нет, отдельная история; товар в примерах — содержание
текста задачи, а не критерий отбора.

## 2. Механизм массовой постановки (ядро тикета)

- **Реестр критериев отбора** на абстрактных швах: разрез + значение (`dimensionValue`)
  и признак активности (`archived` из п.1). Отбор объектов и их число считает сервер, а
  не модель и не клиент.
- **Веб-форма пачки**, самостоятельная точка входа: общие поля (тип, бланк, срок,
  приоритет, текст/описание) + выбор критерия + **предпросмотр со списком попавших
  объектов**, лишние выбрасываются. Одно подтверждение → N обычных задач, создаются тем
  же механизмом, что единичная.
- Потолок пачки настройкой; право на массовое создание — именованное; пустой критерий —
  вопрос человеку («нет объектов с таким разрезом»), а не пачка из нуля задач.
- Механизм проверяется автотестом без AI-сервиса (стиль `scripts/tests/*_check.lsf`) —
  это и есть критерий его самостоятельности.

## 3. AI — потребитель механизма (в объёме #36992)

- Черновик-пачка в `AiTaskDraft` (веб-чат из п.1 #36992): модель возвращает критерий —
  не список объектов, механизм делает отбор, предпросмотр и создание. Шестой инструмент
  `AiTools` (виды разреза и их значения) — из #36992.
- Второго пути создания нет: и руками, и из AI пачка идёт через один и тот же код
  механизма; у AI только разбор фразы.

## Готово когда

Руками: критерий «активные магазины» и текст с «Товар 1» на erp-стенде дают предпросмотр
из **только активных** магазинов; лишние выбрасываются; одно подтверждение создаёт
задачи, и они открываются как обычные. Через AI: фраза-эталон целиком доходит до того же
предпросмотра, приоритет — срочный. Критерий без объектов — вопрос, а не пустая пачка.
Без права на массовое создание пачка не создаётся. Автономный артефакт (без erp) ведёт
себя как раньше: все объекты активны, форма пачки работает без AI-сервиса.

- У `CheckObject` (`task/CheckObject.lsf`) шва активности нет; у `TaskPerformer` есть —
  `archived 'В архиве' = ABSTRACT BOOLEAN (TaskPerformer)` (`meta/TaskPerformer.lsf:19`,
  `active` рядом на :21).
- `ObjectDimension.dimensionValue` — `ABSTRACT ISTRING[150] (CheckObject,
  ObjectDimension)` (`task/ObjectDimension.lsf:22`); `ObjectDimensionValue` наполняет
  его `+=` — образец формы для моста.
- ABSTRACT LIST — семантика по документации платформы (ABSTRACT action, LIST = все
  реализации по очереди до RETURN) и по коду: `onProceed`/`onCreate`/`startExecution`
  (`task/StoreTaskCore.lsf`), `seedRequiredData` (`StoreTaskSettings.lsf:7`),
  `fillRows` (`fillable/HostRow.lsf:8`).
- `docs/mvp/ai-task-creation-design.md` — уже в master (ветка
  `claude/ai-task-creation-tool-35de14` слита, 23cde030); пачки в ней нет — она целиком
  в #36992.
