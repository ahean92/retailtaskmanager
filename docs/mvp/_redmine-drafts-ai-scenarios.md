# Черновик задачи: сценарии автоматизации поверх реестра операций, вызов текстом из контекста

> Статус: **черновик, в Redmine не заведено** (2026-10-08). Проект `retail-help-desk`
> (id 221), трекер «Изменение» (id 2). Область — «AI»; первый срез по существу
> «Задачи» (массовая постановка). Оценка: эпик, первый срез — M.
>
> Откуда: обсуждение эволюции AI-контура (2026-10-08). Сегодня есть два этажа —
> «Задача словами» (маршрутизация текста в одну готовую ручку) и «Гипотезы»
> (генерация кода проверки с утверждением человеком). Средний этаж — композиция
> готовых операций текстом — отсутствует: рутина, которую система умеет делать
> по частям, человек повторяет руками.

---

## Тема

**[AI] Сценарии автоматизации: реестр операций и вызов их текстом из контекста объекта/выборки, с подтверждением и журналом** — эпик; первый срез M.

## Мотивировка

В системе уже есть операции, из которых складывается ежедневная рутина руководителя:
`apiCreateTask` (в цикле = массовая постановка), отчёты `report/`, каналы доставки
`notification/`, расписание `SchedulePlan`, реакция на закрытие `onProceed`. Но
соединяются они только кодом или руками:

- «устроить внеплановую проверку во всех магазинах фильтра» — 27 ручных постановок
  или разовый скрипт администратора;
- «каждый понедельник сводку проваленных проверок руководителю» — не делается вовсе
  (`processNotifications` умеет только сроки);
- «эскалация, если авария не взята за два часа» — только доработкой кода.

При этом AI-контур уже решил главные вопросы для одной операции: «Задача словами»
(`ai/`) маршрутизирует текст в `apiCreateTask` с параметрами, модель видит короткие
списки и отвечает парами «id + подсказка», решение и валидация — на сервере,
исполняет человек после подтверждения. Предложение — обобщить этот контур с одной
операции до реестра.

## Сущность предложения

Не «текст → новый код» (это контур гипотез), а «текст → композиция уже существующих
операций». Модель — маршрутизатор и заполнитель параметров, не генератор.

Слои:

1. **Реестр операций** — справочник `Operation`: код, имя, описание (пишется в первую
   очередь для модели), схема параметров, признак «требует подтверждения», права.
   Диспетчеризация — реализацией по коду операции (`run` + `ACTION+` в модуле
   операции); EVAL по строковому имени не появляется. Новая операция — маленький
   модуль (прецедент: механики `ScoreBy*`).
2. **Сценарий** — запись, связывающая операцию с параметрами и контекстом; первый
   срез — одношаговые сценарии (одна операция с параметрами = 80% рутины).
   Многошаговость (`Scenario → Step` с маппингом результатов) — отдельный этап.
3. **Контекст вызова** — обобщение `aiRequestObject`: текущий объект, выделенные
   строки, фильтр списка уезжают в подбор вместе с текстом и сужают кандидаты
   (принцип `inAiContext`: права, роль, близость).
4. **LLM-контур** — тот же паттерн, что у черновиков: короткие списки в контексте,
   плоский ответ «operationId + параметры + вопрос», разбор подсказок и валидация
   на сервере. Локальная модель, один вызов, без агентного цикла. Разрешение
   ссылок-параметров (объект, исполнитель, шаблон) — переиспользовать контур
   `AiDraftDecision` / `AiSearchApi`.
5. **Подтверждение с превью** — граница «модель предложила → человек согласился»
   вместо чтения кода: перед исполнением показывается план («27 задач, шаблон,
   срок, исполнители»). Для массовых операций превью обязательно — аналог потолка
   `maxCount` у гипотез: ошибка сценария видна людям сразу, а не в прогоне.
6. **Журнал вызовов** — как `AiRequest`/`TaskRequest`: кто, когда, из какого
   контекста, что предложила модель, что подтверждено, что получилось; ключ
   идемпотентности для повторного запуска.

Режимы жизни сценария (этапы 3–4): разовый вызов из контекста; сохранённый с
расписанием (обобщение `SchedulePlan` с «шаблон раз в N дней» до «операция +
выборка + правило срока»); событийный (подписка на `onProceed`, заявки intake,
таймеры-эскалации).

## Принципы (унаследованы из ai-draft и #37494, не изобретать заново)

- **Механика самостоятельна, AI — только интерфейс** (как пачки в #37494): сценарий
  выбирается и запускается руками из справочника; текст — ускоритель. LLM недоступна —
  рутина не останавливается.
- Модель не исполняет — предлагает; решение, валидация и права — на сервере.
- Данные в модель не уезжают: короткие списки, собранные сервером.
- Подтверждение человеком — обязательная граница; для массовых — с превью.
- Операция исполняется от прав подтвердившего, и именно это попадает в журнал.

## Сценарии использования (по убыванию ценности первого среза)

1. **Внеплановая проверка по выборке** (бэк-офис). Стоишь в реестре объектов/отчёте
   с фильтром: «внеплановая проверка выкладки во всех этих до пятницы, исполнители —
   директоры». Операция `createTasksByObjects`: объекты из фильтра, шаблон и срок из
   фразы, назначение по роли. Превью «27 задач» → подтверждение. Естественный
   потребитель механизма пачек #37494.
2. **Сводка по расписанию**. «Каждый понедельник в 8:00 — сводка проваленных
   проверок за неделю мне и региональным». Операция «отчёт + доставка» — обе части
   готовы, сценарий связывает их.
3. **Пересчёт позиции из отчёта**. «Пересчитать эту позицию везде, где продаётся,
   к концу недели» — recount-задачи с `subjects` (механика передачи позиций уже
   есть в intake/`foundRows`).
4. **Клон задачи на другой контур**. Из карточки: «повторить то же на остальных
   магазинах улицы» — параметры из текущей задачи, объекты из контекста.
5. **Развёртка по дочерним объектам** (мобильный). Стоишь в магазине: «проверить
   все кассы» — по дереву `CheckObject`.
6. **После закрытия проверки** (событийный, этап 4). «При провале критичных полей —
   корректирующая тому же исполнителю, автор — наблюдателем»: `onProceed` есть,
   сценарий делает правило строкой данных вместо кода.
7. **Эскалация по времени** (этап 4). «Не взята за два часа — поручить региональному
   и уведомить».
8. **Обогащение внешней заявки** (этап 4). Заявка MITE → задача (есть) + «уведомить
   директора площадки, поставить наблюдателем» — без доработки intake под случай.
9. **Массовые статусы** (последний, самый рискованный). «Вернуть на доработку все
   непринятые за неделю» — с гвардом матрицы переходов и превью непрошедших строк.

## Этапы

1. **Реестр операций + массовая постановка, без AI.** Справочник `Operation`,
   операция `createTasksByObjects` (параметры: шаблон, срок, приоритет, политика
   исполнителя, выборка объектов), превью и подтверждение, журнал вызовов.
   Выбор операции руками из справочника. Кандидат на связь с пачками #37494.
2. **AI-маршрутизация.** Контекст вызова (объект/выделенное/фильтр), эндпоинт
   ai-service по образцу `/v1/task-draft` (новый, например `/v1/scenario-pick`),
   разбор параметров переиспользованием контура `AiDraftDecision`, карточка
   подтверждения с превью.
3. **Повторяющиеся сценарии.** Расписание поверх операций (обобщение `SchedulePlan`),
   стартовый сценарий — сводка №2.
4. **Событийные сценарии.** Подписки на `onProceed`/intake-события/таймеры,
   многошаговость `Scenario → Step`.

## Границы первого среза (что НЕ входит)

- Многошаговые сценарии и маппинг результатов шагов.
- Операции записи статусов (№9) — только после обкатки контура подтверждения.
- Событийные сценарии и эскалации.
- Генерация новых операций текстом — этого не будет вовсе: отсутствие операции —
  воронка в контур гипотез, не в реестр.

## Критерии приёмки (первый срез, этап 1)

1. Справочник операций: код, имя, описание, права; заведена операция массовой
   постановки задач по выборке объектов.
2. Запуск руками без AI: выбрать операцию → указать параметры (форма) → превью
   (список объектов, счётчик, сводка параметров) → подтверждение → задачи созданы
   обычным механизмом `apiCreateTask`.
3. Журнал вызовов: кто, когда, операция, параметры, контекст, исход; повторный
   запуск с тем же ключом не дублирует задачи.
4. Превью обязательно для операции с множеством объектов; подтверждение — всегда.
5. `get_file_problems` на изменённых файлах чисто (с оговорками AGENTS.md), служба
   стартует успешно; ядро (`StoreTaskCoreLib`) не потребует новых пакетов.

## Открытые вопросы (решить на постановке)

- Положение в графе модулей: механика реестра — отдельный отключаемый пакет
  (`scenario/`, ядро его не требует), AI-фасад — в `ai/`; или всё в `StoreTaskAiLib`.
- Схема параметров операции: хранить JSON (`DATA TEXT`) с разбором формой против
  типизированных полей на каждую операцию (как `QuickAction`).
- Состав реестра первого среза: только `createTasksByObjects` или сразу
  «отчёт + доставка» (№2 без AI уже полезна).
- Первый клиент: бэк-офис (веб) или мобильный; предложение — бэк-office, там контекст
  выборки/фильтра богаче.
- Связь с пачками #37494: сценарий — потребитель групповой семантики пачки или
  независимый вход; не делать два механизма массовой постановки.
