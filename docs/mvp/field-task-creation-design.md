# Создание задачи в поле (дизайн)

> Проверяющий приехал на объект и начинает внезапную проверку; заведующий идёт по
> магазину, видит бардак на витрине и ставит задачу сотруднику этого магазина.
> Сегодня задачи заводятся только в бэк-офисе.
> Решение по объёму принято 2026-08-07: **офлайн-создание**, не «онлайн-форма».
> Статус: дизайн, не реализовано. Ветка `mvp_tasks`.
> Нерешённое — в разделе 11.

## 1. Это два сценария, а не один

|  | Внезапная проверка | Поручение |
|---|---|---|
| Исполнитель | я сам | другой человек |
| Что заполняется | шаблон задаёт всё | человек пишет текст |
| Что происходит сразу после | открывается бланк | задача уходит в чужой список |
| Тип задачи | `form` / `checklist` — есть | `issue` — **такого типа нет** |
| Офлайн-риск | нужен предзагруженный шаблон | нужен предзагруженный список людей |

Общее — только момент «создать `Task` на объекте, где я стою». Значит серверная ручка
одна, а входов в интерфейсе два, и второй тянет за собой новый тип задачи с выполнением.

Сливать их в один экран нельзя: у них разный обязательный минимум. У проверки это
шаблон, у поручения — текст и исполнитель. Общая форма «заполните что-нибудь из
десяти полей» — это форма, которую в поле не заполняют.

## 2. Что именно можно создать — данные, а не код

В проекте дважды сделан один и тот же приём: конфигурация как данные плюс матрица
видимости по ролям — [`ArmMenuItem`](../../src/main/lsfusion/storeTasks/mobile/StoreTaskArm.lsf)
и [`HomeBlock`](../../src/main/lsfusion/storeTasks/mobile/HomeScreen.lsf). Третий случай
того же — не совпадение, а способ проекта не выпускать APK на каждое пожелание заказчика.

```lsf
CLASS AssignPolicy 'Кому назначать' {
    self   'Себе',
    pick   'Выбрать из списка',
    byRole 'По роли на объекте'
}

CLASS QuickAction 'Быстрое создание';
code 'Код' = DATA STRING[30] (QuickAction) IN id;
quickAction = GROUP AGGR QuickAction a BY code(a);
title 'Название' = DATA ISTRING[50] (QuickAction) IN id;
icon 'Иконка' = DATA STRING[10] (QuickAction) CHARWIDTH 5;
actionOrder 'Порядок' = DATA INTEGER (QuickAction);
active 'Активен' = DATA BOOLEAN (QuickAction);

type 'Тип задачи' = DATA TaskType (QuickAction);
template 'Шаблон' = DATA Template (QuickAction);
assignPolicy 'Кому' = DATA AssignPolicy (QuickAction);
objectRole 'Роль на объекте' = DATA ObjectRole (QuickAction);   // зависит от #36708
deadlineOffset 'Срок, дней' = DATA INTEGER (QuickAction);
priority 'Приоритет' = DATA TaskPriority (QuickAction);
requirePhoto 'Требовать фото' = DATA BOOLEAN (QuickAction);
requireComment 'Требовать описание' = DATA BOOLEAN (QuickAction);

// та же матрица ролей, что у пунктов АРМ и блоков главной
roleOn 'Вкл.' = DATA BOOLEAN (QuickAction, UserRole);
hasRoleScope (QuickAction a) = GROUP SUM 1 IF roleOn(a, UserRole r);
inCurrentRole (QuickAction a) = GROUP SUM 1 IF roleOn(a, UserRole r) AND has(currentUser(), r);
visible (QuickAction a) = active(a) AND (NOT hasRoleScope(a) OR inCurrentRole(a));
```

Кнопка «+» на телефоне показывает ровно то, что разрешено этому пользователю.
«Внезапная проверка витрины» для Санты — строка в справочнике, а не сборка клиента.

**Объект не выбирается пресетом.** Он всегда тот, который выбран в приложении сейчас
(клиент уже умеет переключать объект — `objects` в `apiHome`). Экран создания показывает
его и позволяет сменить. Заводить `ObjectPolicy` рядом с `AssignPolicy` было бы
симметрично и бесполезно: варианта «фиксированный объект» в поле не бывает.

## 3. Ключ клиента — центральное решение

Весь офлайн-контур клиента прибит к `taskId`, который выдаёт сервер: `outbox.taskId
PRIMARY KEY`, `fill_outbox (taskId, fieldCode)`, `fill_photos (taskId, fieldCode, idx)`
в [`local_db.dart`](../../mobile/pulse_tasks/lib/data/local_db.dart). Задачи ещё нет на
сервере — значит нет ключа — значит писать ответы и фото некуда.

Клиент генерирует UUID в момент создания и живёт с ним всегда:

```lsf
clientId 'Ключ клиента' = DATA STRING[36] (Task);
taskByClientId = GROUP AGGR Task t BY clientId(t);

// сервeрный ST-номер имеет приоритет: он авторитетен, как только появился
taskByAnyId (STRING[50] s) = OVERRIDE task(s), taskByClientId(STRING[36](s));
```

Что это даёт:

* **Идемпотентность бесплатно.** `GROUP AGGR` — тот же приём уникальности, что у
  `taskType`, `taskStatus`, `armMenuItem`, `homeBlock`. Повторная отправка того же UUID
  не создаёт вторую задачу. Связь плохая, клиент ретраит — ничего не двоится.
* **Клиенту не нужно переписывать свои ключи после синхронизации.** Он всегда адресует
  задачу по UUID; `ST-000123` — отображаемый атрибут, а не ключ.
* **В `FillApi` меняется одна резолвящая функция.** Все `apiSetField`/`apiSetCell`/
  `apiSetFieldPhoto` начинают понимать оба вида адреса, не меняя сигнатуры.

Форматы ST-номера и UUID не пересекаются, поэтому `OVERRIDE` однозначен. Приведение
к `STRING[36]` намеренное: UUID ровно 36 символов, ST-номер короче.

### 3.1. `apiTasks` обязана отдавать `clientId`

Иначе после первой же синхронизации телефон покажет задачу дважды: свою локальную и
приехавшую с сервера. Клиент сопоставляет строки по `clientId` и схлопывает их.
Это не деталь реализации, а часть контракта ручки.

## 4. Создание

```lsf
apiCreateTask (FILE body) {
    LOCAL aClientId = STRING[36]();
    LOCAL aType = STRING[20]();
    LOCAL aObject = ISTRING[30]();
    LOCAL aTemplate = STRING[30]();
    LOCAL aAssignee = ISTRING[50]();
    LOCAL aName = ISTRING[250]();
    LOCAL aCreated = DATE();
    LOCAL aDeadline = DATE();
    LOCAL aPriority = STRING[20]();
    LOCAL aComment = ISTRING[500]();
    IMPORT JSON FROM body AS FILE TO() aClientId = clientId, aType = typeId, ... ;

    IF NOT aClientId() THEN throwException('clientId required');
    IF NOT taskType(aType()) THEN throwException('Type not found: ' + aType());
    IF NOT checkObject(aObject()) THEN throwException('Object not found: ' + aObject());
    IF taskByClientId(aClientId()) THEN RETURN;          // уже создана — повтор

    NEWSESSION NESTED (...) {
        NEW t = Task {
            clientId(t)    <- aClientId();
            type(t)        <- taskType(aType());
            checkObject(t) <- checkObject(aObject());
            name(t)        <- aName();
            start(t)       <- aCreated();
            deadline(t)    <- aDeadline();
            ...
        }
        APPLY;
        IF canceled() THEN throwException(applyMessage());
    }
} @@api;
```

Что делается само и переписывать не надо:

* `author(t)` — [`StoreTaskCore.lsf:40`](../../src/main/lsfusion/storeTasks/task/StoreTaskCore.lsf)
  подставляет `currentPerformer()`; Basic-auth уже определяет пользователя.
* `status(t)` — событие по `SETCHANGED(type)` ставит первый допустимый статус типа.
* `start(t)` — событие `start(Task t) <- currentDate() WHEN SET(...)` в **вычисляемой**
  форме, поэтому явное присваивание в сессии его перебивает. Это важно: задача, созданная
  офлайн три дня назад, должна иметь дату создания с телефона, а не дату синхронизации.

Что **не** делается само:

* **Тип обязателен в запросе.** `defaultTaskType()` не NULL только когда тип ровно один
  ([`StoreTaskType.lsf:63`](../../src/main/lsfusion/storeTasks/task/StoreTaskType.lsf)),
  а типов уже три. Задача без явного типа получит NULL и упадёт на констрейнте статуса.

## 5. Что должно приехать на телефон заранее

Внезапная проверка в дальнем магазине без связи — это и есть заявленный сценарий.
Значит к моменту создания на телефоне уже должны лежать:

| Что | Ручка | Зачем |
|---|---|---|
| Пресеты | `apiQuickActions` | что вообще можно создать |
| Шаблоны с полями, опциями и колонками | `apiTemplates` | иначе бланк нечем рисовать |
| Исполнители с их ролями на объектах | `apiPerformers` | иначе некому назначить |

`apiExecutionFields` не годится: она адресуется по `taskId`, а задачи ещё нет.

Объём `apiTemplates` ограничивается сам собой — отдаются только шаблоны, на которые
ссылается видимый пресет:

```lsf
inQuickAction (Template t) = GROUP SUM 1 IF template(QuickAction a) = t AND visible(a);
```

Плановые задачи в этом не нуждаются: у них задача существует, и поля приезжают как
сегодня. Предзагрузка нужна ровно под создание на месте.

`apiPerformers` отдаёт только людей, у которых есть роль хотя бы на одном объекте —
это и есть множество, кому вообще можно поручать. Для Санты полный список сотрудников
в качестве выпадашки бесполезен: 263 магазина.

## 6. Порядок синхронизации

Сегодня очереди независимы и синкаются каждая сама по себе. Для созданной офлайн
задачи порядок становится обязательным:

```
создать задачу → начать выполнение → значения полей → фото → завершить
```

Отправить ответ раньше задачи — получить `Filling not found`. Очередь создания должна
быть барьером для всех остальных очередей этой задачи. Это единственное место, где
в клиенте появляется зависимость между очередями, и его надо написать явно, а не
надеяться на порядок по `createdAt`.

## 7. Тип «Поручение»

`CorrectiveExecution` — это уже «фото + комментарий + завершить»
([`Corrective.lsf:24`](../../src/main/lsfusion/storeTasks/corrective/Corrective.lsf)).
Поручение — то же самое, отличается только происхождением: одно родилось из
несоответствия в бланке, другое — из того, что человек увидел глазами.

Поэтому: класс выполнения переименовывается в нейтральный (`SimpleExecution`),
`Corrective` остаётся типом задачи со ссылкой на исходный пункт, добавляется
`Issue.lsf` — тип `issue` на том же выполнении. Это прямое продолжение решения
#36472 («корректирующее действие — тип задачи, а не отдельная сущность»).

Две вещи, которые при этом легко потерять:

* **Миграция.** Переименование класса — запись `CLASS` в `migration.script`, и вдобавок
  отдельные записи `STORED PROPERTY` на каждое его DATA-свойство (`photo`, `comment`,
  `mirroredPhoto`, `mirroredComment`): переименование класса меняет их канонические
  имена, а автоматически это не отслеживается. Без записей столбцы уедут в `_deleted`,
  и данные выполнений пропадут молча. `migration.script` в репозитории ещё нет — этот
  тикет его заводит.
* **Обязательность фото перестаёт быть константой.** Сейчас констрейнт требует фото
  у любого завершаемого `CorrectiveExecution`. Для поручения «позвонить поставщику»
  это неверно. Требование переезжает в данные — `requirePhoto` пресета, а через него
  флаг на задаче.

## 8. Чего в коде сегодня нет

Найдено при разборе, всё — предпосылки, без которых ручки не пишутся:

1. **У `Template` нет стабильного кода.** Есть только `templateByName`, и в комментарии
   [`Template.lsf:27`](../../src/main/lsfusion/storeTasks/fillable/Template.lsf) честно
   написано «demo/seed helper; names are not enforced-unique». Клиент не может назвать
   шаблон, который хочет открыть. Нужен `code` + `GROUP AGGR`, как у всех остальных
   справочников подсистемы. Существующие шаблоны кода не имеют — свойство остаётся
   необязательным, а в `apiTemplates` попадают только шаблоны с кодом.
2. **Нет связи «исполнитель ↔ объект».** `TaskPerformer` и `CheckObject` в модели не
   связаны никак, а сценарий — «назначить на человека **с выбранного магазина**».
   Это `responsible(CheckObject, ObjectRole)` из **#36708**. Зависимость настоящая.
3. **Нет справочника исполнителей в API.** `apiTasks` отдаёт только имя строкой.
4. **`usesTemplate` объявлено на `Task`, а нужно на `TaskType`** — пресет должен уметь
   проверить «этому типу нужен шаблон» до того, как задача появилась. Свойство
   переезжает на тип, а версия для задачи становится композицией с тем же именем.

## 9. Мины

1. **Дубль задачи на экране после первой синхронизации** — если `apiTasks` не отдаёт
   `clientId`. Самая заметная и самая обидная: выглядит как потеря доверия к приложению.
2. **Порядок очередей** (раздел 6). Проявится не сразу, а на первой же проверке,
   заполненной целиком офлайн.
3. **Дата создания** — если не передать её с телефона, все офлайн-задачи получат дату
   синхронизации, и «просрочено» посчитается неправильно.
4. **Миграция при переименовании класса выполнения** (раздел 7) — молча теряет данные.
5. **Пресет ссылается на шаблон объектной ссылкой, а `apiQuickActions` отдаёт его код.**
   Если шаблон пересоздадут, ссылка уцелеет, а код может уехать. Это тот же риск, что
   записан в #36710 про категорию объекта, и лечится так же: сверять по коду.

## 10. Прошлая проверка при заполнении

Пункт, отложенный при обсуждении, но дешёвый и заметный на демо: при заполнении пункта
показывать значение и вердикт того же пункта по тому же объекту в прошлый раз. Данные
все есть — `previousFilling` через `GROUP LAST` по объекту и шаблону, два поля в
`apiExecutionFields`, подпись на плитке. Отдельный тикет, S.

Ограничение, которое надо назвать сразу: это подсказка, а не сверка. Никакой логики
«стало хуже — значит нарушение» здесь быть не должно, иначе балл начнёт зависеть от
истории, и одинаково заполненные бланки будут давать разный результат.

## 11. Нерешённое

1. **Может ли исполнитель поручения быть не из справочника?** Заведующий может захотеть
   поставить задачу на человека, которого в системе нет. Свободный текст в исполнителе —
   это долг перед отчётностью (та же мина, что с предметом строки в
   [fillable-rows-design.md](fillable-rows-design.md)). Пока считаем, что нет.
2. **Что делать с задачей, созданной офлайн на объект, который к моменту синхронизации
   исчез из хоста?** Магазин закрылся, ERP его убрала. Сейчас ручка бросит исключение,
   и задача навсегда застрянет в очереди. Нужен явный исход: отбрасывать с уведомлением
   автору или создавать без объекта.
3. **Ограничение на создание.** Сегодня любой, кто видит пресет, создаёт задачу на любой
   объект и на любого человека. Роли из #36708 дают рамку, но правило («заведующий ставит
   задачи только по своему магазину») нужно сформулировать с заказчиком.
4. **Внезапная проверка — это тоже проверка?** Она попадёт в те же отчёты и тот же
   рейтинг объектов, что и плановая. Заказчик может считать иначе. Признак «внеплановая»
   в задаче стоит завести сразу, даже если сначала он ни на что не влияет.
5. **Сколько шаблонов реально уедет на телефон.** Ограничение «только те, на которые
   ссылается видимый пресет» решает проблему по построению, но проверить объём на данных
   Санты надо до того, как это уедет в поле.
