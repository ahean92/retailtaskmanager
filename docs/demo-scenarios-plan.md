## 1. Доработки

### ~~A. Раскладка позиций заявки в строки задачи~~ — на этом стенде НЕ НУЖНА

Мост ерп уже делает её целиком ([TaskItemRowErp]): `subjects` заявки (коды товаров
через запятую, пишет их и гипотеза) раскладываются событием в `requestedItem(Task,
Item)` — состав задания; при старте выполнения `fillRows` заводит строки бланка с
остатком и ценой в readonly-колонках `sysqty`/`sysprice`. Следствия:

- `foundRows` в проверках гипотез — **коды товаров erp (`Item.id`)**, не штрихкоды;
  штрихкод резолвится в товар внутри кода проверки;
- шаблоны «изъятие/пересчёт» используют host-поле (`rowSource = 'host'`,
  `subjectKind = 'item'`) с колонками по кодам `sysqty`/`sysprice` + факт-колонки;
- коды, которых нет в erp, молча пропускаются — демо-товары заводим заранее.

Остаётся в бэклоге для standalone/mite-хостов (там раскладки нет) — тикет при
отдельном решении.

### ~~B. Остатки с количеством (SubjectStock)~~ — на этом стенде НЕ НУЖНА

Остатки/цена берутся из erp (`erpBalance`/`erpPrice` по отделам магазина). SubjectStock
— опция standalone/mite-хостов, здесь не участвует.

### C. Демо-остатки на стенде — РЕАЛИЗОВАНО документами, правка кода не нужна

Остатки заведены штатным документом ерп «Изменение остатков (польз.)»
(`demo_promo_03_stock.lsf`): на торговый отдел каждого магазина (отделы перенесены
из santa2, 8 шт.). Магазины разведены 2026-10-11 и по ассортименту, и по количествам:
С-216 — позиции 1–200 групп (1063 строки, 10 весовых в отборе ≤1 кг, дробные
штучные 2,5/0,5/1,5), С-272 — позиции 52–251 (675 строк, 13 весовых ≤1 кг на других
кодах, дробные на других товарах) — гипотеза находит непересекающиеся наборы.
Проверено (`verify_stock2.lsf`): currentBalance материализуется, отбор находит
ровно ожидаемое. Ловушки: количество строки — `quantity` (не `sum` — это деньги),
`description` документа перезаписывается нумератором (идемпотентность — по признаку
«документ отдела со строками-количествами»).

## 2. Сценарий 1 — сроки годности → задача на изъятие

**Механика**: шаблон `expiry-check` (таблица `goods`: `barcode` scan, `best_before`
date, `qty` number) → гипотеза `expired` → прогон по регламенту («ESB:Задачи — гипотезы по
расписанию», раз в 15 минут проверяет назревшие; период гипотезы 24 ч) → заявка →
правило приёма `hypothesis/expired` → задача «Изъятие просрочки» на магазин.
Состав позиций: `foundRows` (коды `Item.id`) → `requestedItem` → строки бланка при
старте выполнения (штатный путь моста, без доработок).

**Дедуп**: ключ находки «магазин#дата последней проверки» — повторные прогоны не
плодят задачи; новая проверка с той же неизъятой просрочкой — новая задача.
«Через 2 дня» получается само: находка возникает в первый прогон, когда записанный
«годен до» стал ≤ текущей даты.

**Корректировка формулировки** (текст — в разборе от 2026-10-09): foundRows — коды
товаров erp (`Item.id`), полученные резолвом штрихкода строки (subjectCode → товар
по штрихкоду erp; при наличии subject — его код); проверка читает заполнения
семейства `expiry-check`.

**Демо-данные**: молочка (кефир/молоко/творог) с штрихкодами, привязанная к магазинам
С-216/С-272; заполнение в С-216 с `best_before` = сегодня (задача встанет в первый
же прогон на глазах), в С-272 = +2 дня (задачи НЕТ — в этом смысл «через 2 дня»).
**Живая проверка** (2026-10-12, `demo_promo_15_quickaction.lsf`): пресет QuickAction
`expiry-check` «Проверка сроков годности» — сотрудник с телефона сам заводит проверку
и сам выполняет: назначение «Себе» (для бланочного пресета это и констрейнт артефакта),
тип checklist + шаблон `expiry-check`, срок — тот же день, приёмки нет; виден всем
сотрудникам (ролевая матрица не отмечена).

**Шаги показа**:
1. Веб: карточка гипотезы — формулировка, код проверки, воронка, потолок находок,
   утверждение, «В расписании».
2. Телефон: сотрудник сканирует бутылки в проверке сроков, завершает.
3. Прогон `runDue` eval-скриптом (или ожидание ≤15 мин).
4. Веб/телефон: задача на изъятие встала, исполнитель по роли, позиции — строками
   бланка с системным остатком; повторный `runDue` — второй задачи нет.
5. Телефон: исполнитель изымает (фиксирует по строкам), завершает; принимающий
   принимает.

**Проверки (чек-скрипт)**: задача создана одна; повторный прогон не создаёт вторую;
нет правила приёма → карантин с причиной; потолок находок срабатывает.

## 3. Сценарий 2 — весовые товары с остатком ≈1 кг → пересчёт

**Механика**: гипотеза `weigh-recount` по остаткам магазина (`storeBalance`):
позиции весовые (признак — единица товара «кг», уточнить по данным стенда) с
`0 < остаток ≤ 1` (порог — параметр формулировки; «±1 кг» уточнить у заказчика) →
находка на магазин, `foundRows` = коды товаров → задача типа `recount` «Пересчёт
весового остатка» (шаблон с host-полем: `sysqty`/`sysprice` readonly + факт. вес).
Кнопки «Создать задание на пересчёт» на форме «Товары» — показать как ручной вход
к тому же шаблону.

**Данные**: ГОТОВО — `demo_promo_03_stock.lsf`: С-216 — весовые 0,35–0,95 кг ×10
(в отборе) + контрольные 1,2–2,4; С-272 — свой срез позиций (52–251), 13 весовых
0,28–0,98 в отборе; штучные с дробным остатком в обоих. Отбор по магазинам даёт
разные товары — удобно показывать «по всем магазинам».

**Контур**: ГОТОВ end-to-end 2026-10-12 — `demo_promo_09_weigh.lsf` (шаблон
`weigh-recount` с host-полем: sysqty readonly + «Факт. вес»; правило приёма
hypothesis/weigh-recount → тип recount, срок 1 день, роль zav), `demo_promo_10…`
(гипотеза `weigh-recount`, код в `scripts/demo/data/promo_weigh_check.lsf`:
весовой признак — «ВЕС» в имени группы, дробность — `остаток != ROUND(остаток, 0)`,
дедуп — дата прогона + магазин), `demo_promo_11…` (прогон: 2 находки → задачи
ST000386/387 с 16/13 позициями, повторный прогон дублей не даёт). Ручной вход —
кнопка «Создать задание на пересчёт» на форме «Товары» (мост, шаблон «Пересчёт
остатков» уже есть).

**Дедуп**: период = дата прогона/неделя — пересчёт по позиции не чаще раза в N дней
(решить при написании кода).

**Шаги показа**: остатки → прогон → задачи пересчёта на «плохие» магазины → телефон:
взвесил/вписал факт → завершение.

## 4. Сценарий 3 — чек-лист подготовки акции с перечнем позиций и приёмкой

**Механика** (из коробки): тип `checklist`, шаблон «Подготовка акции» (пункты-оценки:
выкладка/ценники/реклама + host-поле позиций канала `item`). Состав позиций — руками с
формы «Товары» (отметки → «Создать задание», механика TaskItemRowErp), из задачи
напрямую (вкладка «Позиции») или демo-сидом. Исполнитель проходит чек-лист, сдаёт →
«На приёмке» → принимает/возвращает с причиной. Приёмка включается на ЗАДАЧЕ
(`acceptancePolicy = required`) — тип не трогаем, чтобы не затронуть остальные
чек-листы стенда; без acceptRole на типе принимает АВТОР задачи.

**Реализовано** (2026-10-12, `demo_promo_12_promo_prep.lsf`): шаблон `promo-prep`
«Подготовка акции» (Да/Нет-оценки, «ценники заменены» критичный, фото выкладки
обязательно, host-поле позиций с sysqty + «Выложено»), набор вариантов «Да/Нет»
заводится сидом. Задачи PROMO-216/PROMO-272 «Чистота со скидкой» (мыло + паста,
единый состав из 6 позиций, у 272 непрод. остатки появились — малые группы в
`demo_promo_03_stock.lsf` теперь едины на оба магазина): автор sup.demo, исполняют
заведующие, приёмка «Требуется» (принимает sup.demo — сдающий ≠ принимающий).

**Шаги показа**: постановка → телефон: чек-лист с позициями → сдача → веб: приёмка
(принять/вернуть) → лента/уведомления.

## 7. «Стандартная библиотека гипотез» — концепция и решение

Гипотеза — данные (код проверки живёт в `HypothesisVersion.script`), «библиотека» —
сид-модуль артефакта, заводящий готовые гипотезы с написанным кодом: БЕЗ утверждения
и БЕЗ расписания — человек стенда читает код и включает сам (граница «прочитано
человеком» сохраняется).

**Критерии включения** (по каждой после демо): код проверки опирается только на данные
артефакта и хоста (FillRow, остатки хоста), не на данные конкретного заказчика;
параметры — в формулировке/коде; у гипотезы есть владелец в продукте.

**Кандидаты**: `expired` — да; `weigh-recount` — да, но код проверки зависит от
источника остатков хоста (erp `storeBalance` vs standalone `SubjectStock`) — в
библиотеку как формулировка + код под ерп-хост, вариант для standalone отдельно.

Сценарии 3–4 — шаблоны/типы, не гипотезы; их «стандартность» = готовые шаблоны
в демо-сидах. Решение о включении — после демо; до него гипотезы живут в демо-скриптах.
