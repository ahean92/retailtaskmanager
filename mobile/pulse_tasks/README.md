# Пульс — Задачи (Flutter MVP)

Мобильный клиент подсистемы **StoreTask** (задачи для магазинов). Offline-first:
список задач и смена статуса работают без связи, изменения ставятся в очередь и
синхронизируются автоматически при появлении сети.

## Что умеет MVP

- Загрузка списка открытых задач из lsFusion (`/exec/StoreTask.apiTasks`).
- Кэш в локальной SQLite — список читается мгновенно и **работает офлайн**.
- Карточка задачи: объект, тип, детали, срок, приоритет, исполнитель.
- Смена статуса задачи. Офлайн изменения пишутся в **outbox** и синхронизируются
  (`/exec/StoreTask.apiSetStatus`) при восстановлении связи или вручную.
- **Заполнение чек-листа** (задачи типа `checklist`): пошагово по разделам, крупные
  кнопки вариантов / числовой ввод + комментарий при несоответствии, бегущая оценка и
  вердикт (считается локально — работает офлайн), завершение с серверной проверкой.
  Ответы кэшируются и синхронизируются через отдельную очередь. Фото — следующим шагом.
- **Выполнение поручения фотоотчётом** (#36872): снимки (сколько нужно), комментарий и
  «Выполнено» — на экране без бланка; тем же экраном закрывается корректирующее
  действие. Работает офлайн: снимок, комментарий и завершение ложатся в очереди и
  уезжают при связи в порядке создание → старт → фото → комментарий → завершение. Если
  задача требует фото, кнопка недоступна, пока снимка нет; отказ сервера показывается
  причиной, а не «успехом».
- **Чем открывать задачу, решает сервер**: `executionKind` в `apiTasks` и в пресетах
  создания (`fill` — бланк, `simple` — фотоотчёт). Новый тип задачи появляется в
  приложении без его пересборки; список типов внутри клиента остался запасным путём для
  старых серверов.
- **Вход по токену**: логин/пароль на экране входа, `Authentication.getAuthToken` отдаёт
  JWT, дальше все запросы идут с `Authorization: Bearer`. Пароль уходит на сервер только
  при выпуске токена. Токен живёт сутки и перевыпускается молча — на 401 клиент один раз
  меняет токен и повторяет запрос, повторный 401 сбрасывает сессию.
- **Вход без сети**: если сервер недоступен, пускает по совпадению пароля с локальным
  хэшем — но только если последний успешный обмен с сервером был меньше суток назад.
- **Гейт геолокации**: сразу после входа приложение спрашивает разрешение и определяет
  координаты; без них внутрь не пускает. Требование объявляет сервер (`geoRequired` в
  `apiCurrentUser`) — роли, которой геопривязка не нужна, гейт не выставляют.
- **Список — по объекту, на котором человек стоит**: в шапке списка название объекта,
  расстояние до него и кнопка «Обновить местоположение» (переехал в соседний магазин —
  нажал, список перестроился). Если рядом оказалось несколько объектов, по умолчанию
  выбран ближайший, остальные — из той же шапки, с расстоянием у каждого; если объект
  один, ничего не спрашивается. Пустой список всегда объясняет, почему он пуст: «на
  объекте задач нет», «рядом нет объектов с координатами», «ближайший в 12 км» и
  «неизвестно, где вы» — четыре разные ситуации и четыре разных действия.
- **Секреты — в защищённом хранилище**: токен, учётные данные и хэш пароля лежат в
  `flutter_secure_storage` (Keychain / Keystore), в `shared_preferences` их нет.
- Экран подключения (шестерёнка на экране входа): только адрес сервера, заполняется один
  раз при развёртывании.

## Требования

- Flutter SDK **≥ 3.24** (проверено на 3.44.7, Dart 3.12). Проверить: `flutter --version`.
  Нижнюю границу задаёт `geolocator` 14 (Dart ≥ 3.5).
- Для сборки APK — Android SDK с `cmdline-tools` и принятыми лицензиями
  (`flutter doctor` / `flutter doctor --android-licenses`), либо Android Studio.
- Устройство Android/iOS или эмулятор.
- Запущенный сервер lsFusion с модулем `StoreTaskApi` (см. ниже).

## Сборка и запуск

Платформенные папки (`android/`, `ios/`) уже сгенерированы и лежат в репозитории —
`flutter create` запускать не нужно. В каталоге проекта:

```bash
cd mobile/pulse_tasks
flutter pub get
flutter run              # на подключённое устройство/эмулятор
# либо собрать APK:
flutter build apk --release
```

Готовый APK окажется в `build/app/outputs/flutter-apk/app-release.apk`.

Тесты: `flutter test` — модульные, на хосте. Хранение секретов проверяется ещё и на
устройстве, там где настоящие Keychain/Keystore:

```bash
flutter test integration_test -d emulator-5554
```

Cleartext HTTP (для dev-сервера по `http://…:9080`) уже разрешён в
`android/app/src/main/AndroidManifest.xml` (`usesCleartextTraffic="true"`).
В проде за HTTPS этот атрибут можно убрать.

### Адрес сервера в приложении

- Реальное устройство в одной сети: `http://<IP-компьютера>:9080`
- **Эмулятор Android**: хост-машина видна как `http://10.0.2.2:9080`
- **Симулятор iOS**: `http://localhost:9080`

Кнопка «Проверить подключение» дёргает `apiBrand` — единственную ручку, которая отвечает
без аутентификации, поэтому адрес проверяется до входа и независимо от пароля. Логин и
пароль вводятся уже на экране входа (на dev-сервере — `admin` с пустым паролем).

## Серверная часть (lsFusion)

Модуль: [`src/main/lsfusion/storeTasks/api/StoreTaskApi.lsf`](../../src/main/lsfusion/storeTasks/api/StoreTaskApi.lsf),
подключён в `StoreTask.lsf`. Три эндпоинта (`@@api`, отдаются на web-порту):

| Метод | URL | Назначение |
|-------|-----|-----------|
| GET | `/exec/Authentication.getAuthToken` | Платформенный JWT в обмен на Basic (шаг 1 входа) |
| GET | `/exec/StoreTask.apiCurrentUser` | Профиль исполнителя за токеном (шаг 2 входа) |
| GET | `/exec/StoreTask.apiTasks?lat=&lon=&objectId=` | Открытые задачи вошедшего на этом объекте (JSON-массив) |
| GET | `/exec/StoreTask.apiNearbyObjects?lat=&lon=` | Объекты рядом с точкой, ближайший первым |
| GET | `/exec/StoreTask.apiStatuses` | Справочник статусов |
| POST | `/exec/StoreTask.apiSetStatus?id=<taskId>&statusId=<code>` | Смена статуса |

`getAuthToken` живёт в платформенном модуле `Authentication` (не в `StoreTask`) и отдаёт
голый токен текстом, а не JSON. Проверить руками:

```bash
curl -u admin: "http://localhost:9080/exec/Authentication.getAuthToken"
curl -H "Authorization: Bearer <token>" "http://localhost:9080/exec/StoreTask.apiCurrentUser"
```

Пример элемента `apiTasks` (null-поля опускаются):

```json
{"id":"ST000001","object":"Магазин №1 (Тверская)","objectId":"b24",
 "address":"ул. Тверская, 10","distance":118.4,
 "type":"Проверка по чек-листу","typeId":"checklist","status":"В процессе",
 "statusId":"in progress","deadline":"2026-07-25","subtitle":"Открытие магазина"}
```

`apiTasks` фильтрует по `currentUser()` на сервере — приезжают только задачи вошедшего,
клиентского фильтра по исполнителю больше нет (`assigneeId` в выгрузке остаётся, но уже
как справочное поле). Он же сужает список до одного объекта, если учётной записи нужна
геопривязка: до того, что передан в `objectId`, а если не передан — до ближайшего к
`lat`/`lon`. Учётная запись, которой геопривязка не нужна, получает весь свой список
независимо от параметров.

Пример элемента `apiNearbyObjects`:

```json
[{"id":"b24","name":"Магазин №1 (Тверская)","address":"ул. Тверская, 10",
  "latitude":55.765,"longitude":37.605,"distance":118.4,"nearby":true}]
```

Когда в радиусе (`Радиус «рядом», м` в настройках, по умолчанию 500) не оказалось никого,
ответ не пустой: в нём один ближайший объект **без** ключа `nearby`. Это то, чем клиент
отличает «объектам не проставили координаты» (пустой массив) от «до ближайшего 12 км».

Засеять демо-данные на сервере (8 задач в разных статусах):

```bash
curl "http://localhost:9080/eval/action" --data-urlencode "script=StoreTask.generateTestData();"
```

## Архитектура клиента

```
lib/
  models/        task.dart, task_status.dart, home.dart — модели + (de)сериализация
                 place.dart             — где человек стоит: объект, соседи, расстояния
  data/
    settings.dart          — адрес сервера и кэш оформления (shared_preferences)
    session.dart           — вошедший: токен, учётные данные, хэш пароля, время последней связи, координаты
    secure_store.dart      — Keychain / Keystore: единственное место, где лежат секреты
    password_hash.dart     — PBKDF2-HMAC-SHA256 с солью для офлайн-входа
    api_client.dart        — HTTP-клиент над /exec/StoreTask.* (Bearer + перевыпуск токена)
    geo.dart               — где телефон: разрешение, последняя известная позиция, замер
    local_db.dart          — SQLite: tasks, statuses, outbox, home_cache, place_cache
    task_repository.dart    — offline-first: кэш + outbox + синхронизация (ChangeNotifier)
  ui/            login_screen, geo_gate_screen, settings_screen, task_list_screen, task_detail_screen, widgets/task_card
  main.dart
```

**Хранение секретов.** Токен, логин с паролем и хэш пароля лежат в
`flutter_secure_storage`: на Android — `EncryptedSharedPreferences` под мастер-ключом из
Keystore, на iOS — Keychain с `first_unlock_this_device` (в iCloud и в бэкап устройства
такой элемент не попадает). Файл `FlutterSecureStorage.xml` исключён из Auto Backup
(`res/xml/backup_rules.xml`, `res/xml/data_extraction_rules.xml`): без ключа из Keystore
он всё равно нечитаем, а восстановление такого мусора роняет плагин. Адрес сервера, кэш
оформления и домашний экран остаются в `shared_preferences` — это не секреты.

Пароль хранится потому, что перевыпуск протухшего токена — это повторная аутентификация;
хэша (им проверяется вход без сети) для неё мало. Хэш — PBKDF2-HMAC-SHA256, 100 000
итераций, соль на каждое значение своя; параметры записаны в саму строку
(`pbkdf2-sha256$<итераций>$<соль>$<ключ>`), поэтому их можно поднять, не ломая старые
значения. Считается в отдельном изоляте — «Войти» не подвисает.

При обновлении поверх сборки, хранившей сессию в `shared_preferences`, `Session.load()`
один раз переносит значения в защищённое хранилище и стирает исходники; хэш пересчитывает
из перенесённого пароля, так что повторный вход не требуется. Токен переживает
перезапуск приложения (приложение офлайн-первое, требовать сеть ради открытия нельзя),
но живёт сутки, лежит в защищённом хранилище и стирается при выходе из аккаунта.

**Маршрут запуска.** Нет адреса → экран «Подключение»; нет сессии → экран входа;
координаты ещё не получены, а учётной записи они нужны → гейт геолокации; иначе → сразу
домашний экран. Сброс сессии (пароль сменили на сервере или пользователь вышел) снимает
открытые экраны и возвращает на вход.

**Геолокация.** Гейт стоит в маршруте запуска, а не внутри входа, поэтому его проходят и
те, кто заходит по сохранённой сессии: отозванное за ночь разрешение останавливает
приложение на пороге. Координаты берутся один раз за запуск (`TaskRepository.geoReady`) и
ложатся в сессию. Порядок вопросов к телефону — в `data/geo.dart`: включена ли геолокация,
есть ли разрешение (если нет — системный диалог), затем последняя известная позиция, если
она не старше пяти минут (иначе в холодильной камере и в подвале работать нельзя), и
только потом замер с таймаутом 15 с. Все четыре отказа ведут на один экран
(`ui/geo_gate_screen.dart`) с «Повторить» и «Открыть настройки»; выйти из учётной записи с
него можно, пройти мимо — нет. Требование объявляет сервер: `geoRequired` в
`apiCurrentUser` (роль с настройкой «Разрешить работу без геолокации» его не получает —
lsFusion не экспортирует NULL, поэтому отсутствие ключа и означает «не обязательно»).
Разрешения объявлены в `AndroidManifest.xml`, строка-объяснение для iOS —
`NSLocationWhenInUseUsageDescription` в `ios/Runner/Info.plist`; без неё iOS роняет
приложение при первом запросе.

**Объект, на котором человек стоит.** Координаты — это ещё не место: местом их делает
`apiNearbyObjects`, и его ответ вместе с выбранным объектом лежит в базе пользователя
(`place_cache`), а не в настройках устройства — объект принадлежит смене, а не телефону.
GPS дёргается ровно дважды: один раз за запуск (гейт) и один раз на нажатие «Обновить
местоположение»; открытие списка спрашивает не телефон, а то, что уже определено или
сохранено. Отсюда же берётся поведение без сети: замер телефон отдаст и офлайн (помнит
последнюю позицию), а сервер о соседях промолчит — тогда сохранённый объект остаётся в
силе, время определения в шапке не переписывается свежим замером, и кэш задач продолжает
фильтроваться по тому объекту, по которому он и приехал. Фильтр по объекту в клиенте
повторяет серверный намеренно: переключение в шапке перестраивает список сразу, не
дожидаясь ответа.

**Поток данных.** Чтения всегда идут из локальной БД (мгновенно, офлайн). `refresh()`
тянет с сервера и перезаписывает кэш. Смена статуса → запись в `outbox` (эффективный
статус задачи берётся из outbox, пока не подтверждён сервером) → попытка `syncOutbox()`.
При обрыве связи очередь сохраняется и досинхронизируется при реконнекте
(`connectivity_plus`) или по кнопке синхронизации в шапке списка.

## Ограничения MVP / что дальше

- `apiSetStatus` при ошибке (например, статус недопустим для типа задачи) возвращает
  HTTP 500; сейчас запись остаётся в очереди, ошибка показывается пользователю.
  Для прода стоит отделять постоянные ошибки от временных сетевых.
- Выполнение задач (заполнение чек-листа/пересчёта/ценников) в приложении не
  реализовано — только просмотр и смена статуса (см. роадмап `docs/mvp/roadmap.md`, п.14).
```
